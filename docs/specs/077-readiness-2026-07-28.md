# Spec 077 readiness decision — 2026-07-28

## Decision

Spec 077 — EVIDENCE-EGRESS-0 is promoted from `planned` to `ready`.

This decision authorizes one bounded implementation of the merged definition in
`docs/specs/077-evidence-egress-0.md`. It does not authorize a second egress
service, a new sensitivity level, raw S2/S3/S4 evidence egress, a new provider
route, a new BLUECAD state, a broader repair loop, UI work, or any Hermes/MCP
scope.

## Readiness evidence

The review confirmed:

- the full 077 definition is merged in PR #196 at master commit `060b59e8`;
- dependencies 044, 059a, 059b, and 076 are `merged`;
- merged 076 owns deterministic attempt-scoped evidence sight, bounded repair
  requests, valid-candidate lifecycle, and atomic successful pointer replacement;
- 059a already owns `evidence:<id>` sources, workspace-bound labels, source
  digests, sanitized derivatives, staleness, and S0/S1-only external eligibility;
- 059b already owns prompt/context authority, exact per-binding packets,
  confirmation, reservations, fallback re-evaluation, adapter invocation, and
  safe audit evidence;
- the current packet contract already digests included manifests and source
  digests, and the safe-manifest validator accepts bounded nested scalar metadata
  while rejecting prompt, content, body, credential, and secret fields;
- no open PR overlaps the 077 definition, registry, readiness decision, BLUECAD
  structural loop, or 059a/059b implementation files;
- no database migration is required for the chosen lineage representation.

## Binding decision 1 — attempt accounting

External evidence authority is prepared before a BLUECAD structural attempt is
inserted.

The implementation sequence is:

1. resolve the concrete route binding;
2. preserve the merged 076 path unchanged when the binding does not require
   network access;
3. for a network binding, re-render and validate the exact evidence sight in one
   coherent authority preparation step;
4. resolve labels, source digests, derivative authority, and any required local
   sanitization before `start_structural_attempt(...)`;
5. if preparation is denied, paused, stale, malformed, or sanitizer-failed,
   return the original valid candidate with zero external adapter calls, zero
   structural attempt rows, and zero structural-request budget consumption;
6. after preparation becomes eligible, insert the next candidate-wide structural
   attempt and call `run_ai_task` with the real workspace and one approved
   evidence derivative context block;
7. any later 059b denial, confirmation pause, provider configuration failure, or
   adapter failure is recorded as the outcome of that structural attempt and
   consumes exactly one structural request slot.

A local sanitizer AI job is not a BLUECAD structural request and never consumes
`max_structural_repairs`.

Preparation failures remain inspectable through safe events or existing egress
and sanitizer records. They must not create a synthetic BLUECAD attempt merely to
represent work that never entered the structural request boundary.

## Binding decision 2 — prompt authority

The external structural prompt is separate from canonical evidence context.

- Raw `EVIDENCE_SIGHT_V0` text must not appear in the network-bound user prompt.
- The external prompt contains only the repair instruction and the already valid
  GeometrySpec.
- Because current 059b intentionally rejects unclassified marker-free prompts
  when canonical context is present, the external structural prompt must use an
  existing deterministic prompt-derivative authority.
- That derivative is workspace-bound, final S1, versioned, digest-bound, and
  created or reused through the current 059b prompt-derivative store.
- The deterministic prompt derivative may preserve the exact safe external
  prompt bytes. This is explicit prompt authority, not a FAST_DEV exception or a
  new sensitivity default.
- Local and fake-provider 076 prompt bytes and prompt version remain unchanged.

## Binding decision 3 — evidence derivative identity

The existing canonical derivative remains the authority for evidence content.

For an exact-sight deterministic derivative:

- canonical `source_refs` remain the existing sorted, duplicate-free set;
- `source_digests` remain bound to the current canonical evidence snapshots;
- derivative content is exactly the rendered sight when all sources are current
  effective S0/S1;
- sanitized S2/S3/unknown evidence uses the existing local canonical-source
  sanitizer and produces a current effective S0/S1 derivative;
- `sanitizer_config_digest` binds the exact renderer configuration, including the
  ordered renderer refs, sight digest, renderer id/version, limits, workspace,
  candidate, and source attempt;
- `transformations` contains stable semantic identifiers and is not used as an
  opaque store for lineage.

The canonical derivative's sorted source-ref set is intentionally distinct from
the renderer order. Renderer order is preserved explicitly in packet lineage as
defined below.

## Binding decision 4 — packet-bound evidence lineage

No additive SQLite column or table is authorized.

The implementation extends the existing server-owned authorized-context manifest
with one bounded nested object named `evidence_lineage`. At minimum it contains:

- lineage schema/version;
- workspace id;
- candidate id;
- source BLUECAD attempt id;
- structural BLUECAD attempt id;
- ordered `evidence:<id>` source refs from `EvidenceSight.record_ids`;
- `EvidenceSight.digest`;
- renderer id/version;
- renderer `max_lines` and `max_chars`;
- derivative id, content digest, and effective level;
- sanitizer kind, version, config digest, and sanitizer AI job id when present;
- sensitivity and egress policy versions.

The ordinary derivative manifest and canonical source-digest map remain present.
The new lineage object carries no prompt, evidence line, derivative body, report
body, solver output, credential, or secret.

The lineage object must pass the existing recursive safe-metadata validator and
is included in `included_manifest_json`; therefore it is covered by the existing
exact packet digest. Any lineage mutation creates a different packet digest and
invalidates any prior decision, ticket, or reservation. Every fallback rebuilds
and re-evaluates the packet with the concrete provider/model and fallback index.

Lineage enrichment is server-only. No frontend or ordinary caller may submit,
override, or authorize it. The implementation may add one narrowly typed internal
argument or context-authority helper, but not a generic caller-controlled metadata
channel.

## Required model exposure

The current `sanitized_derivatives` table already stores sanitizer kind, version,
config digest, sanitizer AI job id, approval source, and auto-approval state. The
implementation may extend internal read models and server-only context helpers to
expose those existing fields.

This is a read-contract completion, not a migration. It must preserve all existing
API response schemas unless the spec explicitly requires an additive safe field;
prefer an internal server-owned model where public exposure is unnecessary.

## Implementation ownership

One branch, `spec/077-evidence-egress-0`, and one implementation PR own delivery.
Parallel implementation PRs are not authorized.

Expected bounded paths are:

- `backend/app/modules/bluecad/evidence_egress.py` — new coherent preparation and
  lineage owner;
- `backend/app/modules/bluecad/evidence_sight.py` — stable renderer metadata only;
- `backend/app/modules/bluecad/prompts.py` — dedicated external structural prompt
  and version;
- `backend/app/modules/bluecad/loop.py` — binding split, preparation ordering,
  workspace/context handoff, and existing lifecycle preservation;
- internal 059a/059b sensitivity, sanitizer, execution, or egress modules only for
  the smallest typed prompt-derivative and safe-manifest enrichment seams;
- focused 077 tests plus unchanged 076 regression tests;
- `docs/specs/STATUS.md` only for normal implementation lifecycle transitions.

No schema, migration, provider adapter, provider registry, route configuration,
frontend, process model, mesh/FEM adapter, runner, or workflow change is expected.
If implementation proves that the required lineage cannot be represented through
the existing packet manifest without weakening type or authority boundaries, stop
and return 077 to `planned`; do not hide lineage in unrelated JSON or add a schema
change within the implementation PR.

## Required delivery gates

The implementation PR may merge only when tests prove:

- exact workspace/candidate/source-attempt ownership and re-render equality;
- inserted, removed, reordered, replaced, or mutated evidence invalidates
  preparation;
- preparation failure creates no structural attempt and consumes no structural
  request slot;
- eligible preparation creates exactly one next-numbered structural attempt;
- a later 059b denial or pause is recorded on that attempt with zero adapter calls;
- local/fake-provider 076 prompt bytes, attempt counts, status, and pointers remain
  unchanged;
- the external prompt contains no raw evidence and has current deterministic
  prompt-derivative authority;
- evidence content appears exactly once as an approved derivative context block;
- sorted derivative source refs and ordered lineage refs are both correct and are
  tested as separate invariants;
- source refs/digests, sight digest, renderer metadata, workspace, candidate,
  source attempt, structural attempt, derivative, sanitizer, and concrete binding
  are packet-bound;
- mutating any lineage field changes the packet digest and invalidates prior
  confirmation authority;
- raw S2/S3/S4, stale, missing, revoked, sampled-audit-rejected, or policy-mismatched
  evidence produces zero external calls;
- no prompt/evidence/derivative/report/solver body enters safe logs or manifests;
- no candidate state, pointer, promotion, decision record, or structural-budget
  authority is widened;
- full backend pytest, Ruff, spec-status self-test, BLUECAD canary, and strict
  Gmsh/CalculiX proof are terminal green.

## Rollback boundary

If external evidence authority cannot be prepared without changing local 076
behavior, adding caller-controlled metadata, weakening 059a/059b, or introducing
an unapproved migration, keep external evidence-guided repair fail-closed, retain
all evidence, leave local 076 behavior intact, and return 077 to `planned`.

## Merge authority

The implementation agent may inspect, implement, test, diagnose CI, and update its
own branch. It must not merge or enable auto-merge. Final merge remains a human
maintainer decision after the exact implementation head and deterministic gates
are verified.
