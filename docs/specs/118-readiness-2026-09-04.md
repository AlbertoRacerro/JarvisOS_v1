## Existing owners reused / explicitly not reused

Merged 111 remains the sole common context owner:

- `backend/app/modules/ai/thread_service.py::_context_blocks_for_new_submit` keeps added exact-ref Jarvis context local-route-only by resolving the effective route and rejecting non-`local:` routes.

118 must integrate through that seam when repository evidence is admitted as Jarvis CONTEXT; it must not create a second context-preview/digest/staleness owner. The local-route-only restriction is preserved exactly. Repository inspection as a backend READ capability is not itself model-context admission.

### Existing GitHub/network transports

Fresh master already contains bounded GitHub transports, but none is a lawful product repository-truth owner for 118:
- `scripts/cheap_review.py::gh_request` — review tooling only;
- `scripts/verify_merge_authority.py::_request_json` — merge-authority verification only;

Reusing any of these inside product runtime would cross their accepted control-plane ownership and couple product repository truth to repository-development tooling. Therefore 118 needs one new product-only GitHub read transport function, but no generic SCM/provider framework.

### Architecture-enforcement ownership

`configs/architecture_enforcement.json` is already the canonical AE002 owner/exception registry. The new product transport is not under an automatically accepted provider directory, so the implementation PR must add exactly one review-visible AE002 `accepted_owner` entry for the concrete new transport symbol, with `owner_or_removal_spec: "118"`. The code symbol and config entry must land atomically on the same implementation head so `_validate_exception_targets` can resolve it. No broad path allowlist or generic network exception is authorized.

## Credential and repository mode

Fresh exact-master inspection found no existing product GitHub read credential seam that 118 can lawfully adopt without introducing new credential authority. The initial implementation is therefore **public configured repositories only** and requires no GitHub token.

- repository identities are explicit server-owned `owner/name` allowlist values;
- API host is exactly `api.github.com`;
- generated navigation host is exactly `github.com`;
- no request/model/frontend token field exists;
- private repository access returns a typed unavailable/authorization outcome and is deferred to a separately authorized credential extension;
- no environment-variable GitHub token lookup is added by 118.

This avoids both accidental reuse of repository-development credentials and creation of a new secret/config system.

Implementation is authorized only for the following bounded surface, revalidated against fresh master at implementation start:

1. `backend/app/modules/coding/__init__.py` — package marker only if the package does not already exist on the implementation base.

## Frozen operation behavior

The implementation allowlist remains exactly:
`repository_ref_truth`, `commit_truth`, `path_list`, `file_preview`, `literal_search`, `compare_truth`, `pull_request_truth`, `check_truth`, `review_truth`, `safe_github_url`.

Unknown or write-capable operations are rejected before network dispatch.

Every network-backed success includes configured repository identity and immutable resolved SHA evidence. PR/check/review results include the exact head/base or evaluated SHA evidence needed to detect stale state. Branch/ref labels alone are never sufficient truth.

## Literal search feasibility — exact-SHA public mode

118 must **not** use GitHub code-search as its truth source: that API requires authentication and cannot satisfy arbitrary exact-commit search semantics.

For the initial public-only implementation, `literal_search` is an exact-SHA bounded scan built from ordinary read-only repository tree/blob operations:
1. resolve the requested ref to one commit SHA;
2. enumerate repository paths at that exact SHA under the frozen tree/path bound;
3. deterministically select only regular text candidates within path/count/aggregate-byte limits;
4. read candidates by the exact SHA/blob identity and perform plain literal matching locally;
5. stop at the first deterministic bound and return `partial=true` with bound metadata rather than claim completeness.

This keeps search exact-ref, unauthenticated, read-only and deterministic. It is intentionally not semantic/fuzzy search and does not create a local clone/index. A repository whose searchable surface exceeds the bound receives explicit partial evidence.

## Frozen numeric bounds

Centralize these constants in the 118 owner and test them offline:
- decoded file preview: `262_144` bytes;
- aggregate provider payload consumed by one operation: `1_048_576` bytes;
- tree/directory entries examined: `1_000`;
- literal-search candidate files examined: `100`;
- literal-search matches returned: `100`;
- compare files returned/examined: `100`;
- PR/check/review items per collection: `100`;
- pagination: maximum `10` pages;
- connect timeout: `5.0` seconds;
- read timeout: `10.0` seconds;
- redirects: `0` automatic redirects; a provider redirect response is validated and only same approved host/repository semantics may be handled explicitly, otherwise fail closed;
- retries: maximum `1` retry and only for a clearly transient transport/provider failure; zero retries for validation, auth, stale-ref, malformed, partial/oversize or policy failures.

Any reached content/count/page bound is explicit partial/oversized evidence and is never represented as complete.

## Path, content and response safety

Before dispatch, reject absolute paths, `..` segments, encoded traversal/separators, backslash traversal, NUL/control characters, non-approved repository identity, non-approved host and arbitrary URLs.

Repository text is untrusted data. 118 never executes/imports/evals/shells/builds it, follows repository-controlled workflow instructions, or interpolates it into commands. Binary/invalid UTF-8 content is typed unsupported preview; no lossy decoding is used to fabricate text. Archive/submodule/LFS/symlink/provider-download indirection is not followed as an arbitrary URL.

Provider JSON is schema/shape validated before use. Malformed or inconsistent responses fail typed rather than being guessed.

## Audit / telemetry decision

118 does not introduce a durable audit table or an egress ledger because the accepted operation is read-only and a new persistence owner would be disproportionate. It does require one bounded safe application log event per attempted provider read through the new transport.

The event may contain only:
- stable event name, e.g. `coding_repository_read`;
- provider=`github`;
- operation family;
- a one-way SHA-256 digest of configured repository identity, not raw repository name;
- exact resolved commit SHA when known;
- coarse outcome category (`success`, `partial`, `not_found`, `unauthorized`, `rate_limited`, `timeout`, `provider_error`, `validation_error`);
- response byte/count metadata needed for bounds.

It MUST NOT contain credentials, Authorization headers, provider response bodies, file contents, patches, commit/PR/review text, search matches, arbitrary URLs, raw query strings or repository-controlled content. Tests capture logs and prove both positive event emission and forbidden-value absence.

This is telemetry only; it never becomes repository freshness or merge authority.

## Typed failure contract

The implementation must preserve distinct non-fabricating outcomes for:
- unauthorized repository/provider/host/operation;
- invalid/forbidden ref or path;
- missing repository/ref/path/PR;
- private/auth-required repository in the initial public-only mode;
- stale/moved ref or stale PR head;
- rate limited, timeout or provider unavailable;
- malformed/inconsistent provider response;
- redirect/host escape;
- binary/unsupported content;
- oversized/partial result.

No failure falls back to cached-as-current, alternate-host or model-supplied data.

## Deterministic offline acceptance matrix

The implementation PR must include focused fake-transport tests proving at minimum:

1. configured public repository succeeds without a credential and no GitHub token is read or exposed;
2. private/auth-required repository is typed unavailable/unauthorized rather than triggering credential discovery;
3. unauthorized repository and alternate host are rejected before transport dispatch;
4. arbitrary URL, redirects and redirect-host escape fail closed;
5. mutable ref resolves to an immutable SHA before content operations;
6. moved/stale ref or expected PR head mismatch cannot be represented as current;
7. absolute/backslash/control/`..`/encoded traversal variants are rejected;
8. binary and invalid UTF-8 preview remains typed unsupported;
9. each frozen count/byte/page bound yields deterministic partial/oversized state;
10. timeout, rate limit, auth, malformed JSON/shape and provider-unavailable responses remain typed;
11. literal search operates only over exact-SHA tree/blob reads, never GitHub code-search, and reports partial when candidate/tree/byte bounds stop the scan;
12. compare/PR/check/review evidence is associated with exact expected SHA and stale evidence is explicit;
13. workflow/check success is not converted into semantic review approval;
14. safe GitHub URLs are derived only from validated configured repository and validated commit/PR/path identifiers;
15. all mutation/write operation names are rejected before network dispatch;
16. repository-controlled text cannot trigger shell, workflow, provider rerouting, credential access or COMMIT/EXECUTE authority;
17. exactly one new AE002 accepted-owner entry targets the concrete 118 transport symbol and architecture enforcement remains green;
18. when used as Jarvis CONTEXT, the adapter is registered through merged 111, preview/digest/stale checks are reused, and non-local effective routes remain rejected;
19. safe audit log event is emitted for attempted provider reads and excludes credentials, repository content and raw repository identity;
20. all tests are offline; CI performs no live GitHub network call and uses no paid/provider credential.

## Readiness conclusion

The accepted 118 boundary is implementable on current master without a new credential, database, cache/index, local clone, generic SCM framework, direct frontend provider path, or second Jarvis context owner.

The one new network transport is necessary because current GitHub transports are repository-development/control-plane owners, not product runtime owners. Its AE002 registration is explicit and atomic with implementation. Public-only exact-SHA tree/blob scanning makes the mandatory literal search implementable without weakening exact-ref semantics.

After this readiness artifact is merged, the live registry may be transitioned mechanically from `planned` to `ready`. Only that fresh `STATUS.md = ready` state, with dependency 111 still merged and no competing implementation front, authorizes implementation.
