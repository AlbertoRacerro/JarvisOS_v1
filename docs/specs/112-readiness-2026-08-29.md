## Exact-master readiness findings

### Existing canonical owners are sufficient; no second Project truth store is needed

Fresh exact-master inspection confirms that the full specification's ownership split is implementable without duplicating canonical Project, modeling, proposal, dependency, freshness, run, or Jarvis truth:

- `backend/app/modules/modeling/service.py` still owns canonical `model_specs`, `assumptions`, `requirements`, `parameters`, `simulation_runs`, and `decisions` rows.
- `backend/app/modules/modeling/parameter_lifecycle.py` remains the Parameter stale-protected lifecycle/CAS owner and must be composed rather than bypassed.
- `backend/app/modules/memory/service.py` still owns proposal transitions and Parameter replacement promotion/freshness effects.
- `backend/app/modules/flowsheet/service.py` remains the dependency graph projection owner; 112 may construct only the bounded ephemeral proposed-state projection required by the accepted specification.
- existing 050/051/098 behavior remains authority for dependency/freshness/Parameter lifecycle semantics.

The new 112 persistence is therefore restricted to coordination identity, draft intent, validation/reconciliation evidence, immutable reconciled snapshot history, Requirement applicability, and the minimum owner metadata required by the accepted contract. It must never become a peer mutable copy of canonical Project/model values.

### Transaction-capable owner primitives are required and are not optional refactoring

Fresh code confirms two accepted gaps are real and implementation-critical:

1. `modeling.service.update_requirement()` performs an id-only update with no workspace CAS and no audit event.
2. `memory.service._transition()` and `promote_parameter_replacement()` currently open/commit their own connections/transactions.

Final reconciliation cannot safely compose those public wrappers. Implementation MUST extract minimum connection-taking primitives while preserving current public wrapper behavior. Equivalent connection-taking stale-protected primitives are also required for Assumption, ModelSpec, Requirement and accepted Decision mutations that 112 actually authorizes.

No implementation may simulate atomicity by sequencing HTTP calls or separately committed service calls.

### Requirement lifecycle and criterion semantics are frozen

Readiness confirms the current schema uses `requirements.status = draft | active | retired`; 112 MUST reuse that field and MUST NOT introduce a second Requirement lifecycle column.

The accepted V0 adds only the bounded Requirement-owned criterion metadata required by the specification, including `basis_kind`, typed criterion fields as specified, and `reconciliation_gate = required | advisory`. Historical rows must default to non-blocking/advisory semantics unless prior accepted repository authority proves otherwise.

Requirement human-readable criterion text remains `requirements.statement` with optional `rationale`. No non-existent `acceptance_criteria` prose field may be invented.

### Decision lifecycle must remain distinct from Memory proposal state

Current Decision rows reuse `status` for proposal-style states in MemoryStore paths. Therefore accepted-current Global Decision retirement must use the minimum separate owner lifecycle defined by the full-spec authority (for example `basis_lifecycle_state = active | retired`) rather than overloading proposal status. The exact column name may follow schema conventions but the two state machines must remain distinct and transactionally auditable.

### Reconciled historical state requires immutable snapshots

Current Requirement, Decision, Assumption, Parameter and ModelSpec owners mutate rows in place. Consequently the accepted reconciled snapshot manifest is necessary to make historical reconciled revisions reconstructable and branchable. It is immutable history, not a new current owner.

A successful reconciliation must atomically commit canonical owner mutations, proposal/replacement/freshness effects, working-chain consumption, reconciliation request success and the exact immutable reconciled snapshot manifest in one `BEGIN IMMEDIATE` transaction. Failure at any point rolls back all success effects together.

Historical branch/inspection must fail closed on missing, corrupt, unsupported, wrong-workspace or digest-mismatched snapshot evidence; it must never silently substitute current canonical values.

### Reconciliation idempotency is independently workspace-scoped

The final accepted contract requires one independent uniqueness scope:

`UNIQUE(workspace_id, idempotency_key)`

Working revision, target revision/digest, acknowledgement/policy identity, selected-validation-set digest and request digest are bound immutable values of that key, not additional uniqueness dimensions. Any same-key reuse with changed bound values is a deterministic conflict before canonical mutation.

### Validation history is append-only with one current row per slot

`project_knowledge_validation` must preserve append-only history and explicit `supersedes_validation_id` semantics. For each validation slot `(working_revision_id, criterion/rule identity, rule revision/version, validated-input/basis digest)`, exactly one unsuperseded current row may exist.

Final reconciliation must bind and re-check the exact selected current validation set digest inside the final transaction. Older PASS evidence can never be chosen after a newer admissible FAIL/not-evaluable row supersedes it.

Broken/cyclic/cross-slot supersession, multiple unsuperseded rows, missing current evidence, basis/source drift or a replacement appended after request creation all fail closed.

### Scalar result storage is revision-neutral; validation is revision-bound

The accepted scalar projection remains unique per `(run_id, output_name)` and represents an immutable observed result, not one consumer working revision. Revision-specific admissibility belongs in `project_knowledge_validation` and must prove workspace, immutable source result/run identity, exact source/input basis, criterion/rule identity and no recomputation-requiring drift.

A sibling revision may reuse one scalar only when its exact basis remains admissible. Changed source inputs require truthful recomputation/stale handling rather than scalar duplication or silent reuse.

### Requirement applicability is a minimum relationship seam, not copied Requirement data

The exact master has no accepted Requirement-to-model/version applicability owner. The minimum `requirement_applicability` seam authorized by the full spec is therefore necessary and sufficient.

It may own only workspace/model-spec/model-version applicability identity and stale-protected lifecycle/audit state. Requirement payload remains in `requirements`; model/model-version truth remains in current modeling owners. Missing/ambiguous/stale required applicability blocks the mandatory criterion set rather than being inferred from prose or UI grouping.

### No solver/provider/network side effect belongs in reconciliation

112 is deterministic local state coordination. No provider call, solver run, filesystem side effect or network effect is authorized inside the canonical reconciliation transaction. If current evidence is insufficient, the state must be `recomputation_required` with exact domain and missing evidence contract; the operator is routed to the existing canonical domain owner.

This preserves all AI/provider/budget invariants and prevents a database transaction from spanning unbounded external work.

## Deterministic acceptance matrix

Implementation must prove at minimum the following classes, in addition to the complete full-spec mandatory cases.

### Schema and migration

1. existing data upgrades additively with no destructive rewrite;
2. historical Requirements become advisory/non-blocking unless explicit accepted evidence says otherwise;
3. required indexes/uniqueness constraints exist, including independent `UNIQUE(workspace_id, idempotency_key)`;
4. migration/bootstrap is idempotent and current schema checks remain green.

### Draft / approval / proposed-state impact

5. draft CAS rejects stale token/wrong workspace/unsupported operation;
6. preview uses exact parent + cumulative accepted ancestor state + current draft delta;
7. add/remove/change dependency/applicability deltas affect proposed-state impact correctly;
8. dangling/ambiguous/bound-exhausted graph/applicability evidence returns incomplete/rejected, never false no-impact;
9. `Approve all` creates one immutable working revision and does not mutate reconciled canonical truth;
10. approval retry is idempotent and conflicting reuse fails closed.

### Canonical owner mutation and rollback

11. Requirement/Assumption/ModelSpec/Decision owner mutations are workspace-scoped stale-protected and audited;
12. Parameter changes preserve 098 CAS/lifecycle/replacement/freshness authority;
13. proposal-origin Assumption/Decision/Parameter operations transition proposal state atomically with accepted canonical effect;
14. configured Parameter replacement uses the existing replacement/freshness semantics exactly once;
15. injected failure after any owner/proposal/replacement mutation rolls back every canonical success effect, snapshot, chain consumption and request success together.

### Validation / results

16. deterministic stored-output validation writes revision-bound immutable evidence;
17. insufficient output becomes truthful `recomputation_required` with exact domain/source contract;
18. scalar uniqueness remains `(run_id, output_name)` and is not duplicated per working revision;
19. criterion-only sibling reuse succeeds only with identical admissible basis;
20. changed-input sibling cannot reuse stale scalar evidence;
21. PASS -> replacement FAIL makes FAIL current; FAIL -> replacement PASS makes later PASS current;
22. concurrent replacement validation against one predecessor yields one successor and one stale-predecessor rejection;
23. broken/cyclic/cross-slot or multiple-current validation evidence blocks reconciliation;
24. request-bound selected-validation-set digest rejects any post-request replacement/drift.

### Reconciliation / snapshot / idempotency

25. same workspace/key/exact bound values returns the same committed outcome with zero replay;
26. same key with changed working revision/target/acknowledgement/request/validation digest conflicts before mutation;
27. concurrent first use of one workspace/key yields one persisted request identity;
28. success atomically commits canonical owners + proposal/replacement/freshness + snapshot + chain consumption + request outcome;
29. response loss after commit returns the same success without replay;
30. R1 snapshot remains exactly reconstructable after R2 changes current canonical rows;
31. deliberate branch from R1 after R2 uses R1 snapshot, never current R2 values;
32. corrupt/missing/digest-mismatched historical snapshot fails closed.

### Requirement gate/applicability

33. required PASS satisfies its gate;
34. required FAIL cannot silently pass and requires the accepted explicit known-FAIL acknowledgement path;
35. required not-evaluable blocks ordinary reconciliation;
36. advisory missing/FAIL does not alone block reconciliation;
37. workspace/model-spec/model-version applicability yields deterministic mandatory sets;
38. unrelated model versions do not inherit one another's model-specific required criteria;
39. applicability/gate drift invalidates prior preview/validation evidence.

### Security / regression / UI

40. no 112 route invokes provider/LLM execution;
41. rollback/validation logs and responses contain no secrets or unbounded opaque payloads;
42. existing 040/050/051/071b/098/111 behavior remains green;
43. existing Project Basis/Models UI is reused; frontend state never becomes canonical;

45. no 113/114/115/121+ functionality is activated by 112.
