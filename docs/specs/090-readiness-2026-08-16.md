## Minimum-necessary conclusion

Current master already has the execution, egress, continuation and proposal authorities that 090 must reference. The canonical server-owned entry point is `app.modules.ai.execution.run_ai_task`; external bindings continue through `egress_runtime.run_external_task`, 059b policy/budget/confirmation, and the 061 flow/attempt ledger. `AiTaskOutcome` already exposes the terminal attempt (`ledger_id`), canonical `flow_id`, response text, proposal ids/capture error and egress references. The existing public `/ai/tasks/run` wrapper is not the 090 persistence seam because its response omits `flow_id` and its workspace id is currently coupled to `include_project_context`.

One narrow execution seam is necessary for correctness: the thread interaction must own a durable canonical flow reference **before** dispatch begins. Otherwise a paid execution can finish and then lose its thread→flow link if the post-call thread write fails; a retry would have no safe way to distinguish “never dispatched” from “completed but not persisted” and could duplicate spend.

Readiness therefore authorizes a pre-created-flow seam, not a second execution path:

1. create the thread interaction and one unused canonical `ai_flows` row in the same SQLite transaction;
2. persist the interaction→flow reference before dispatch;
3. call the existing `run_ai_task` with that exact pre-created flow id;
4. require `run_ai_task`/external runtime to validate and consume only an unused, running flow whose workspace, task kind and requested route match the call;
5. persist the terminal assistant display snapshot after canonical execution;
6. if that final thread write fails, keep the interaction visibly incomplete but retain the canonical `flow_id`; never re-dispatch automatically.

This is smaller and safer than a second ledger, provider idempotency abstraction, transcript replay system, distributed rollback or provider-specific retry mechanism.

## Runtime authority inventory

### Canonical execution

The authoritative function is:

```python
app.modules.ai.execution.run_ai_task(...)
```

It owns local execution and delegates every network route to `app.modules.ai.egress_runtime.run_external_task(...)`. No 090 route may call a provider adapter directly.

`AiTaskOutcome` provides the minimum stable references required by 090:

- `flow_id`: canonical multi-attempt/continuation identity;
- `ledger_id`: terminal/current canonical attempt identity returned by the execution spine;
- `status` and `error_type`;
- `response.text` when an assistant result is available;
- `proposed_record_ids` and `records_parse_error` after canonical record capture;
- egress decision/ticket/reservation references for the current execution response.

090 stores `flow_id` as its durable provenance reference. Attempt ordering, provider identity, cost, latency, token usage, fallback and continuation remain canonical in `ai_flows`/`ai_jobs` and are read from that authority rather than copied into thread tables.

### Canonical flow lifecycle

`token_flow_service.FlowState` is authoritative and currently consists of:

- `running`;
- `confirmation_required`;
- `complete`;
- `partial_terminal`;
- `failed_terminal`;
- `cancelled_terminal`.

One interaction may therefore map to multiple attempts. 090 must never infer “one message = one provider call”. Read models expose canonical flow state and terminal reason as bounded provenance facts.

### Canonical proposal capture

`flow_record_capture.capture_final_flow_records_in_transaction` already binds a complete flow, terminal attempt, final output digest and proposal ids atomically and idempotently. 090 must read proposal ids from `ai_flow_record_captures` when present. It does not own proposal creation semantics, bodies, promotion or rejection.

### Additive SQLite discipline

Current database initialization uses separate schema statement/index/migration groups, idempotent additive setup, foreign keys, WAL and a busy timeout. 090 may add one independently removable schema group and register it in `database.py`; it must not alter existing token-flow, MemoryStore, egress or engineering tables.

## Frozen storage contract

Add one 090-owned schema module with exactly two tables.

### `ai_threads`

Required fields:

- `id TEXT PRIMARY KEY` — server-owned UUID;
- `workspace_id TEXT NOT NULL` → `workspaces(id)`;
- `title TEXT` — optional local label, maximum 120 Unicode code points after service validation;
- `created_at TEXT NOT NULL`;
- `last_activity_at TEXT NOT NULL`.

No archive/delete mutation is required in 090. Threads cannot move between workspaces.

Deterministic list order is `last_activity_at DESC, id ASC`.

### `ai_thread_interactions`

Required fields:

- `id TEXT PRIMARY KEY` — server-owned UUID;
- `thread_id TEXT NOT NULL` → `ai_threads(id)`;
- `request_id TEXT NOT NULL` — caller idempotency token, bounded by the existing safe-id grammar or an equivalently strict 128-character grammar;
- `request_digest TEXT NOT NULL` — canonical digest of immutable submit semantics;
- `interaction_index INTEGER NOT NULL CHECK (interaction_index >= 0)`;
- `user_text TEXT NOT NULL`;
- `assistant_text TEXT` — local advisory display snapshot only;
- `assistant_text_truncated INTEGER NOT NULL DEFAULT 0 CHECK (... IN (0,1))`;
- `flow_id TEXT NOT NULL` → `ai_flows(id)`;
- `persistence_state TEXT NOT NULL` with only `reserved`, `dispatching`, `captured`, `capture_failed`;
- `persistence_error TEXT` — bounded local diagnostic, never provider packet/body/credential data;
- `created_at TEXT NOT NULL`;
- `updated_at TEXT NOT NULL`.

Required uniqueness:

- `UNIQUE(thread_id, request_id)`;
- `UNIQUE(thread_id, interaction_index)`;
- `UNIQUE(flow_id)`.

Do not duplicate terminal attempt id, provider id, cost, latency, usage, fallback, continuation lineage, proposal bodies, egress packets, context blocks or engineering records into 090 tables. These remain joins/references to canonical authority.

Deleting or rolling back 090 tables must not delete canonical flow/job/proposal/evidence rows. Do not use cascading deletes from thread storage into those authorities.

## Frozen bounds

Server and client must enforce:

- thread title: 120 code points;
- user input: 12,000 code points;
- stored assistant display snapshot: 131,072 code points maximum; longer output is stored as an explicitly truncated snapshot with `assistant_text_truncated=true` while the canonical flow/digest remains authoritative;
- persistence diagnostic: 500 code points maximum;
- thread list: default 25, hard maximum 50;
- interaction read: latest 50 by default, hard maximum 100, returned in ascending `interaction_index` order with an explicit `has_older`/truncated indicator;
- proposal references rendered from canonical capture: maximum 50 ids plus total/truncated metadata.

No bound may silently coerce malformed IDs, statuses or cross-workspace access into success.

## Frozen create/read API

Add a router beneath the existing `/ai` router; do not add a second top-level API authority.

Minimum endpoints:

- `POST /ai/threads` — create a local thread for one existing workspace; no AI execution;
- `GET /ai/threads?workspace_id=...&limit=...` — bounded deterministic list;
- `GET /ai/threads/{thread_id}?workspace_id=...&interaction_limit=...` — bounded thread plus interaction/provenance read;
- `POST /ai/threads/{thread_id}/interactions` — submit exactly one user turn.

Every thread read/write receives or resolves the expected workspace and fails closed on mismatch/not-found. Never return another workspace’s thread as a generic successful empty result.

The submit body is deliberately small:

- `request_id`;
- `prompt`;
- optional `task_kind` using the canonical task-kind grammar;
- optional `route_class` using the canonical route grammar;
- optional positive `max_tokens`.

090 does **not** accept arbitrary `context_blocks`, full-thread history, provider messages or an `include_project_context` convenience flag. Each turn sends only that turn’s bounded prompt through the existing canonical execution spine. Project/thread-derived context can be added only by a later separately bounded authority; 090 must not silently concatenate history.

The 090 inspection UI uses the default local route and does not expose a paid-provider selector. Direct API callers may request an existing canonical route, but 059b/provider/budget policy remains authoritative and can reject or require confirmation.

## Pre-created canonical flow seam

Add the smallest internal seam needed to make interaction→flow identity durable before dispatch.

### Token-flow helper

Add `create_flow_in_transaction(connection, *, task_kind, requested_route_class=None, workspace_id=None)` to `token_flow_service.py`; refactor existing `create_flow` to call it inside its current transaction. The helper must preserve exactly the same validation, continuation-snapshot and schema semantics as current `create_flow`.

### Execution consumption

Add an **internal-only** optional `existing_flow_id` argument to `run_ai_task` and the external runtime seam it calls. Do not add this field to `AITaskRunRequest` or `/ai/tasks/run`.

Before any adapter invocation or egress packet construction, the seam must fail closed unless the referenced flow:

- exists;
- is `running`;
- has the exact workspace id expected by the thread;
- has the exact task kind;
- has the same normalized requested route semantics;
- has `attempt_count == 0` and no linked `ai_jobs` rows;
- has no terminal metadata;
- has not already been consumed by another 090 interaction (enforced by `UNIQUE(flow_id)` in thread storage).

When `existing_flow_id` is omitted, every existing call path must behave byte/semantically as before and continue creating its own flow.

No provider adapter, budget formula, egress decision, reservation reconciliation, continuation algorithm, proposal capture or accounting rule may change.

## Submit/idempotency state machine

Before canonical execution:

1. validate workspace/thread/request bounds;
2. canonicalize the immutable submit tuple `{prompt, task_kind, route_class, max_tokens}` and compute `request_digest`;
3. in one `BEGIN IMMEDIATE` transaction, create the pre-owned canonical flow and interaction row with `persistence_state='reserved'`, the next deterministic `interaction_index`, and unique `(thread_id, request_id)`;
4. commit the durable interaction→flow identity;
5. atomically change that interaction from `reserved` to `dispatching` before calling `run_ai_task(existing_flow_id=...)`.

Duplicate handling is exact:

- same `(thread_id, request_id)` + same digest returns/re-reads the existing interaction and **never starts another execution**;
- same `(thread_id, request_id)` + different digest returns `409`;
- an interaction already `dispatching`, `captured` or `capture_failed` is never auto-dispatched again;
- if the process dies after marking `dispatching` but before canonical execution creates an attempt, later reads expose an interrupted/ambiguous dispatch state; 090 does not guess that retry is safe and does not auto-pay again. A new explicit user turn requires a new request id.

This fail-closed rule is intentionally conservative. Provider-specific idempotency and restart-safe redispatch are outside 090.

## Completion and partial-persistence recovery

After `run_ai_task` returns, update only the 090 interaction snapshot/state and `ai_threads.last_activity_at`.

- If an assistant response exists, store it as inert local text subject to the explicit snapshot bound/truncation flag.
- If no response exists, keep `assistant_text=NULL` and render canonical flow status/reason.
- `flow_id` is already durable and never changes.
- Proposal references are read from canonical `ai_flow_record_captures`; no post-call proposal-id copy is required.

If the final thread update fails after canonical execution completed, do **not** roll back or delete the real flow/attempt/egress/proposal evidence and do **not** re-dispatch. The interaction remains `dispatching` or is best-effort marked `capture_failed`; a subsequent thread read joins the canonical flow and must explicitly render, for example, “Canonical execution completed; assistant display snapshot was not durably captured.” This is not success text and is not silent data loss.

A terminal assistant answer may be presented as a durable thread snapshot only when `assistant_text` is actually stored. Canonical flow state may still be shown independently.

## Canonical status/provenance read

Thread read joins `ai_thread_interactions.flow_id` to canonical `ai_flows` and its ordered attempts. Expose only bounded provenance facts required before 091:

- flow id;
- canonical flow state and terminal reason;
- attempt count;
- terminal/current attempt id when canonical;
- proposal ids/count from `ai_flow_record_captures`;
- local `persistence_state` and whether assistant snapshot is truncated.

Do not surface provider credentials, raw route metadata JSON, context bodies, prompt derivatives, egress packets, protected segment bodies, filesystem paths or secret/sanitizer internals. Provider/cost/latency/token-detail presentation belongs to their existing canonical surfaces and later 091 composition.

Unknown persistence/canonical states fail parsing or render bounded raw canonical status; never coerce to `complete`.

## Confirmation, failure and continuation behavior

The thread read model preserves canonical flow semantics rather than inventing chat statuses:

- `running` → execution in progress/unknown interruption;
- `confirmation_required` → explicit confirmation-required state, with no automatic confirmation/resume action added by 090;
- `complete` → completed canonical flow; assistant snapshot may or may not have been captured;
- `partial_terminal` → bounded partial result state; stored assistant snapshot may be shown only if actually returned/captured and must be labelled partial;
- `failed_terminal` → failed canonical execution;
- `cancelled_terminal` → cancelled canonical execution.

Continuation attempts remain represented by the one canonical flow. 090 never runs its own continuation loop and never equates a flow with one attempt.

## Egress/privacy contract

Raw complete-thread egress is prohibited deterministically.

The submit service may pass only the current bounded `prompt` and the explicit request fields above to `run_ai_task`. It must never derive `context_blocks` from thread history and must not serialize prior interactions into any provider request.

Thread tables may contain only the user’s local turn text and bounded assistant display snapshot. They must not persist:

- provider request/response packet JSON;
- credentials/tokens/secrets;
- sanitizer derivatives or raw context blocks;
- protected continuation segment bodies copied from 061;
- filesystem paths hidden by existing APIs;
- cost/usage/provider accounting copies.

Untrusted thread text is always inert plain text.

## Frontend stale-response and submit guards

Use one small pure state helper + deterministic harness. Freeze generation/identity contexts for:

- workspace A→B and A→B→A list reads;
- thread X→Y and X→Y→X detail reads;
- submit on X followed by selection of Y;
- create-thread followed by workspace change;
- late submit completion after workspace/thread changed;
- selected thread disappearing or becoming unreadable;
- duplicate click with the same in-flight request id.

Changing workspace synchronously invalidates list/detail/submit generations and clears old thread content/errors. Changing selected thread invalidates detail/submit ownership before the new read starts. Late completion may trigger a fresh canonical read only when captured generation + workspace + thread identities still match.

The client generates one request id per explicit submit action and disables submit while that interaction request is in flight. It must not generate a new request id for an automatic retry because there is no automatic retry.

The narrow pre-created-flow seam is therefore required specifically to prevent orphaned successful/paid execution and ambiguous retry.
