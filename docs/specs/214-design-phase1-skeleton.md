# 214 — Design Phase 1: project, Plant, components and Workshop

Accepted outcome and readiness: maintainer [issue #901](https://github.com/AlbertoRacerro/JarvisOS_v1/issues/901), including its 2026-10-23 scheduling update, after specs 212 and 213 merged. The issue fixes the product direction; this contract fixes the bounded Phase 1 outcome and evidence. Phase 2 CFD and later physics remain separate. Live state is only in `STATUS.md`.

## Outcome

An engineer opens one project and active version in Design, starts at the Plant flowsheet, opens a PFD unit's nested component model tree, navigates by stage or tree, finds published custom models in a Library, and creates a custom model through a guided Workshop. Existing BlueCad geometry, Process, Dynamic Studio and Studio actions remain usable from this shell. The documented C1 horizontal and fence cases can be opened and run there with the same inputs and numerical results as the current surfaces. The current Design stays reachable through an explicit switch until replacement coverage is proven.

## Contract

1. **Project and version.** The existing workspace is the project identity. A backend-owned active project version is visible beside Design navigation and applies to Plant and components together. Switching project/version must change the data context actually read and edited; a version label cannot merely decorate unrelated current drafts. Existing data receives a truthful, non-destructive initial-version association. New versions have stable identity and an explicit parent or source; mutable work is revisioned or guarded against stale writes. Historical data and pinned published Studio/CAD/Process references retain their identity and provenance. Avoid copying large artifact blobs merely to make a version.
2. **Plant and components.** Plant owns the existing Process PFD and steady/dynamic entry points. A unit can be opened by double-click or keyboard into a component. Components have stable project/version-scoped identity, optional parent, and arbitrary-depth containment with cycle rejection. A component, including an assembly, has a model tree with Parameters, Geometry, Materials, Physics, Mesh, Studies, Results and Reduced model nodes. Nodes with no capability yet say so plainly; they cannot imply a mesh, CFD result or validated physics exists. A parent assembly may represent one fluid domain in the model, but Phase 1 does not generate that domain.
3. **Navigation.** The top bar shows project/version, Plant and CAD → Motion/Mechanics → CFD → Optics → Reduced model. Inside a component, stages focus the corresponding tree area and permit free jumps. Motion/Mechanics is a labelled placeholder. The central view and inspector use the selected existing artifact/owner where available. The old Design and new shell share the same backend records rather than diverging copies.
4. **Fidelity and handoff.** A new Process unit starts with its available 0D/1D model and an honest fidelity label. A visible Deepen action creates or opens its component and passes typed Process design parameters into supported parametric BlueCad geometry. Unsupported unit/geometry mappings explain the limit. The existing published Studio version pinning and Process/BlueCad handoff remain authoritative. Publishing a reduced model into Process, obsolescence detection, and CFD-derived correlations belong to Phase 2 unless an existing owner already supports the specific action; Phase 1 must not claim a live coupling.
5. **Library and Workshop.** Studio stops being a peer destination in the new shell. Its published models appear in a project Library, and Generate new opens a focused Workshop. Guided initialisation asks one question at a time about purpose, approach, typed inputs/outputs, assumptions and test intent; answers visibly build an editable contract, explanation and Python source. AI drafting, when invoked, uses `run_ai_task`/`ai_jobs`, the existing provider and budget controls, and proposal-only output; ordinary use must work with safe fake/offline defaults. Closing initialisation opens two full, synchronised columns: derived explanation with rendered equations and validity/units on the left, editable Python with suitable syntax/theme on the right. Selecting an equation or source span highlights the corresponding span where derivation has a reliable mapping; unsupported constructs remain explicitly unlinked and visible. Python remains authoritative, and saving/testing/publishing uses existing Studio Draft → Test → Publish boundaries. Custom correlations/physics/geometry attach to a component node when compatible; custom units and procedures attach to Plant where supported. No new execution path bypasses Studio's sandbox.
6. **One operation, shared history.** Operations exposed by this Phase 1 shell call the same typed backend owners as the existing GUI and authorized agent tools. A model change is an editable, attributable revision/event in its owning history, with provenance and conflict behavior. No separate agent-only geometry or model mutation channel is introduced. This does not require implementing every future sketch, mesh or study command in Phase 1.

## Acceptance and evidence

1. Backend tests prove project/version isolation and switching, legacy association without loss, stable nested component identities, cycle refusal, stale-write behavior, and reuse of typed Process/BlueCad/Studio owners. Existing clients remain compatible.
2. A real-browser walk in Lumen Light and Dark shows project/version context shared across Plant and a component; PFD unit double-click/keyboard entry; stage and model-tree jumps; Library → guided Workshop → full two-column editor → existing test/publish path; and the explicit old/new Design switch. Capture screenshots and console errors. A placeholder is marked as such.
3. Rebuild both spec 212 C1 layouts in the new shell using the same recorded setup or pinned input records. Execute the same available geometry/optics/Process capability through existing owners. Compare input digests, model versions, units, run artifacts and numeric outputs with a stated tolerance (exact where deterministic). Report missing source evidence and the qualified scientific conclusion unchanged; do not label a proxy run a 2013 replication.
4. Relevant offline backend tests, Ruff, frontend build/tests, and exact-head semantic review cover the changed owners. Verify browser behavior in Chromium. Add only tests that exercise the actual new contract and regressions.

## Boundaries

- No OpenFOAM installation or execution, CFD/mesh pipeline, FSI, full Motion/Mechanics implementation, new optics fidelity, C2–C9 science, reduced-model publication mechanism or obsolescence claim. Those require later accepted slices.
- No forced stage sequence. P&ID remains distinct from the existing PFD. No second database, new general workflow engine, or hardcoded screenshot/mock C1 result.
- Preserve current user data, existing API consumers, Project/Studio/Process/BlueCad authority, version pins, paths and AI safety defaults. Runtime data stays outside the repository.
- Phase 1 may be delivered through several coherent implementation PRs under this single contract. Every PR keeps `STATUS.md` and its implementation association truthful; final acceptance requires the integrated browser and C1 evidence.
