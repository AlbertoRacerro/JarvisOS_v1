## Minimum-necessary conclusion

The existing MemoryStore already owns proposal listing and every lifecycle transition needed by the first Review workbench. No new store, schema migration, route, lifecycle, AI call, dependency or global UI system is needed.

One small backend read expansion is necessary. Current `MemoryRecordRead` omits persisted proposal facts required to decide safely. Without those fields, the operator could accept a Parameter without seeing its value/unit/range or a Decision without its rationale. The implementation may therefore extend only the existing read model and union projection with already-persisted columns.

## Frozen backend read contract

Add the following nullable/read-only fields to `MemoryRecordRead` and the matching `_select_record_sql()` union projection:

- `scope: str | None`;
- `confidence: str | float | None`;
- `symbol: str | None`;
- `value: str | None`;
- `unit: str | None`;
- `value_status: str | None`;
- `value_min: float | None`;
- `value_max: float | None`;
- `rationale: str | None`;
- `linked_run_id: str | None`.

Projection rules are exact:

- Assumption fills `scope`, textual `confidence`; Parameter/Decision-only fields are null.
- Parameter fills `symbol`, `value`, `unit`, `value_status`, `value_min`, `value_max`, numeric `confidence`; Assumption/Decision-only fields are null.
- Decision fills `rationale`, `linked_run_id`; Assumption/Parameter-only fields are null.

Existing fields (`title`, `statement`, `decision_text`, `name`, `source_ref`, `notes`, `supersedes_parameter_id`, lifecycle/provenance/timestamps) remain unchanged.

No schema, table, migration, join, endpoint or event changes are authorized. Extend `backend/tests/test_memory_store.py` with one focused API/read-model test proving these fields round-trip from existing columns for all three record kinds.

## Frozen frontend client

Add `frontend/src/api/memory.ts` containing only typed wrappers for existing authority:

- `listMemoryProposals(workspaceId, status?)`;
- `promoteMemoryRecord(kind, id)`;
- `rejectMemoryRecord(kind, id)`;
- `promoteParameterReplacement(id)`.

Use `API_BASE_URL`, URL-encode user/record identifiers, reject non-2xx responses, and preserve a bounded human-readable backend error message when available. No retry loop, polling, cache, provider call or filesystem access.

The list response is the full selected-proposal read source after the additive expansion. Do not add a proposal-detail endpoint or N+1 detail fetch.

## Local state and stale-response rules

Use one small pure `reviewState.ts` plus deterministic harness. Freeze these responsibilities only:

- deterministic ordering: `created_at` descending, then `record_kind`, then `id`;
- stable display label fallback;
- request context `{generation, workspaceId, statusFilter}`;
- mutation context `{generation, workspaceId, recordKind, recordId}`;
- accept a completion only when both generation and all captured identities still match;
- deterministic selection retention/fallback after a refreshed list;
- next-after-removal focus target: item at the removed index, otherwise previous final item, otherwise list/filter heading.

Changing workspace or status filter synchronously increments request/mutation generations, clears prior visible proposals/selection/errors/transition notice and starts a fresh list read. This covers A→B→A even when identity returns to A.

Selection itself is local over the accepted list, so there is no separate X→Y detail request. X→Y→X stale protection applies to mutation completions and list refreshes, not to an invented detail endpoint.

## Workspace ownership

## Transition behavior

Only exact status `proposed` exposes enabled Accept/Reject controls.

Accept routing:

- Assumption → generic promote endpoint.
- Decision → generic promote endpoint.
- Parameter with no `supersedes_parameter_id` → generic promote endpoint.
- Parameter with `supersedes_parameter_id` → **only** `promote-replacement`.

Reject always uses the existing generic reject endpoint, including configured replacements.

One mutation at a time within Review. While in flight, both transition controls for the selected proposal are disabled and the primary article exposes busy state.

No optimistic terminal mutation. On success:

1. preserve a bounded transient transition notice from the real response;
2. reload the active list canonically;
3. reconcile selection from the accepted refreshed list;
4. only then present final list/selection state.

For replacement acceptance the transient notice includes only returned facts: accepted replacement id, superseded parameter id, freshness invalidation affected count and source/replacement refs.

On mutation error, keep/restore the current canonical proposal visible when still present, show the error, then permit explicit Refresh. Do not translate conflict/error into success.

If workspace/filter/selection context changes while mutation is in flight, the late completion must not repaint that context. Because the backend mutation may have committed, the next accepted read remains canonical truth.
