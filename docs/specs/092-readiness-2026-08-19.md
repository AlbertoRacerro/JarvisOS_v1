# 092 — SCENE-BINDING-0 readiness

Date: 2026-08-19  
Definition authority: `docs/specs/092-scene-binding-0-rederived.md`  
Exact inspected master: `ed944a79a47a5da3dae7e0ca72fa900fc4ed9390`

## Decision

**READY after this record merges and the registry is reconciled.**

The current runtime does not yet contain a trustworthy scene-hit → semantic BLUECAD part binding. The viewer deliberately exposes ephemeral `mesh-N` inspection keys generated from GLTF traversal order, while the canonical GeometrySpec already owns stable non-empty `part_id` values and the geometry manifest is keyed by those part IDs. The current exporter combines built part shapes into one build123d compound and exports one GLB without an explicit semantic scene-binding contract.

Therefore 092 requires one bounded additive CAD-export seam: exported selectable GLTF objects must carry a deterministic semantic BLUECAD part key derived from canonical `part_id`, and the generated manifest must record the binding contract/version needed to validate that key against the exact artifact/spec. The frontend may then resolve a hit by that semantic key. Mesh ordinal, traversal order, material, color, bounds and display labels remain inspection data only and may never be fallback identity.

This is the minimum sufficient seam. It adds no engineering database, no new durable store, no provider path, no general scene graph service and no object-recognition heuristic.

## Exact runtime evidence

### Viewer and current selection

`frontend/src/components/BluecadGlbViewer.tsx` currently:

- traverses loaded GLTF meshes and assigns `meshKey: mesh-${ordinal}`;
- uses mesh names only as `displayName`;
- raycasts visible meshes and returns the generated mesh key;
- already has a generation/session guard that prevents an old GLB load from publishing into a newer viewer generation;
- clears inspection state on artifact replacement/unmount.

`frontend/src/app/selection.ts` already distinguishes a `geometry-hit` selection from a record selection, but its geometry identity is explicitly ephemeral (`viewerSessionId`, `ephemeralObjectId`). It is not sufficient semantic authority.

`frontend/src/components/bluecad/BluecadWorkbench.tsx` already owns candidate/workspace request generations and clears its inspection snapshot when candidate or GLB artifact changes. It currently publishes the candidate record as the app-level selection; geometry inspection remains local presentation state.

### Existing semantic CAD authority

`schemas/bluecad_geometry_spec_v0_1.schema.json` requires every part to have a non-empty `part_id`. Connections also reference part/port identities rather than export order.

`backend/app/modules/bluecad/models.py` preserves `BuiltPart.part_id` through placement and emits manifest entries keyed by part ID.

`backend/app/modules/bluecad/export.py` currently:

- receives `parts: dict[str, BuiltPart]` keyed by canonical part ID;
- exports a single shape/compound to `model.glb`;
- emits `manifest.parts` and `manifest.resolved_ports` keyed by stable part ID;
- does **not** emit a scene-binding map/version and does not establish that GLTF mesh/node names are stable semantic IDs.

This proves both sides required by the definition: stable semantic keys already exist, but the rendered artifact currently lacks an authoritative bridge to them.

### 071b ownership

`frontend/src/components/engineering/EngineeringProperties.tsx` is the sole transient working-configuration owner. 092 must not move or duplicate its bindings, baseline, revision, preflight, undo/revert or run behavior. Scene selection supplies semantic target context only. Any editing still uses 071b validation and revision safety.

## Mapping strategy

### Chosen strategy — exporter-owned semantic part key

For each selectable BLUECAD part in a newly generated GLB:

1. the exporter assigns a deterministic GLTF-visible semantic key derived exactly from canonical `part_id` before export;
2. the manifest declares a versioned scene-binding section that binds that semantic key to `part_id` and the exact generated GLB/spec identity;
3. backend artifact/candidate reads continue to own candidate/artifact/spec identity; no frontend persistence is added;
4. the viewer reads the semantic key from loaded GLTF object metadata/name only after validating it against the authoritative manifest binding for the current candidate/artifact;
5. a raycast hit returns a semantic part target only when exactly one valid current binding exists;
6. missing, malformed, duplicate, unknown or conflicting keys produce `unresolved`/`ambiguous`, never an ordinal/name/bounds heuristic.

The implementation may use a namespaced deterministic GLTF node/object name such as an encoded `part_id` **only if an exact pinned-kernel test proves build123d/OCCT GLTF export preserves it bijectively**. If the exporter cannot preserve a per-part semantic name reliably, implementation must stop and return to readiness rather than substitute mesh order. A separate sidecar map keyed by mesh ordinal is explicitly forbidden because reorder would invalidate identity.

### Rejected alternatives

- `mesh-N` / traversal index: rejected because current viewer creates it from load order.
- raw `mesh.name` without exporter contract: rejected because current runtime treats it as display text and uniqueness/stability is unproven.
- bbox/nearest-part matching: rejected because similar/overlapping geometry can alias and floating-point/export changes can reorder results.
- material/color: rejected as presentation state.
- `part_id` inferred from candidate brief or AI: rejected because model text is not identity authority.
- new scene-object database/table: rejected as unnecessary duplicate authority; canonical GeometrySpec + manifest are sufficient.

## Binding contract

The implementation may add a backward-compatible optional manifest member with semantics equivalent to:

```json
{
  "scene_binding": {
    "version": "bluecad_scene_binding_v0_1",
    "artifact": "model.glb",
    "objects": {
      "<semantic_glb_key>": {"part_id": "<canonical part_id>"}
    }
  }
}
```

Exact field spelling may be adjusted during implementation only if required by existing manifest conventions; semantics may not broaden. The section must participate in the existing manifest digest because it is part of artifact evidence. No migration rewrites historical manifests.

Validation requirements:

- semantic keys and part IDs are bounded strings and rendered inertly;
- every declared part target must exist in `manifest.parts`;
- duplicate semantic keys or one semantic key mapping to multiple parts fail closed;
- a GLTF semantic key absent from the current manifest is unresolved;
- a manifest key absent from the loaded GLTF is not fabricated into a visible selection;
- current candidate/workspace/artifact identity is part of the frontend resolution context;
- historical manifests without `scene_binding` remain viewable and geometry inspection remains available, but semantic Properties state is `Unresolved engineering binding`.

No endpoint is required solely for resolution if the existing candidate aggregate/artifact JSON reads can provide the exact current manifest. A new route is not authorized unless implementation proves those existing reads cannot safely provide the binding metadata.

## UI and state composition

### Selection states

The BLUECAD stage may publish a semantic geometry selection with enough ephemeral context to reject stale responses, but it must not persist it. The normal Properties header states are:

- no hit: candidate/no-selection context;
- resolving: current candidate/artifact + pending semantic target resolution;
- resolved: human `part_id` (or an existing authoritative human label if one is later proven) and part `kind` primary; candidate relationship secondary;
- unresolved: no authoritative binding for this visible hit;
- ambiguous: more than one authoritative target; no automatic choice;
- stale/removed: semantic target cleared before editing can continue.

Machine details (`viewerSessionId`, mesh inspection key, raw GLTF name, artifact UUID) remain Inspect/Audit disclosures.

### Stale safety

Use existing generation/session patterns rather than a new state framework.

A semantic result is accepted only if all captured preconditions still match current state: workspace, candidate, GLB artifact, viewer session/generation and current hit. Candidate/workspace/artifact switch clears semantic target synchronously before any later response can update Properties. Viewer unmount/error clears it. A late response is ignored.

Compact `Jarvis | Properties` pane switching from 096 must not clear or recreate a valid semantic selection because pane visibility is presentation state, not scene authority.

### Properties and Jarvis

092 may add semantic selected-target/header context to `EngineeringPropertiesPanel`, but may not create object-specific model/property semantics that belong to 058c. Existing 071b working state remains unchanged unless the operator edits through its existing contract.

Jarvis may receive only a compact human context reference for the resolved target. Selection itself triggers no AI task/provider call and no canonical/working/run mutation.

## Deterministic tests required

1. Export fixture with at least two visually similar parts having distinct `part_id`s; generated binding is bijective and manifest targets exist.
2. Reorder input/assembly/export traversal without changing part IDs; semantic GLTF keys still map to the same part IDs.
3. Pinned real-kernel GLB proof parses the generated GLB and proves the semantic key survives export for every selectable part. A manifest-only assertion is insufficient.
4. Duplicate/malformed/unknown semantic key is rejected/fails unresolved; no ordinal fallback.
5. Historical manifest without `scene_binding` remains viewable and resolves semantic selection as unavailable rather than failing candidate load.
6. Manifest binding changes alter existing manifest digest evidence.
7. Frontend pure/state tests or checker fixtures prove stale old session/candidate responses cannot replace newer semantic selection.
8. Selection/clear performs no working-configuration mutation, run creation or provider dispatch.

If test 3 cannot be made green with the bounded exporter seam, 092 implementation is not ready to merge and must return to a readiness decision; do not weaken identity semantics.

## Failure/race handling

- Candidate/artifact changes during GLB load: old loader generation is disposed/ignored; semantic target cleared.
- Binding metadata fetch fails: keep GLB inspection usable; semantic binding becomes unavailable/unresolved; no guessed fallback.
- GLB loads but declared semantic key is absent: unresolved.
- More than one rendered object claims the same semantic key or metadata maps one key to multiple parts: ambiguous/fail closed.
- Part removed from current manifest/spec: clear target; never retain editable stale target.
- Properties preflight already in flight when selection changes: 092 does not reinterpret or promote that result; 071b revision/model guards remain authoritative.
- Workspace change: clear candidate and semantic selection before accepting later responses from the old workspace.

## Backward compatibility and rollback

Historical candidates require no rewrite. Existing GLB orbit/pan/zoom and geometry inspection continue to work. Semantic binding is additive for newly generated artifacts; absence means unresolved.

Rollback removes semantic export metadata and frontend semantic resolution while preserving existing candidate viewing, ordinal inspection, all canonical GeometrySpecs/manifests already stored, 071b working state and run history. Newer manifests containing the optional binding section remain ordinary JSON artifacts even if an older frontend ignores that field.

## Minimum-necessary test

Criterio di accettazione della spec: stable authoritative scene hit → engineering part identity.  
Questo lavoro serve a soddisfarlo? **sì** — current GLB hit identity is traversal-order `mesh-N`, while stable `part_id` exists only outside the rendered artifact.  
Il criterio è raggiungibile senza di esso? **no** — not without guessing from display name/order/bounds or adding a larger duplicate scene-object authority.  
Why this seam: exporter-owned semantic key + manifest binding reuses the existing canonical part identity and existing artifact evidence with the smallest additive contract.
