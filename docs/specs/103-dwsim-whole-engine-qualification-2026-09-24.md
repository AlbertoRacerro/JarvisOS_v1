# DWSIM whole-engine qualification — 2026-09-24

Status: candidate architecture with bounded runtime qualification, not scientific qualification. This extends the 103 bakeoff after the maintainer clarified that internal commercial use, without software distribution, is the present deployment assumption. It does not supersede accepted 103/104 implementation evidence or authorize a 107 ownership change by itself.

## Decision under test

Evaluate a **complete pinned DWSIM engine** as the owner of generic process streams, thermodynamics, units, flowsheet topology, recycle, steady and dynamic solving, holdup, control and native case files. JarvisOS would retain canonical project/design state, policy, evidence, scientific qualification, studies, AI and promotion. A replaceable adapter would map exact case and solver identity, units, species, settings, object IDs, errors, convergence histories and balance residuals. No DWSIM object or session ID would become canonical Jarvis state.

The previous 103 [bakeoff](103-process-upstream-bakeoff-evidence.md) deferred DWSIM because the runtime was unavailable. That was an environmental limit, not a technical rejection. The [current upstream](https://github.com/DanWBR/dwsim10) is DWSIM 10; the old repository is archived. The [10.2.9 release](https://github.com/DanWBR/dwsim10/releases/tag/v10.2.9), published 2026-09-20, identifies source commit `d113563` and publishes checksums for self-contained Windows and Linux desktop packages and a Linux headless MCP package. This removes the assumption that a separately installed .NET SDK is required to run a distribution; the downloaded packages were extracted for qualification without system installation.

The initial assessment was source inspection. The WSL2 execution addendum below now establishes one headless → Windows desktop edit/save → WSL2 headless round trip, not scientific qualification or a Windows-native solver run. Upstream's own test report includes five intentionally failing sample flowsheets; that limits any general reliability claim. A Windows-native solve, exact BlueRev case, scientific reference comparisons, and qualified domain-specific custom unit remain separate gates. A successful round trip establishes interoperability, not physical validation.

## WSL2 execution addendum — pinned 10.2.9

The official Linux x64 headless MCP `.deb` (SHA-256 `75b5aad47a3806a833e5a2c19a074f108e29b35729419d9ab993b8f993a339db`) and desktop `.tar.gz` (SHA-256 `fc899a4890ea0fea276c94e46965585290431f31af5aff12b148c43cb7ea659c`) were downloaded from the release and checked against GitHub's asset digests. The `.deb` was extracted under `/tmp`, not installed as a system service. Its self-contained `dwsim-mcp` started over stdio on WSL2 without a separate .NET runtime and registered 53 tools. The native type list includes 44 unit types, including Mixer, Splitter, Recycle, Tank, Pump, Valve, HeatExchanger, reactors and BioReactor. The property-package list includes Steam Tables, Seawater IAPWS-08, CoolProp families, PR/SRK, NRTL, UNIQUAC, UNIFAC and CAPE-OPEN. These lists prove exposed names, not successful use of every unit/package.

Four packaged sample cases were loaded into the headless engine and solved with zero reported solver errors: water/ethanol flash (`db55c1144f486ee4ef9fe3df5fe63de3f3b04c7aa5db46fa9d9eade27538f0e2`), water recycle (`48fdbdd83e05576084f1068f5de38c789ee4965f90994413fee303559eea978c`), tank/valves/PID (`be65838fa3339ac541cb4b9bc894d6d9b08b031d764f0f61e16b75cbf9e625c4`) and a custom hydrocyclone unit (`a22854bbe6ab3a3f113d431f8a34fef55d266de1c877e2dc62919f9ea500a911`). The recycle case had six streams and four units, all marked calculated. The dynamic tank case had four streams and five units; its stored `Sch1`/`Int1` schedule and `NewState1` loaded, and a 30 s requested run returned seven recorded samples at 0, 5, ..., 30 s with level 0.0100296 to 0.310918 m. This is execution of upstream examples, not an independent physical benchmark or BlueRev case.

A headlessly built water Mixer connected two feeds and one product. An initial `dwsim_stream_add_material` call requesting 2 kg/s for the second feed returned success but readback showed 1 kg/s; `dwsim_stream_set_conditions` corrected it. The solved product was then 3 kg/s from 1 + 2 kg/s feeds, and save → close → load → solve reproduced 3 kg/s. The adapter must read back inputs and check conservation; an MCP success envelope alone is insufficient. In an intentionally incomplete case, `dwsim_solve_run` returned `ok: true` while its `findings` contained `NO_PROPERTY_PACKAGE` and `NOT_CONVERGED` blockers and objects were uncalculated. Read `findings`, `blockers`, per-object calculation state and balances before reporting convergence. After reload, `dwsim_flowsheet_summary` returned `property_packages: [null]` although the saved XML contained `Steam Tables (IAPWS-IF97)` and the case solved; native identity must be recovered and checked from another field or file. For the tank run, the run/status envelope reported 30 s and six steps, while the nested summary reported 35 s and seven steps; the time-series itself ended at 30 s. Do not promote nested summary timing without reconciliation.

Still unproven: native Windows solver execution; actual CAPE-OPEN component compatibility; BlueRev custom unit and saline mixture/flash; solver iteration/residual metadata; valid pressure-flow dynamic initialization; comparative accuracy, uncertainty and scientific qualification. The packaged tank case's dynamic check returned `ready: true` with warnings for an unsolved level gauge and a valve opening/Kv characteristic, so its transient is a capability smoke only. The MCP package's default service configuration binds `0.0.0.0` without authentication; a Jarvis adapter must use local-only binding and an explicit token or stdio custody.

### Native desktop and Python custom-unit extension

The SHA-256 checked Windows x64 portable archive (`9b6244c366e50c2e7c73e169594c2922a41ff58345bd783fbe16ba2f35ea85a1`) launched its native desktop UI on Windows 11 and opened the **same** headlessly created `mixer.dwxmz` over the WSL UNC path. The pre-edit file was preserved with SHA-256 `1baaf07f3892e03ef91f865ff4f5550b30f6dfd5a35f6631e29120bc86ec518f`. In the native editor, the `FeedB` stream tag was changed through its editable UI control to `FeedB_UI` and the native Save button was invoked. The resulting file hash was `5c7e16dc5d037ae8b70e717d2d0d62c3c40fc1f68fba835ad8af24512575d0c2`; its XML and the [post-edit desktop screenshot](../implementation/103-evidence/dwsim-desktop-edited-2026-09-24.png) (SHA-256 `431edbd411b46c291968ac453c98cb2a40a37a0bc09d291d3db4af56f724dbac`) show `FeedB_UI`. A fresh WSL2 MCP process loaded that exact file, listed the same four native IDs with the new tag, read back 1 and 2 kg/s feeds and 3 kg/s product, returned zero readiness findings and zero solve errors, and reproduced a zero mass residual. This proves the desktop edit/save → headless read-back/solve direction. It does not establish Windows-native solver execution or general frontend parity.

The same desktop-saved case was then modified headlessly with `dwsim_stream_set_conditions` for `FeedB_UI` at 2.5 kg/s. Immediate authoritative read-back returned 2.5 kg/s; a new solve returned 3.5 kg/s product from 1 + 2.5 kg/s feeds. A separate `mixer-desktop-then-headless.dwxmz` was saved with SHA-256 `5458191f461f13166f728a28ca3adfd649e187c16bc365a7de94cd272c35d2f9`. The original desktop-saved file was preserved. This proves headless modification of a desktop-saved case and total mass closure for that mixer. It does not prove every native desktop-created case or every property setter.

### Dynamic event, state and process-restart extension

In a new copy of the packaged tank/valve/PID case, the headless API saved `JarvisBeforeEvent`, attached an event at 10 s setting inlet `PROP_MS_2` from 10 to 5 kg/s, and ran the existing `Sch1` schedule for 20 s. Event read-back listed the 10 s step. The inlet property read-back after execution was 5 kg/s. The monitored level series at 0, 5, 10, 15 and 20 s was 0.0100296, 0.0601778, 0.110326, 0.1354 and 0.160474 m. The slope change after 10 s is consistent with the halved feed, but is not a validated tank benchmark. A post-event state was saved and the native case was written as `tank-event-restart.dwxmz` with SHA-256 `cc3c6542a906404ca2233a27cf6db1a4ef32d3ef5059bbbb2509c2309d852ab3`.

After terminating that MCP process, a separate MCP process loaded the saved case. It listed both named states and the event, read 5 kg/s before restoration, restored `JarvisBeforeEvent`, and read 10 kg/s. Rerunning 20 s reproduced the five monitored level samples above and the 5 kg/s post-event inlet. This proves native state/event persistence and deterministic restart of this short case across a process boundary. It does not prove continuous time continuation from the exact interruption instant: the restored pre-event state starts a new schedule at 0 s. The run/status envelope reported 20 s and four steps while its nested summary reported 25 s and five steps; the actual series ended at 20 s. An adapter must derive sample timing from the time-series and reconcile or reject conflicting summary metadata.

A separate active/inactive PID comparison enabled linear opening characteristics on both sample valves, set `PID-008` to a 0.5 m setpoint, and ran the same 30 s schedule from separate loads. Native read-back confirmed the controller's `active` state. With PID active, monitored `V2` moved from 33.8441% to 0% at 5 s and stayed there; with PID inactive, `V2` remained 33.8441%, and the readiness check added `PID_INACTIVE`. This proves controller actuation reaches the valve variable. The monitored tank level was identical in both runs (0.0100296 to 0.310918 m), so process-level control effectiveness is **not** proven by this sample. The unsolved level-gauge warning remained; a pressure-flow-qualified BlueRev case is still required.

The packaged `Hydrocyclone Custom Unit Operation.dwxml` contains a `DWSIM.UnitOperations.UnitOperations.CustomUO` with persisted IronPython `ScriptText`. In WSL2 the headless solver ran this upstream sample with the custom unit marked calculated. The script accesses connected streams as `ims1`, `oms1`, `oms2`, calls CAPE-OPEN `GetProp`/`SetProp` for temperature, pressure, component fractions and flow, and produces script variables visible through `dwsim_unitop_get_results`. Through `dwsim_unitop_set`, a transient copy changed the script's separation efficiency from 98 to 97; solve readback changed `eff` to 97 and output mass flows to 2.752567013546597 and 9.247432986453404 kg/s from a 12 kg/s feed. Save → close → reload → solve preserved the modified script and results in `hydro-eff97.dwxml` (SHA-256 `ffe43d70d800a5a6d87f17a145b3623d69e1fd3148c15348baa5e2eac54d37a3`). Total mass residual was -1.78e-15 kg/s; the maximum five-species residual computed from reported overall-liquid mass fractions was 1.42e-16 kg/s. This is executable extension and persistence evidence, not a validated BlueRev separator. Its reported enthalpies give a 4,129.216 kJ/s inlet-minus-outlet difference, so the sample cannot be treated as an energy-qualified model; a BlueRev custom unit needs an explicit duty/energy closure and reference checks.

The 53-tool MCP surface has a material creation gap: `dwsim_unitop_add(type="CustomUO")` and `type="Python Script"` both returned unknown type, and `dwsim_unitop_add_external(display_name="Python Script")` refused it because the template does not implement `IExternalUnitOperation`. Loading and editing an existing custom unit works. Creating one from a blank case therefore needs proof through the native desktop or the lower-level Automation/Fluent API (`AddUnitOperation(ObjectType, tag)`), or a narrow upstream MCP addition; do not claim MCP creation today. The custom-unit API exposes `ScriptText`, execution-engine selection and dynamic-support flags, but the current probe has not proven custom-unit dynamic integration or BlueRev-specific equations. Scripts are executable code and belong behind a Jarvis capability/evidence boundary, not an AI promotion path.

### Jarvis frontend projection boundary for 149

An MCP `dwsim_flowsheet_list_objects` readback of the saved mixer returned stable native object IDs, tags, native types, x/y positions and dimensions, calculation flags and object errors. For example `FeedA` had ID `MAT-956c3ab4-33ca-4187-998a-769dd5ef99d7`; its position changed from `(50, 50)` to `(60.465347, 29.529707)` after desktop editing while its ID remained stable. `M1` retained ID `MIST-5ceecaac-0471-419b-89e0-4cc412c2f3bc`. `dwsim_graphic_list` returned no annotation objects for this case; it is not a stream-connection API. The saved native XML carries connector attachment IDs and port indexes. Its stream property-package ID resolves through root `PropertyPackages` to `DWSIM.Thermodynamics.PropertyPackages.SteamTablesPropertyPackage`; `SelectedUnitSystem1` supplies display units. The live `dwsim_flowsheet_summary` returned `property_packages: [null]` after reload, so that field alone is not authoritative.

The 149 frontend needs a read-only, revisioned projection with: native object ID/tag/type/category/geometry and calculated/error state; typed input and output ports with attached object IDs, connector indexes and energy/material kind; compound and property-package IDs plus resolved names/types; display-unit system; editable property IDs, current values, units and read-only status; solved stream phase/species values and unit values; dynamic schedule, integrator, monitored variables, event sets, controller wiring/parameters, stored-state names, time-series and findings; exact source case hash, DWSIM version/settings and provenance. Port attachments must come from native connector records or a proven Automation API, not canvas lines. A typed edit must target native ID plus expected case revision, call a supported DWSIM API, read back the affected inputs and graph, solve/check as appropriate, verify balances, then persist a new immutable Jarvis evidence revision. Native IDs remain case-local references, never canonical Jarvis object identity. The MCP surface currently covers IDs/geometry/values and dynamic summaries, but lacks a reliable complete connector graph and property-package identity in one call; `dwsim_dynamics_properties` reported 275 inlet properties but returned only the first 20 in an unfiltered call, so it is not a complete editable-property schema. An Automation/XML-backed adapter or upstream API repair is needed before implementing this projection. Jarvis keeps project/evidence/study authority while DWSIM owns the generic process graph and dynamic state.
