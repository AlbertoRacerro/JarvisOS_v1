### Exact owner ref

The common exact-ref model is bounded and workspace-scoped. Required fields:

- `workspace_id`: non-empty bounded id;
- `owner`: bounded domain namespace;
- `kind`: bounded owner-defined kind;
- `id`: stable object id.

Exact identity fields:

- `version: str | None`;
- `revision: str | None`;
- `immutable_ref: str | None`;
- `content_digest: str | None` (`sha256:<64 hex>` when present).

At least one of `version`, `revision`, `immutable_ref`, or `content_digest` is required for an accepted added ref. The service never fabricates one. An adapter may require a stricter subset for its own kind and must compare the supplied identity to current owner truth.

`owner + kind + id + exact identity + workspace_id` forms the deterministic exact-ref identity used for deduplication and digesting. Conflicting duplicate identities fail closed; identical duplicates collapse deterministically.

### Resolution output

A resolved ref contains only bounded inspected evidence:

- original exact ref;
- state `current | stale | unavailable | unknown`;
- inert `content` only when current and adapter-approved for preview;
- bounded source/provenance descriptor;
- optional sensitivity/egress metadata supplied by an existing owner;
- allowed common action classes.

A resolved ref is not a copied canonical record.

### Action registry

Fixed action classes remain:

`PRESENTATION | READ | CONTEXT | PROPOSE | COMMIT | EXECUTE | NAVIGATE`.

The common registry may register only `PRESENTATION`, `READ`, `CONTEXT`, `PROPOSE`, and `NAVIGATE`. Any adapter/capability registration containing `COMMIT` or `EXECUTE` is rejected deterministically at registration time. Common Jarvis code does not gain a fallback commit/execute path.

### Adapter activation

Production registry is empty in 111. The implementation establishes the protocol/registry and tests it with test-only adapters, but it does **not** register Project Knowledge, Development, Coding, BLUECAD or Process domain adapters. Only 121–123 may activate the relevant Jarvis domain adapters after their owner foundations exist. Specs 112–120 remain unable to register them.

## Preview and dispatch policy

### Preview

A new narrow common Jarvis context service resolves an explicit request list through the adapter registry and produces:

- deterministic ordered included refs/blocks;
- stale/unavailable/unknown outcomes without silent substitution;
- existing `canonical_digest()` over the exact inspected resolution payload/blocks;
- source manifest carrying exact ref identity;
- included/dropped/stale/unavailable counts/lists;
- configured character budget evidence.

The existing `/ai/context/packs/preview` endpoint is unchanged. The common contract should use a dedicated narrow `/ai/jarvis/context/preview` endpoint rather than overload the legacy project-record selection shape.

### Submit binding

`AIThreadSubmit` gains one optional common-context request/binding pair, omitted by default for full backward compatibility:

- explicit Jarvis context request: canonical route descriptor + added exact refs + budget;
- `expected_jarvis_context_digest`.

Both are supplied together or both omitted. For a new submit, `thread_service` rebuilds/revalidates the exact-ref preview before durable reservation. Digest/ref drift raises the existing conflict-style failure before `run_ai_task()` and therefore before provider spend. Immutable request identity includes the common-context request and expected digest so retries cannot change semantics under the same `request_id`.

The resolved current blocks passed to `run_ai_task()` use the existing context block/prompt-separation spine; the common layer does not call a provider directly.

### External exact-ref context

**Explicitly unavailable in 111.** 111 does not add a new owner-ref -> sanitized-derivative bridge to 059a because no production domain adapter is activated yet and adding egress transformation/approval logic now would be speculative authority.

If a submit contains Jarvis added-context refs and its execution route is not explicitly local/backend-safe under the existing routing contract, the common-context submit path fails closed **before** `run_ai_task()`/provider dispatch with a truthful unavailable/policy result. It must not forward raw resolved owner blocks to an external route, silently drop them, or rely on a later `manual_context_not_authorized` pause after presenting the capability as available.

A later 121–123 slice that activates a production domain adapter may separately prove and authorize the exact inspected-ref -> current approved 059a derivative bridge before external added-context dispatch becomes available.
