## Minimum-necessary conclusion

Current master already owns the shell, thread persistence, context preview and canonical AI execution authorities required by 091. The minimum implementation is therefore a bounded composition of those existing surfaces, plus one narrow backend extension to the **existing 090 thread-submit contract** so a user-approved 042 context preview can be consumed by the same durable thread interaction without introducing a second execution path.

No new durable store, migration, provider policy, ledger, transcript engine or shell region is necessary.

The only runtime gap is concrete: `AIThreadSubmit` currently carries prompt/task/route/token semantics only, and `thread_service.submit_interaction()` calls `run_ai_task(..., context_blocks=None)`. The existing 042 `/ai/context/packs/preview` endpoint can already build bounded server-owned context and return its digest, but 090 cannot bind that reviewed context to a thread submit. 091 therefore authorizes a digest-bound context-selection seam on the existing submit path.

Advisory role profiles are **deferred in 091**. Current canonical provenance has no dedicated profile-id/policy-version field, and forcing profiles into task kinds, route metadata, prompt text or a new ledger/schema would add disproportionate authority ambiguity for no acceptance-critical benefit. The initial sidecar is one honest `Jarvis advisory` role. A later slice may add versioned profiles only with explicit provenance authority.

### Test del minimo necessario

Criterio di accettazione: make the existing 083 sidecar the normal contextual Jarvis interaction surface while reusing 090 threads and showing exactly what bounded project context will be used before submission.

Questo lavoro serve a soddisfarlo? **sì**.

Il criterio è raggiungibile senza estendere il thread submit? **no** — current 090 hard-codes `context_blocks=None`; calling `/ai/tasks/run` instead would create a forbidden second conversation/execution path.

Perché non aggiungere altro? Existing 083/090/042/059b/061 contracts already cover shell ownership, thread durability/idempotency, context building, egress, budget, confirmation, continuation and provenance. Profiles, new stores, streaming, tools and shell redesign are not required.

### 042 context authority

`POST /ai/context/packs/preview` already accepts a workspace id, bounded selection and character budget. It uses `build_workspace_context_bundle()` server-side and returns blocks, digest, source manifest, counts and size estimates.

The frontend does not need a new preview endpoint. It needs only a typed client over this existing endpoint and a compact summary; raw preview blocks do not need to be rendered or persisted in sidecar state.

### Canonical execution authority

`run_ai_task()` already accepts bounded `context_blocks` and routes both local and external execution through the existing 059b/061 controls. 091 must continue to reach it only through the 090 thread service and its pre-created canonical flow.

No frontend provider call, direct `/ai/tasks/run` sidecar call, alternate flow creation or alternate proposal capture is authorized.

## Frozen context-submit seam

Extend the existing 090 submit model with the minimum optional context fields. Equivalent names are allowed only if semantics remain identical:

- `context_selection`: optional bounded selection using the existing 042 selection grammar (`kinds`, `statuses`, `ids`, `query`, `max_items_per_kind`);
- `expected_context_digest`: required when `context_selection` is present, forbidden when it is absent.

No raw `context_blocks` field is exposed on the thread API.

### Semantics

1. Absence of `context_selection` means no project context and preserves exact 090 behavior.
2. For a new request with context enabled, the server rebuilds the 042 bundle for the same workspace and bounded selection before reserving/dispatching the interaction.
3. The rebuilt digest must equal `expected_context_digest`. A mismatch fails closed **before provider dispatch and before creating a new interaction/flow**. The operator must preview again.
4. The exact validated blocks from that rebuild are passed to the existing `run_ai_task(..., existing_flow_id=...)`; they are not reconstructed by the frontend.
5. The request digest includes the normalized context-selection semantics and expected digest, so a request id cannot silently bind to different context.
6. An already-reserved duplicate with the same request id/digest remains an idempotent read and must not redispatch merely because canonical records changed after the original request. Therefore duplicate identity must be checked before a fresh context rebuild can invalidate an already-dispatched request. A race-safe duplicate check remains required again at reservation.
7. Context mismatch is a pre-dispatch validation outcome, not a provider failure and not a reason to create a second ledger path.

This seam deliberately binds **what the operator inspected** to **what the server dispatches**, avoiding the failure mode where preview A is shown but mutable records silently produce context B at submit time.

## Initial sidecar product boundary

The first 091 implementation contains one advisory identity only: `Jarvis advisory`. No profile selector is required or authorized.

The sidecar must:

- be available through the existing shell sidecar on workspace-backed application routes;
- retain the current route/workbench while open;
- list/select/create the same 090 workspace threads;
- show the bounded interaction history returned by 090;
- submit through the same 090 interaction endpoint;
- offer project-context off/on control;
- when context is on, call existing 042 preview, show compact source/count/size/digest information and bind submit to that digest;
- show the current route/selection as a **local contextual descriptor** only; it is not automatically provider context unless represented through the bounded 042 selection;
- preserve any existing stage-provided sidecar contribution as a secondary local context section rather than discarding it;
- show canonical state, persistence uncertainty and proposal references without adding mutation authority;
- keep `/ai-threads` as the non-primary inspection/history route.

A proposal reference may navigate to an existing Review/Engineering Data route. 091 adds no promote/reject/grade operation.

## State ownership and close/reopen behavior

The shell may hide/unmount visual sidecar content while an interaction is in flight. Closing or changing route must never cancel or redispatch canonical backend execution.

Implementation must keep enough request ownership to satisfy 090 retry semantics across the sidecar lifecycle. Acceptable minimum approaches are:

- App-mounted controller/hook state that survives panel close, with visual content rendered from that controller; or
- another equally small composition that demonstrably preserves pending request id and stale ownership across close/reopen.

Do **not** change Layout into a persistent hidden chat runtime merely to retain component state unless browser evidence proves the existing App-level approach cannot satisfy the contract.

Workspace/thread/route/selection changes synchronously invalidate stale UI ownership and release obsolete local busy state. Late completion may update canonical backend data but cannot overwrite the new visible context.

## Context preview freshness

Preview ownership is keyed by at least workspace plus normalized context selection. A route/selection/workspace change invalidates visible preview ownership. Late preview responses are ignored.

A digest mismatch at submit is rendered as a bounded “context changed; refresh preview” state and causes no provider dispatch.

The frontend stores only the bounded preview summary required for inspection. It does not cache raw complete context packs as a second authority.

## Required deterministic evidence

Backend focused tests must establish:

1. no-context submit remains exact 090 behavior;
2. context preview selection rebuild is server-owned and bounded;
3. matching expected digest passes those exact blocks to `run_ai_task` with the existing pre-created flow;
4. digest mismatch performs zero provider dispatch and creates no new interaction/flow;
5. same request id + same digest rereads without redispatch even if underlying records later change;
6. same request id + changed context semantics conflicts fail closed;
7. cross-workspace context selection cannot be used to dispatch in another workspace;
8. raw complete-thread history is never added to context;
9. external routes still traverse 059b policy/budget/confirmation and canonical 061 accounting.

Frontend deterministic/browser evidence must establish:

- shell opens one Jarvis sidecar without route navigation;
- existing stage sidecar and analytics dock contributions remain reachable;
- create/select/list/detail use 090 contracts;
- submit X → select Y before completion releases Y immediately and stale X cannot poison Y;
- workspace A→B→A stale rejection;
- close/reopen during an in-flight submit causes no second dispatch and preserves safe retry ownership;
- preview request → workspace/route/selection change ignores stale preview;
- changed context digest requires refresh and cannot dispatch;
- duplicate Enter/click is suppressed and unchanged retry reuses request id;
- confirmation-required, failed-terminal, partial-terminal and capture-failed/persistence uncertainty remain distinguishable;
- hostile markup-like text renders inertly;
- no-workspace/empty-thread/preview-failure states are explicit;
- keyboard submit/Escape/focus restoration and effective-200%-width containment pass;
- frontend tests perform zero external-provider/network calls beyond mocked same-origin API contracts;
- `/ai-threads` remains reachable and reads the same persisted threads.
