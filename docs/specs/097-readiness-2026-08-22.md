## 1. Readiness decision

097 is implementable as a bounded **frontend-only deterministic engineering-action V0** over the existing 071b/058c working-configuration owner.

The minimum safe V0 does **not** add a backend action API, thread schema, durable action table, provider route, runner endpoint, global state store, command bus, or natural-language parser.

The current runtime already provides the two boundaries needed for a useful first implementation:

1. `EngineeringProperties` owns the single transient working configuration, revision, baseline, Undo/Revert, semantic target/source, deterministic preflight and existing Run path;
2. `App` already composes that controller and the Jarvis sidecar under the same workspace/selection context, while `useJarvisSidecar` already accepts local contextual React content.

Therefore V0 should add typed, transient action cards generated only from **deterministic local/runtime evidence already held by the Properties controller**. Ordinary Jarvis prose remains advisory and inert. AI-origin executable action generation, exact natural-language command execution and previous-successful-run restore are deferred because current exact runtime does not expose a safe typed transport or compatible historical snapshot projection without broader authority expansion.

This is intentionally narrower than the eventual ergonomic target in the definition. It satisfies the definition's instruction to reduce implementation surface rather than invent a generic action architecture when exact runtime cannot safely support it.

## 2. Exact runtime evidence

### 2.1 Single working-state owner is already present

`frontend/src/components/engineering/EngineeringProperties.tsx` currently owns:

- `baseline` and `working` binding maps;
- `revision` and stale-preview generation guards;
- bounded Undo stack;
- field/Revert-all mutations;
- model selection;
- 058c semantic target/source adoption and dirty-target conflict handling;
- deterministic preview/preflight;
- existing request-keyed Run create/execute/retry path.

All direct working mutations converge on the controller's `commitWorking(...)`, which snapshots the prior bindings, writes one new binding map, increments revision and clears stale run result state.

097 must reuse this owner. It may add one typed compare-and-apply/atomic-patch method to the controller; it may not create a Jarvis shadow binding map.

### 2.2 Deterministic blocker evidence already exists

The Properties controller and panel derive current blocker state from authoritative preflight data:

- local non-finite numeric input;
- preview variable `binding_state === "invalid"`;
- required preview variable with `binding_state === "missing"`;
- server preview errors.

The panel already renders the blocker count and `Go to first issue`. No provider is needed to know whether the configuration is blocked.

097 may project this **existing result** into Jarvis action UI. It must not reimplement the model validator or invent blocker severities.

### 2.3 Jarvis conversation transport is text/proposal-only

`frontend/src/components/ai/useJarvisSidecar.tsx` and `frontend/src/api/threads.ts` show that current 090/091 thread interaction data contains assistant text, flow/persistence state and proposal references, but no typed engineering-action object.

`submitThreadInteraction(...)` sends free text plus optional inspected context digest and later reloads the thread. There is no trusted typed field that can be interpreted as a working-state mutation.

Consequences:

- assistant prose, Markdown, HTML-looking text or JSON-looking text remains inert;
- V0 must not parse assistant text to synthesize actions;
- V0 must not add a backend typed-action transport merely to reach the ergonomic natural-language target;
- exact natural-language command execution remains deferred until a later accepted authority can expose a typed server-owned action result without heuristic parsing.

### 2.4 App already provides the minimum composition seam

`frontend/src/App.tsx` creates one `engineeringProperties` controller and one Jarvis sidecar under the same route/workspace/selection owner.

`useJarvisSidecar(...)` already accepts local `contextualContent` and renders it inside the Jarvis sidecar without sending that React content to providers.

The minimum integration is therefore to pass one deterministic engineering-action surface, backed by the existing controller, into this local Jarvis context area. No second conversation engine or backend route is needed.

### 2.5 Existing Run authority is sufficient

`EngineeringProperties.startRun()` already requires:

- current workspace/model;
- no semantic conflict;
- current semantic context adopted when applicable;
- preflight phase ready;
- preview state `ready`;
- normalized input set;
- explicit non-empty run label.

It creates one request-keyed immutable run snapshot and reuses the existing runner create/run/retry path. Response-loss and replayed-terminal reconciliation are already implemented.

097 adds no run endpoint. After a working patch, preflight reruns because revision changes. Run remains a separate explicit operator action through the existing controller path.

## 3. Minimum typed action contract

The V0 action object is transient frontend data. It is not persisted as canonical state and is never reconstructed from transcript prose.

Conceptually it contains:

```text
EngineeringWorkingAction
- id                     stable UI identity for the proposal lifetime
- workspaceId            exact current workspace
- modelVersionId         exact selected model
- contractDigest         current authoritative input-contract digest
- workingRevision        exact controller revision at proposal time
- semanticTarget         exact current semantic target fingerprint or null
- operations[]
  - variableName
  - expectedBinding      exact current {value, parameterId}
  - proposedBinding      exact proposed {value, parameterId}
  - unit                 exact contract unit
  - basis                deterministic basis class
  - reason               human-readable deterministic reason
- confirmationRequired   boolean
- origin                 deterministic-local for V0
```

No arbitrary JSON payload from a model is accepted as this type.

### 3.1 Semantic target precondition

For object-specific actions, apply-time validation must bind to the same current 058c/092 engineering target, including current workspace/candidate/artifact/part identity and current semantic-source context. Ephemeral viewer/session identity remains a stale-response guard according to merged 058c/092 semantics; it must not become a second engineering identity authority.

Model-level actions use no object target but still bind workspace, model, contract digest and working revision.

### 3.2 Atomic compare-and-apply

The controller method must validate **all** operations before committing any mutation:

1. workspace still matches;
2. selected model still matches;
3. input-contract digest still matches;
4. working revision exactly matches proposal revision;
5. semantic target/source precondition still matches when applicable;
6. every variable still exists in the current authoritative contract;
7. each operation unit exactly equals the contract unit;
8. current binding exactly equals `expectedBinding`;
9. proposed numeric values, when non-empty, are finite;
10. proposed linked Parameter IDs, when used, resolve to a currently compatible same-workspace exact-unit finite non-superseded source under the existing controller rules.

Only after every operation passes does the controller call one working-state commit.

Any failure returns a typed local status such as `stale` or `invalid` and performs **zero** partial mutation.

First successful apply increments revision, so a repeated/double Confirm using the same action fails the revision precondition and cannot double-apply semantically.

## 4. What V0 action proposals may come from

V0 exposes only deterministic proposals that can be derived without provider execution and without inventing engineering values.

### 4.1 Safe deterministic bases available now

The current controller can prove these bases:

1. **Working baseline** — restore an edited field to its current authoritative working baseline when baseline value/source exists.
2. **Compatible canonical Parameter** — select an already-loaded same-workspace Parameter only when exact unit matches, value is finite and the source is currently usable under existing 071b/058c compatibility rules.
3. **CAD/semantic-source baseline** — for the reviewed object-specific Geometry values already adopted by 058c from the exact CAD-link source snapshot, restore to that adopted baseline.

These are the only V0 sources that may be described as deterministic safe-fix bases.

### 4.2 Safe-fix generation

`Apply safe fixes` may prepare one atomic action containing only deterministic operations whose basis is currently provable.

Examples:

- malformed/non-finite working override → restore a valid existing baseline;
- dirty required field whose baseline is valid → restore baseline;
- required missing field with exactly one currently compatible authoritative Parameter may be offered as a typed choice, but must not be silently chosen when multiple credible sources exist;
- object Geometry dirty override → restore exact adopted CAD-link baseline.

If no deterministic basis exists for a required numeric blocker, the blocker stays unresolved. V0 must never fabricate a number to reduce blocker count.

### 4.3 `Other` escape hatch

Every bounded deterministic choice set/action card must include `Other`.

In V0, selecting `Other` may reveal a local text input or route the operator toward manual Properties/Jarvis conversation, but entered text is **inert**:

- it does not call the compare-and-apply method;
- it is not parsed as JSON, `field=value`, Markdown or imperative language;
- it does not become a typed action automatically.

The operator can still edit Properties manually. Future conversion of natural language into a typed action requires separate safe typed authority and is outside V0.

## 5. Explicit deferrals required by exact runtime

### 5.1 AI-origin executable actions — deferred

Current 090/091 thread output has no trusted structured-action projection. Adding one would require a new server contract, AI-output validation boundary and potentially working-state context projection into AI execution.

That is not minimum necessary for a useful 097 V0 and is therefore deferred.

Jarvis may continue to offer conversational advice. Any concrete numeric value or model recommendation presented by ordinary Jarvis assistant text inside 097 scope remains inert advisory prose **and must visibly carry `AI suggested — not validated` (or wording with the same substance)**. This warning is provenance/decision-support information only: it does not make prose executable, does not create a typed action and does not bypass confirmation or deterministic validation.

If a later slice introduces typed AI action proposals, AI-origin values must retain the same visible `AI suggested — not validated` substance and require confirmation exactly as the definition requires.

### 5.2 Precise natural-language command execution — deferred

Current runtime cannot convert `Set inlet pressure to 34 bar` into a trusted typed action without parsing free text in the frontend or adding new typed server AI authority.

Both are outside this V0. The phrase remains conversational input only.

Manual Properties editing continues to provide the precise direct-edit path.

### 5.3 Previous successful run restore — deferred to 006b

Current controller has the current run result and request snapshot but no authoritative read path that reconstructs an arbitrary prior successful run as a model/contract/unit-compatible working snapshot with exact source provenance.

Adding broad historical snapshot retrieval only for 097 would duplicate the planned variant/prior-run authority of 006b.

Therefore previous-successful-run automated restore and `restore ... and rerun` are not implemented in V0.

### 5.4 Patch-and-run natural-language intent — deferred

Since natural-language action execution is deferred, V0 does not create a combined typed `patch + run` command surface.

After any applied deterministic action:

- Properties updates immediately;
- revision changes;
- deterministic preflight reruns;
- existing explicit Run control remains the sole execution intent.

This preserves 071b run semantics and proves patch alone creates zero run records.

## 6. Deterministic blocker presentation in Jarvis

Add a bounded local action surface inside the existing Jarvis contextual-content region.

It may show:

- `Ready` when no blocker/action is relevant only if useful; avoid duplicating persistent green validator dashboards;
- current blocker count when blockers exist;
- first/current blocker engineering label and exact unit where available;
- deterministic safe-fix actions when a proven basis exists;
- `Apply safe fixes` only when at least one safe deterministic fix exists;
- `I'll edit` / `Go to issue` equivalent when manual input is required;
- `Other` on every bounded choice/action set.

Before **any** confirmable action/change-set can expose an enabled `Confirm`/`Apply` control, the normal operator-visible card must show the complete proposed change for every operation: engineering target/field, `old → proposed`, exact unit, deterministic basis/source and reason. This is mandatory for single-field and multi-field confirmable actions, including `Apply safe fixes`; machine preconditions such as workspace/model/contract/revision/semantic fingerprints may remain under Technical details. A summary-only card is never sufficient authority to confirm a mutation.

It must not claim that Jarvis AI discovered the blocker. The source is current deterministic preflight/working state.

Provider unavailability cannot remove this surface.

## 7. Error/status separation

V0 action UI distinguishes:

- `applied` — atomic working-state patch committed locally;
- `stale` — workspace/model/contract/revision/semantic-target/current-binding precondition changed;
- `invalid` — proposal no longer satisfies current deterministic contract/source rules;
- `no-safe-fix` — blocker exists but no deterministic basis is available.

AI/provider/thread errors remain the existing Jarvis conversation status and are never reported as engineering-action validation failure.

No local action status claims server persistence or canonical record mutation.

## 8. Durable state decision

No durable engineering-action persistence is necessary for V0.

Reasons:

- the working configuration itself is transient by 071b authority;
- actions are compare-and-apply proposals over that transient state;
- successful apply is already represented by the changed working state, dirty markers and Undo history;
- existing 090 transcript remains durable for ordinary conversation;
- persisting transient action cards would add schema/migration/idempotency work without improving the acceptance criterion.

Historical assistant messages are never retroactively parsed into actions.

## 11. Readiness questions answered

1. **Smallest typed action transport:** transient frontend typed object, generated only from deterministic Properties/preflight data. No thread/API transport in V0.
2. **Validation location:** one atomic compare-and-apply method on the existing `EngineeringProperties` controller before `commitWorking`.
3. **Exact controller seam:** expose current immutable action context/proposals as needed and one `applyEngineeringAction(action)` result; keep direct manual methods unchanged.
4. **Required identities:** workspace + model version + contract digest + working revision; object actions also bind current semantic target/source context.
5. **Natural-language conversion:** not safely available now; defer rather than parse prose or add a new server action path.
6. **Deterministic blocker projection:** derive from the existing current preview/local-invalid state and render through Jarvis local contextual content; no provider call, no duplicate validation logic.
7. **Safe-fix bases available:** current valid working baseline, currently compatible exact-unit canonical Parameter, and adopted 058c CAD/semantic-source baseline. No arbitrary fill.
8. **Previous successful snapshot retrieval:** insufficient for exact historical compatible restore; defer to 006b.
9. **Transient working values in AI context:** not needed in V0 because AI does not generate executable actions.
10. **Durable persistence:** unnecessary; actions are transient and successful apply is visible in the working state/Undo history.
11. **Double-confirm:** exact revision + expected-current-binding comparison; first apply increments revision, second fails stale.
12. **Files:** bounded allow-list in section 9; backend/thread/provider/runner/package changes are unauthorized by default.
13. **No text parsing proof:** hostile transcript and `Other` free-text browser cases plus code review showing no parser/action construction from assistant text.
14. **Error representation:** local applied/stale/invalid/no-safe-fix statuses separate from existing AI/provider failures.
15. **Run reuse:** action apply only changes working revision; existing 071b preflight and `startRun` remain the only run path.
16. **`Other`:** always present on bounded typed choice/action sets; alternative free text is local/inert and cannot call apply without a future separately typed authority.
