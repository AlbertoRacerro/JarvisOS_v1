## Readiness boundary

Implementation is authorized only for the bounded path frozen in the full spec:

1. deterministic version-controlled merge-authority declaration;
2. stdlib-only verifier with VERIFIED/MISMATCH/UNKNOWN/ERROR classification and hostile/offline fixtures;
3. permission-safe trusted live verification/reporting path;
4. explicit minimum enforcement request/action preparation for `master` only;
5. post-enforcement live readback.

The implementation may directly build and validate items 1–3 and the deterministic enforcement-request boundary. It may not fabricate success for item 4.

## Human-controlled enforcement gate

The current ChatGPT/GitHub connector exposes GitHub protection/ruleset reads but no supported branch-protection/ruleset write action. The detailed classic-protection endpoint is also unreadable to this integration. Therefore applying the actual protection is a known **human-controlled GitHub settings/permission gate**, not an implementation defect.

This does not block coding the verifier/bootstrap, because the implementation can and must first prove that current state is MISMATCH. It **does** block final acceptance/merge completion if the implementation reaches its enforcement checkpoint and `master` is still unprotected.

At that checkpoint the exact human action must be derived from the implementation's frozen declaration/check-context evidence. No broad or speculative settings change is authorized by this readiness packet.

## Required implementation evidence before the human gate

Before requesting any settings action, the implementation PR must prove on one exact head:

- declaration schema validation and deterministic digest;
- current unprotected snapshot -> MISMATCH;
- UNKNOWN and ERROR fixtures cannot become VERIFIED;
- exact required check contexts are discovered from real successful checks rather than guessed;
- auto-merge enabled -> MISMATCH;
- wrong repo/branch/ref enforcement target fails closed;
- privileged live verification/enforcement paths execute trusted master code only;
- no PR-controlled executable content receives a settings-write credential;
- no model/review/PR Attention workflow receives merge or settings authority;
- no runtime/product/provider/frontend/schema changes.

## Required final evidence

134 is merge-complete only when all are true:

1. deterministic implementation/test gates are green;
2. independent semantic review is terminal and acceptable;
3. `master` minimum protection has actually been applied through an explicit maintainer-controlled GitHub action;
4. deferred auto-merge remains disabled;
5. fresh trusted post-enforcement readback returns `VERIFIED`, not UNKNOWN/MISMATCH/ERROR, for every V1 minimum control;
6. exact implementation head remains current after any settings-side evidence that matters to acceptance.

A 2xx settings response without VERIFIED readback is insufficient.
