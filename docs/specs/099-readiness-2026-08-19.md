## Confirmed vulnerable runtime path

On inspected master, `.github/workflows/cheap-review.yml` and `.github/workflows/senior-review.yml`:

1. are manually dispatched with a PR number;
2. checkout `refs/pull/${{ inputs.pr_number }}/head`;
3. fetch `master` and overwrite only `AGENTS.md`, `scripts/cheap_review.py`, and `scripts/manual_review.py`;
4. execute `python scripts/manual_review.py` while a provider API key and `GITHUB_TOKEN` are available.

The trusted `scripts/manual_review.py` imports Python modules before entering `main()`, including `json` and `urllib.error`, and imports many names from `cheap_review`. Restoring only the two named review scripts is therefore not a complete executable trust boundary: other files below `scripts/` remain supplied by the reviewed PR and may shadow imported modules.

A concrete failure case is a reviewed PR adding `scripts/json.py`. Executing `python scripts/manual_review.py` places the script directory on Python's import search path; `import json` can therefore resolve PR-controlled code before the trusted review logic performs its API-based review. The same class applies to other direct or transitive imports.

No claim is made that this has already been exploited.

## Existing seam that makes the fix small

`manual_review.py` already does not need the PR checkout to obtain the review payload:

- `_fetch_pr(...)` obtains PR metadata through GitHub API;
- the PR diff is obtained through `gh_request(..., accept="application/vnd.github.v3.diff")`;
- the exact PR head SHA is captured from API metadata and checked again after model review for staleness;
- comments are posted through GitHub API;
- the implementation spec and `AGENTS.md` excerpts can be read from trusted merged `master`, which is the normal source of implementation authority under JarvisOS lifecycle.

Therefore the PR-head checkout is unnecessary for the manual Cheap/Senior review path.

## Chosen implementation boundary

For both `.github/workflows/cheap-review.yml` and `.github/workflows/senior-review.yml`:

- checkout trusted `refs/heads/master` only;
- use `persist-credentials: false`;
- delete the current partial repair step that fetches master and overwrites three files;
- execute the existing trusted self-tests and trusted `scripts/manual_review.py` from the master worktree;
- continue passing only the requested PR number and bounded provider configuration through environment variables;
- keep existing permissions unless a narrower permission set is proven sufficient without breaking comment posting.

The implementation may pin the checkout to an exact trusted master SHA resolved at dispatch if that can be done without broadening workflow complexity. A symbolic `refs/heads/master` checkout is acceptable for this emergency slice because `workflow_dispatch` itself is master-gated and the executed code/secret boundary remains repository-owner-controlled; exact reviewed PR SHA evidence continues to be captured separately by the script.

## Why partial sanitization is rejected

Rejected alternatives:

- restore a longer list of Python files from master: transitive imports can grow and the allow-list can become incomplete again;
- delete only `scripts/json.py`: fixes one proof-of-concept, not the class;
- trust fork-secret withholding alone: the vulnerable workflow is manually dispatched in the base repository with base-repository secrets, so the safe boundary must be explicit in our own job;
- run the provider step after tests over the PR checkout: a later Python import can still execute untrusted modules;
- rotate keys without changing workflow: rotation does not remove the execution path and would only replace credentials exposed by a future hostile dispatch.

## Implementation allow-list

Expected minimum paths:

- `.github/workflows/cheap-review.yml`;
- `.github/workflows/senior-review.yml`;
- one focused checker/test under `scripts/` and/or existing test locations;
- `scripts/manual_review.py` only for a minimal offline test seam or explicit trusted-worktree assertion if required;
- `scripts/cheap_review.py` only if the focused offline seam genuinely requires it;
- `docs/specs/STATUS.md` for lifecycle bookkeeping.

No product/backend/frontend/schema/provider/runner files are authorized.

## Deterministic proof required

The implementation must add a checker/test that fails against a fixture equivalent to the current vulnerable shape and passes only when all of these are true:

1. Cheap/Senior review remain `workflow_dispatch` only;
2. job is master-gated;
3. checkout is trusted master, not a PR ref or user-controlled ref;
4. `persist-credentials: false` is set;
5. no later shell command checks out/reconstructs a PR-controlled worktree;
6. secret-bearing execution invokes trusted `scripts/manual_review.py`;
7. provider secrets are not exposed to any earlier untrusted-code step.

A second offline test should prove the script can construct a review from mocked PR metadata/diff while the local filesystem contains only trusted master authority. It must make zero provider/network calls.

## External-PR secret-rotation gate

Before 099 merge, inspect available workflow/PR evidence for whether a vulnerable Cheap/Senior manual review was actually dispatched against an external/untrusted PR head. The existence of a fork, including `anujeditsbyanuj-bit/JarvisOS_v1`, is not evidence of credential disclosure by itself.

- If no vulnerable external dispatch is found, do not rotate solely because a fork exists.
- If one is found, or evidence is materially incomplete for a known suspicious dispatch, report the affected credential classes and rotate them through the existing secret-management path. Never expose values in logs or comments.
