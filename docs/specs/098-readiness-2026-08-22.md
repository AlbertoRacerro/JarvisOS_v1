## 1. Decision

098 is implementable, but the minimum safe V0 is **Parameter-first**, not a guessed uniform lifecycle layer over every engineering record kind.

The implementation may add server-owned lifecycle/edit authority for canonical Parameters and the corresponding Engineering Data controls. Assumptions, Decisions, Requirements and Model Specs remain read-only under their existing status/maturity contracts in this slice unless a later exact-head amendment proves an equally bounded seam. The UI must not fabricate disabled or client-only lifecycle behavior for those kinds.

This narrowing is required by exact runtime evidence:

- Parameters are the only Engineering Data kind already tied directly to 058c/071b working inputs, run-start source guards, explicit replacement lineage and 050/051 freshness invalidation.
- the existing Parameter replacement path already proves the transaction pattern needed for one canonical mutation + freshness + audit;
- current status vocabularies are asymmetric and overloaded with proposal/value/maturity meaning, so reusing `status` as a universal lifecycle field would corrupt existing authority;
- current generic freshness persistence is replacement-specific and cannot truthfully represent arbitrary deactivate/archive/delete invalidation with no replacement identity.

Therefore V0 implements the lifecycle vocabulary where it can be made truthful without a second store or second dependency engine, and rejects transitions whose downstream consequences cannot yet be persisted truthfully.

## 2. Exact runtime findings

### 2.1 Parameter persistence and revision seam

`parameters` already contains `updated_at`, canonical value/unit/provenance fields, proposal `status`, `value_status`, and `supersedes_parameter_id`.

`updated_at` is generated with timezone-aware `datetime.now(UTC).isoformat()` and changes on existing canonical mutations. It is sufficient as the bounded optimistic-concurrency token for this V0 when compared exactly inside the same transaction as the mutation.

Readiness therefore chooses:

- request precondition: exact `expected_updated_at` from the record displayed to the operator;
- server check: `WHERE id = ? AND workspace_id = ? AND updated_at = ?` or equivalent transaction-local compare before mutation;
- stale result: deterministic `409` domain conflict with no canonical write, audit event or freshness side effect;
- accepted mutation: assign a fresh `updated_at` in the same transaction.

No repository-wide revision framework, ETag layer, command bus or version table is authorized.

### 2.2 Lifecycle must be separate from current `status`

Current Parameter `status` participates in MemoryStore proposal/replacement semantics (`proposed`, `accepted`, `rejected`, `superseded`). `value_status` separately describes value/evidence quality.

098 must not overload either field.

V0 may add one additive Parameter column:

`lifecycle_state TEXT NOT NULL DEFAULT 'active'`

with accepted values:

`active | inactive | superseded | archived | deleted`

Migration/backfill rule:

- existing rows whose legacy `status = 'superseded'` become `lifecycle_state = 'superseded'`;
- all other existing rows become `active` under lifecycle semantics while their existing proposal/value status continues to determine whether they are actually eligible under domain rules.

No separate lifecycle table is justified for the Parameter-only V0.

### 2.3 Existing replacement transaction is the reusable pattern

`promote_parameter_replacement()` already uses `BEGIN IMMEDIATE`, validates the old/new Parameter relationship, prepares the 050/051 closure, updates both Parameter statuses, persists freshness marks, writes an event and commits atomically.

098 must reuse that transaction discipline. It must not create a second dependency traversal or audit store.

Existing Parameter replacement promotion remains the authoritative supersede path in V0. When it succeeds, 098 must also keep lifecycle truth coherent:

- superseded Parameter lifecycle -> `superseded`;
- replacement Parameter lifecycle -> `active`.

Engineering Data does not invent a second two-record supersede algorithm. If a replacement proposal does not already exist under 040 authority, the 098 action surface may direct the operator to the existing proposal/replacement flow rather than synthesize a replacement record.

### 2.4 Existing freshness persistence is replacement-specific

Current `freshness_invalidations` requires both `superseded_parameter_id` and `replacement_parameter_id`, and current `prepare_freshness_invalidation()` emits reason `upstream_parameter_superseded`.

It is therefore **not truthful** to reuse that persistence unchanged for a value edit, deactivate, archive or delete with no replacement.

V0 must not fake a replacement ID, repurpose the reason code, or add a generic second invalidation engine merely to make every lifecycle button succeed.

For a Parameter mutation that changes/removes current upstream authority:

1. compute the current 050 dependency closure using the existing graph authority inside the mutation transaction;
2. if the complete affected downstream closure is empty, the mutation may proceed with audit atomically;
3. if a non-empty downstream closure exists and the operation is not the already-supported replacement-promotion path, fail closed **before mutation** with a concrete `parameter_lifecycle_dependents_require_reconciliation` / equivalent domain response.

This is the definition-authorized rejection route when truthful invalidation is unavailable. A later 101/102-owned general canonical invalidation boundary may broaden it; 098 must not pre-empt that work.

### 2.5 Linked Parameter snapshots currently lack source revision binding

Schema-v2/v3 normalized inputs currently persist:

- numeric `value`;
- contract `unit`;
- `source_parameter_id` when linked.

The run-start usability guard re-reads current Parameter existence/workspace/status/value/unit/freshness, but it does not compare the current source value/unit/revision with the value/unit captured in the normalized input snapshot.

098 therefore authorizes the minimum source-integrity extension for schema-v2/v3 linked inputs:

- normalized linked input adds `source_parameter_updated_at` captured from the Parameter used by preview/normalization;
- current value and exact unit remain present in the same normalized item and are part of the immutable run payload;
- preview/normalization verifies the Parameter is lifecycle-current before returning `ready`;
- create and final execution claim require current Parameter `lifecycle_state = active`, exact source `updated_at` match, exact value match after existing finite normalization, and exact unit match;
- any mismatch fails with one deterministic linked-source-changed/unusable safety result;
- legacy schema-v1 and historical no-contract payload semantics remain unchanged.

No run snapshot redesign or second working-state owner is authorized.

## 3. Supported V0 Parameter mutations

### 3.1 Edit

Engineering Data may edit a bounded Parameter field set only:

- `name`;
- `symbol`;
- `value`;
- `unit`;
- `value_status`;
- `value_min` / `value_max`;
- `source_ref`;
- `confidence`;
- `notes`.

It must not directly edit:

- `id` / `workspace_id`;
- proposal `status`;
- `origin` / `source_ai_job_id` / `promoted_at`;
- `supersedes_parameter_id`;
- lifecycle state through the Edit command.

Existing Parameter validators continue to apply. Value/unit edits additionally require the downstream-closure and linked-source protections in this readiness.

Every Edit carries `expected_updated_at` and creates one durable atomic audit event containing actor/source, operation, changed field names, prior values and resulting values. Secret/event redaction remains owned by existing `log_event`.

### 3.2 Activate / Deactivate / Archive / Delete

These are dedicated lifecycle commands, not free-form status edits.

Every command carries:

- workspace ID;
- Parameter ID;
- expected lifecycle state;
- exact `expected_updated_at`;
- optional bounded human reason where the UI collects one.

Legal V0 transitions:

- `active -> inactive`;
- `inactive -> active`;
- `active|inactive -> archived`;
- `active|inactive|archived -> deleted`;
- retries against the already-achieved target may return an explicit idempotent/already-transitioned result only when the expected precondition proves they refer to the same accepted mutation; otherwise stale state fails closed.

`superseded` is entered only by the existing replacement-promotion authority in V0. No direct `superseded -> active` resurrection is authorized.

Delete is a tombstone state in the Parameter row. Physical deletion/cascade is not authorized.

Deactivate/archive/delete from current authority must apply the downstream-closure rule from §2.4. If dependents exist, reject before mutation rather than leave them falsely fresh.

### 3.3 Supersede

Engineering Data may expose `Supersede` only when there is an existing compatible proposed replacement that satisfies current replacement validation, or may route the operator to the existing proposal/review flow. Actual two-record promotion remains `promote_parameter_replacement()` (or a minimum wrapper over it), preserving existing replacement idempotency/freshness evidence.

On successful replacement promotion, lifecycle columns for both rows are updated in the same existing transaction as status/freshness/event persistence.

## 4. Server API and transaction boundary

Readiness does not require a generic lifecycle command bus.

Minimum acceptable shape:

- `PATCH /parameters/{parameter_id}` for the bounded canonical Edit model with `workspace_id` + `expected_updated_at`;
- one narrow Parameter lifecycle route, e.g. `POST /parameters/{parameter_id}/lifecycle`, with typed action literal and preconditions;
- existing replacement-promotion route remains the supersede execution path.

Exact route spelling may follow current routing conventions, but all mutation logic must converge on one Parameter-domain service boundary so API handlers do not duplicate transition legality, CAS, dependency closure, audit or lifecycle filtering.

Mutation transaction requirements:

1. `BEGIN IMMEDIATE` before reading mutable preconditions;
2. resolve exact Parameter in requested workspace;
3. validate `expected_updated_at` and expected lifecycle;
4. validate domain/value/unit constraints;
5. for authority-changing mutation, inspect complete existing dependency graph closure;
6. reject before write if a non-empty closure cannot be truthfully invalidated by the existing replacement path;
7. update canonical Parameter + lifecycle/updated_at;
8. write audit event in the same connection;
9. when using replacement promotion, persist its existing 050/051 invalidation in the same transaction;
10. commit once; any exception rolls back all effects.

## 5. Read/query semantics

### 5.1 Parameter API

Normal Parameter reads used as current canonical authority must exclude lifecycle states other than `active` unless the caller explicitly requests history/alternatives.

To avoid destroying audit/navigation capability, V0 must provide an explicit include/filter mechanism for Engineering Data history, rather than client-side hiding after receiving an undifferentiated authoritative list.

A bounded query parameter such as repeated `lifecycle_state=` or `include_noncurrent=true` is acceptable. Default behavior for existing current-authority consumers must be chosen by caller migration rather than silently changing unrelated historical/audit consumers.

### 5.2 Engineering Data

Normal Engineering Data mode:

- lists current Parameters only;
- still lists the other existing record kinds under their unchanged semantics;
- shows lifecycle humanly, separately from value/proposal quality;
- selected Parameter inspector may expose valid Edit / Activate-Deactivate / Archive / Supersede / Delete actions;
- successful mutation refreshes from server truth;
- rejected/stale mutation leaves no optimistic false state.

Advanced/Audit controls may request and show inactive/archived/superseded/deleted Parameters. These rows are visibly historical/noncurrent and are not treated as current source choices.

### 5.3 Context and linked-source projections

For Parameters, normal 042 canonical context must require both:

- existing requested `value_status`/proposal semantics;
- lifecycle `active`.

Explicit ID selection does not bypass lifecycle authority for normal AI context. A separate Audit/history surface may inspect a noncurrent record without injecting it as current canonical context.

058c/071b Parameter lookup for linked source choices must return/use lifecycle-active records only. Historical run/evidence lineage may still resolve tombstoned/noncurrent IDs through explicit audit reads.

## 6. Schema changes authorized

Only these additive schema changes are authorized by readiness unless exact implementation reveals a direct conflict:

1. Parameter `lifecycle_state` with server validation and default/backfill described in §2.2.
2. If needed for bounded query performance, one index over `(workspace_id, lifecycle_state)`.

No generic lifecycle table, deletion ledger, event store, new dependency table, or repository-wide revision column is authorized.

The existing `updated_at` is the V0 CAS token.

Migration tests must prove:

- pre-existing superseded Parameters backfill to lifecycle `superseded`;
- other rows retain all existing proposal/value fields and become lifecycle `active`;
- historical databases remain readable;
- migration is additive/idempotent.

## 7. Deterministic acceptance

Implementation must include focused tests for at least:

1. edit with matching `expected_updated_at` commits exactly once and advances `updated_at`;
2. two edits from the same old `expected_updated_at`: first commits, second returns stale conflict, with no second event or side effect;
3. lifecycle transition with stale expected lifecycle/updated_at fails before write;
4. wrong-workspace Parameter ID fails closed;
5. duplicate lifecycle retry does not duplicate audit side effects;
6. edit/lifecycle audit event contains target, actor/source, operation and reconstructable prior/result state;
7. noncurrent Parameters are excluded from current-authority Parameter/context/source queries and remain retrievable in explicit history mode;
8. deactivate/archive/delete with non-empty 050 downstream closure is rejected before mutation and leaves canonical/freshness/audit state unchanged;
9. the same lifecycle operation succeeds when the complete downstream closure is empty;
10. existing replacement promotion still atomically supersedes old + accepts replacement + persists existing freshness invalidation + audit, and lifecycle states become `superseded`/`active` in that same transaction;
11. linked schema-v2/v3 preview captures `source_parameter_updated_at` and rejects nonactive source;
12. canonical Parameter value/unit edit after preview causes create to reject the stale linked snapshot;
13. canonical Parameter value/unit edit after queue/create causes final claim to reject before execution when source revision/value/unit changed;
14. historical schema-v1/no-contract behavior remains unchanged;
15. mutation creates no provider request, AI job, runner execution or simulation run by itself;
16. migration/backfill rules are exact and idempotent.

Full backend Pytest, Ruff and spec-status gates remain required.

## 8. Browser acceptance

A browser/evidence harness must prove the implemented Parameter subset at normal desktop and effective 200%:

1. normal Engineering Data shows current Parameter lifecycle without exposing UUID as the primary identity;
2. Edit clearly says it changes canonical Engineering Data, not only the transient working configuration;
3. successful bounded edit refreshes value/unit/source/lifecycle from server truth;
4. stale edit conflict shows a deterministic message and refreshes current server truth instead of silently retrying;
5. Deactivate/Archive/Delete confirmation identifies target and consequence;
6. transition rejected for canonical dependents explains that current dependents prevent a truthful transition and leaves the row unchanged;
7. successful no-dependent transition removes the Parameter from normal current view;
8. secondary history control can reveal the noncurrent record with its lifecycle state;
9. Supersede does not invent a replacement; it uses/routes to existing replacement proposal authority;
10. workspace switch during an in-flight edit/transition cannot apply stale response to the new workspace;
11. keyboard access/focus restoration is usable for action menus/confirmations/conflicts;
12. no page-level horizontal overflow, focus trap or forced raw technical payload;
13. light/dark/system and reduced-motion invariants remain intact.

## 10. Explicit non-goals

- lifecycle/edit runtime for Assumptions, Decisions, Requirements or Model Specs merely for symmetry;
- generic record repository/ORM/command bus/event sourcing;
- a second canonical store or lifecycle table;
- generic dependency/freshness reimplementation;

## 11. Rollback

Rollback is additive and fail-safe:

- frontend lifecycle controls can be removed while leaving lifecycle columns/evidence readable;
- mutation routes can be disabled without rewriting historical records;
- lifecycle noncurrent rows remain retained rather than physically deleted;
- schema column is not destructively removed from existing databases;
- existing legacy status/value_status and replacement evidence remain untouched.

If source-revision guard integration cannot preserve historical schema-v1/no-contract behavior, implementation stops and returns to readiness rather than weakening the guard or migrating historical run payloads heuristically.

## 12. Minimum-necessary test

### Test del minimo necessario
Criterio di accettazione della spec:
Server-owned, stale-safe canonical Parameter Edit/lifecycle with truthful normal projections, audit, lineage and linked-run source integrity.

Questo lavoro serve a soddisfarlo? **sì.** Current Engineering Data is read-only; current Parameter status is not a lifecycle field; current linked-run guard cannot detect source value/unit revision drift; and current non-replacement lifecycle has no safe write path.

Il criterio è raggiungibile senza di esso? **no** for the selected Parameter subset. Frontend-only hiding violates server authority; reusing proposal status corrupts semantics; omitting CAS permits lost updates; omitting source revision permits stale run execution; forcing generic freshness persistence would fabricate replacement evidence.

Perché questa soluzione minima? It adds one Parameter lifecycle field, reuses `updated_at` as CAS, existing events, existing replacement/freshness transaction discipline, existing dependency graph and existing linked-source/run guards. It deliberately rejects non-replacement authority changes with downstream dependents instead of building the broader canonical invalidation/write architecture already owned by 101/102.
