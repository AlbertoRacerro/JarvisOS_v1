## Frozen implementation boundary

### HTTP contract

Add exactly one read-side V0 route on the existing AI API boundary:

- `GET /ai/provider-settings`

It returns a typed, secret-free projection of canonical provider identity/configuration, independent credential status axes, operation-specific credential mutation capabilities, and accepted status/blocking facts. It performs no provider egress, no persistence of a provider snapshot, no secret readback, and no provider smoke.

Credential mutation remains exclusively on the existing 082 Scaleway save/delete endpoint family. V0 adds no generic credential mutation route. Existing `POST /ai/provider-smoke/run` remains DeepSeek-only and must not be called, widened, parameterized, or represented as generic provider health.

### Permitted product-code touch set

Implementation is limited to the minimum required subset of these existing owner surfaces:

- `backend/app/modules/ai/provider_registry.py` — read-only canonical provider metadata consumption; do not create a second registry or mutate registry truth;
- the existing AI HTTP router/model/service modules that currently own `/ai/*`, only to add the typed `GET /ai/provider-settings` projection;
- `backend/app/modules/secrets/service.py` and `backend/app/modules/secrets/storage.py` only if required to expose already-owned bounded status/capability facts; do not broaden `ScalewaySecretStore` or add generic persisted-secret authority;
- `frontend/src/api/settings.ts` — browser-to-JarvisOS API client only;
- `frontend/src/pages/Settings.tsx` — provider catalogue/status/mutation interaction;
- `frontend/src/components/fusion/FinalSettingsSurface.tsx` only if section composition requires wiring; the canonical AI Settings route is `/settings/ai`;
- existing Settings styles/components only when necessary for the bounded interaction.

Any requirement to add a new provider SDK, provider adapter, generic secret store, generic provider-test service, second provider registry, global settings store, new policy/accounting authority, or browser-direct provider/network path fails readiness and requires separate prerequisite authority.

Before the implementation PR is opened, the implementer must resolve the exact existing AI router/model/service filenames from then-current `master` and list the actually touched subset in the PR body. This does not permit a new router solely for 124.

## Deterministic acceptance obligations

Exact-head evidence must prove all of the following together:

1. provider identities/capabilities are derived from the canonical provider registry, with unknown provider IDs failing closed;
2. `effective_source` and `persisted_state` remain independent typed axes, including environment, secure-persisted, absent, invalid-environment, corrupted, unavailable, not-required, and not-supported combinations;
3. API/frontend/event/log/error serialization contains no credential value and no masked preview derived from it;
4. persisted mutation capability is owner-derived and operation-specific; on this readiness head only Scaleway can expose persisted replace/delete, and those capabilities are not collapsed into one mutable boolean;
5. DeepSeek/GLM/Kimi remain environment-managed for credentials and receive no persisted save/delete affordance;
6. no browser-supplied provider ID, env-var name, secret reference, secret ID, filesystem path, or stale async response can redirect or cross-bind a mutation/status result;
7. ambiguous mutation/reload produces explicit `uncertain` state, no automatic retry, and no optimistic configured state;
8. environment override remains authoritative without hiding independent persisted-store damage;
9. usage/budget/policy/status projections delegate to accepted owners and do not synthesize a second health or accounting truth;
10. the browser talks only to JarvisOS backend endpoints; no provider URL/SDK/direct egress is introduced;
11. `POST /ai/provider-smoke/run` remains DeepSeek-only and is neither called nor generalized by `GET /ai/provider-settings` or Settings;
12. generation/identity guards prevent provider A catalogue/status/mutation responses from overwriting provider B or a newer canonical snapshot.

## Exact-head real-browser proof — REQUIRED

Because 124 changes provider/credential operator behavior, deterministic lower-layer evidence is not sufficient by itself. Final implementation acceptance requires accepted real-browser proof on the implementation PR exact head using a locally running JarvisOS frontend and backend.

The proof must exercise `/settings/ai` against real JarvisOS backend responses and record, without exposing any credential value:

1. provider catalogue/status renders from `GET /ai/provider-settings` and browser network traffic targets JarvisOS backend only;
2. a no-credential/local provider shows `not_required` / `not_supported` semantics and no mutation control;
3. an environment-managed provider shows environment/absent/invalid status as available from the owner and no persisted mutation control;
4. Scaleway persisted replace and delete follow the existing 082 endpoint family, canonical state is reloaded after definitive completion, and no secret value/preview appears in DOM, URL, storage, console, network response, or Jarvis context;
5. an environment override does not falsely present persisted replacement/deletion as changing the effective credential, while persisted-state damage/cleanup remains independently visible;
6. switching provider or refreshing while a read/mutation is pending cannot let stale completion overwrite the newly selected/current provider;
7. an ambiguous/refused/error outcome remains bounded and truthful, with no auto-retry or stale green/configured state;
8. no generic Test connection/provider-smoke affordance appears and `/ai/provider-smoke/run` is not triggered by Settings.

The browser artifact must name the exact implementation head SHA. Any head mutation invalidates this browser proof and requires it to be repeated.
