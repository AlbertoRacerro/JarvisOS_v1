## 1. Readiness result

Fresh exact-master inspection finds that the existing 006b/088/089 seams are sufficient for a frontend-only V0. No backend route, schema, store, provider path, unit-conversion layer, or second analytics owner is required.

The minimum implementation extends the existing single Analysis Dock so one transient selected-run set drives both:

1. the already-089-owned result comparison; and
2. a new read-only engineering-configuration matrix derived from the same persisted successful run snapshots and exact current model contracts.

The implementation must not create a durable variant/comparison object and must not mutate the 071b working owner merely by comparing runs.

## 2. Exact runtime findings

### 2.2 006b already contains the exact configuration reconstruction rules

`frontend/src/components/engineering/previousRunLoad.ts` provides `reconstructPreviousRunBaseline(...)` and proves the relevant V0 compatibility boundary:

- same workspace;
- run status exactly `succeeded`;
- non-null exact `model_version_id`;

- authoritative input contract available with digest;
- no unknown persisted input keys;

058b may reuse these pure validation/reconstruction semantics read-only. It must not invoke the 006b working-state adoption path while merely rendering a comparison.

### 2.3 089 already owns result comparability

`frontend/src/components/analytics/analyticsState.ts` already owns:

- run projection from persisted `output_payload`;
- successful-run and model-version requirements;
- supported result envelope validation;

- declared-unit requirement;
- bounded output payload/key/unit limits;

058b must call/extend this authority rather than fork a second output parser or conversion table.

### 2.4 One transient run-selection owner already exists

`AnalyticsDockContent.tsx` already owns one local `selectedIds` set and keeps it bounded to six runs. Workspace changes synchronously clear run and selection state before the next response is accepted. This is the correct V0 owner for comparison selection.

Do not add another comparison context, persistent browser state, second run picker, second drawer, or comparison page.

### 2.5 Model semantics are shown only when contract authority proves them

Current model implementations expose the authoritative input contract used by 006b. 058b may show a semantic model-family/model-option row only when the exact selected model implementation/contract contains authoritative schema-v3 metadata that the current runtime can parse without inference.

If that metadata is absent or malformed, configuration input rows may still compare, but the UI must omit the semantic model-choice row rather than infer one from implementation IDs, labels, payload values, or display text.

### 2.6 Historical provenance remains evidence-only

Configuration cells compare the effective historical value that was persisted in each immutable run snapshot. Historical source identifiers/revisions may remain Inspect/Audit evidence if already available, but V0 must not resolve them through current project records and must not relabel a historical value as currently `Measured`, `Parameter`, `CAD`, or `Linked stream`.

No new provenance resolver is required for 058b.

## 3. Frozen V0 compatibility predicates

### 3.1 Configuration comparable

A selected run is configuration-comparable only when all hold:

1. same current workspace;
2. `status === "succeeded"`;
3. exact non-null model-version identity resolves to an available current implementation in that workspace;
4. its input contract is parseable and has a non-empty digest;
5. persisted `input_payload` parses as an object;
6. every persisted field exists in the exact contract;
7. every required contract field exists in the snapshot;
8. every persisted value is finite numeric data in the supported V0 scalar shape;
9. every persisted unit equals the contract unit exactly;
10. all selected runs use the **same exact model-version identity** for aligned configuration rows.

No fuzzy cross-version mapping is authorized in V0, even when two contracts look structurally similar.

When any selected run fails this predicate, configuration comparison is explicitly unavailable/incompatible. Result comparison may still be shown only if the independent 089 predicate can prove it.

### 3.2 Configuration row identity

Rows align by the exact authoritative contract variable `name`, never by:

- display-label similarity;
- array order;
- numeric-value coincidence;
- guessed unit dimensionality;
- model display name;
- mesh/scene identity;
- AI inference.

Units come from the exact contract and must still match the persisted snapshot exactly.

### 3.3 Result comparable

Result comparison remains exactly the existing 089 rule in `analyticsState.ts`:

- supported succeeded output envelope;
- finite numeric scalar;
- stable exact output key;
- declared non-empty unit;
- exact unit-string equality across selected runs;
- same exact model version under the current 089 direct-comparison rule.

058b adds no conversion table.

### 3.4 Partial compatibility presentation

Configuration and result compatibility are separate states. The UI must be able to say, for the same selected set:

- configuration + results comparable;
- configuration comparable / some result groups rejected;
- configuration unavailable / results comparable;
- comparison unavailable.

Never use one broad `Compatible` badge for all evidence.

## 4. Baseline rule

V0 uses exactly one comparison baseline.

Rule:

- baseline defaults deterministically to the **first currently selected run**;
- operator may explicitly choose another currently selected run as baseline;
- removing the baseline immediately promotes the first remaining selected run;
- fewer than two selected runs returns to the existing instruction state.

Baseline choice is transient and resets on workspace change. It is identified in accessible text, not color alone.

For a comparable numeric configuration/result cell, V0 may show the recorded value and an absolute delta from baseline. Percentage change, ranking, scoring and optimization are out of scope.

## 5. Bounds

Reuse current 089 bounds wherever they already exist.

Frozen V0 bounds:

- maximum selected runs: `6` (existing `MAX_SELECTED_RUNS`);
- maximum persisted output keys: `128` (existing 089 bound);
- output key length: existing `160` code-point bound;
- output unit length: existing `64` bound;
- output payload: existing `1 MiB` bound;
- maximum configuration variables per exact input contract: **128**;
- configuration variable name length: **160 code points**;
- configuration unit length: **64 code points**;
- input payload accepted for comparison only up to **1 MiB UTF-8**.

These new configuration-side limits mirror the already-proven 089 hostile-payload scale and do not alter backend persistence. Exceeding a bound rejects configuration comparison explicitly; it does not silently truncate data used for compatibility decisions.

The UI may visually collapse/scroll rows locally, but semantic comparison must not silently omit a row and still claim complete compatibility.

## 6. Async and stale safety

The current Analysis Dock has workspace-generation rejection but 058b adds selected-run/model reads and therefore requires one monotonic comparison generation bound to:

- workspace id;
- ordered selected run-id set;
- baseline run id;
- relevant exact model-version identities.

On workspace or selected-set change:

1. increment generation;
2. clear derived configuration rows and compatibility summary synchronously;
3. accept later async evidence only if generation + workspace + selected set still match.

Required fail-closed cases:

- workspace A → B with late A response;
- selected X → Y with late X evidence;
- X → Y → X with late first-X response;
- baseline removed;
- run disappears during refresh;
- model implementation becomes unavailable;
- one selected run is malformed/incomplete;
- route/dock closes while comparison read is pending.

Because `listRuns` already carries persisted input/output snapshots, the minimum path should avoid unnecessary per-run detail fan-out. Model-implementation reads may be shared/current rather than one request per row.

## 7. Analysis Dock implementation decision

Extend the existing `AnalyticsDockContent` and existing analytics state helpers. Do not create a second comparison surface.

Recommended bounded composition:

- keep `selectedIds` in `AnalyticsDockContent` as the sole comparison-selection owner;
- add transient `baselineRunId` derived from/validated against that same selected set;
- fetch/reuse current workspace model implementations required for exact contract validation;
- extend pure analytics/comparison helpers with configuration projection/comparison;
- render one engineering-first comparison matrix section above or alongside the existing result groups inside the same dock;
- keep existing 089 result groups and rejection semantics intact.

The implementation should prefer pure helper functions and one composed comparison result over a second reducer/store.

## 8. 006b Load behavior

A Load action is **not required** inside the 058b matrix for V0 because source Runs already expose the 006b action. The comparison surface must at minimum allow navigation to the source Run.

This deliberately avoids duplicating dirty-confirmation/model-switch/load state inside Analytics Dock.

If implementation can reuse the exact existing Runs navigation without adding another loader, do so. Do not add a second reconstruction/apply helper just for comparison.

## 11. Deterministic acceptance

The implementation must prove at least:

1. two same-workspace successful runs with one exact model version align exact contract variable names and exact units;
2. historical effective values are compared without restoring live source bindings;
3. optional missing values render explicit Empty/unavailable state rather than zero;
4. different model versions reject configuration alignment even if variable labels/units happen to match;
5. unknown persisted field rejects configuration comparison;
6. required missing field rejects configuration comparison;
7. malformed/non-finite input rejects configuration comparison;
8. exact-unit mismatch rejects configuration comparison;
9. schema-v3 model choice appears only when authoritative metadata is present and valid;
10. result observations continue through existing 089 comparability, including exact-unit rejection;
11. first selected run is deterministic baseline and operator baseline change produces deterministic absolute deltas;
12. removing baseline selects the first remaining run;
13. one partial/malformed selected run is not silently omitted from a comparison claiming completeness;
14. workspace/selection generation guards reject late evidence;
15. comparison produces zero canonical mutation, zero runner create/run, zero provider/thread call and zero BLUECAD mutation;
16. comparison selection is transient and creates no browser-storage/durable truth;
17. no 058d Process scaffold or 100 visual-identity behavior appears.

## 13. Minimum-necessary test

Acceptance criterion: compare a bounded set of immutable successful runs using exact engineering configuration evidence and the existing unit-safe result analytics, without another state/analytics authority.

This work needs no new backend/store/infrastructure. The existing run snapshots, exact model contracts, 006b validation semantics and 089 Analysis Dock satisfy the criterion.

A second comparison page/store, backend endpoint, durable variant table, conversion service or AI summary would not be minimum necessary and is rejected.
