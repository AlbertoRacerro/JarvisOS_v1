## Final implementation owner and file set

Implementation is authorized only for this bounded surface, revalidated again at implementation start:

1. `backend/app/modules/coding/runtime_truth.py` — new sole local-runtime observation/alignment owner: trusted root derivation, fixed Git probe seam, startup/live snapshots, typed failures, alignment derivation, safe telemetry.
2. `backend/app/modules/coding/runtime_routes.py` — one GET-only Coding route; no arbitrary local path/command/process input.
3. `backend/app/main.py` — capture/store one immutable process-start snapshot and register the narrow route.
4. Focused tests under `backend/tests/test_coding_runtime_truth_119.py` and, only where route/startup behavior needs separation, one small route/startup regression test file.

No changes are authorized to 118 transport semantics, database schema, persistent state, frontend, provider/credential systems, runner execution machinery, generic system-info ownership, dependency files, architecture network ownership, or service-control surfaces unless a deterministic implementation failure proves a directly necessary minimal supporting change. No new third-party dependency is expected or authorized by default.

## Runtime repository identity

119 observes **this JarvisOS runtime checkout**, not an arbitrary configured coding repository. The request may name a repository only to select the approved remote target, and implementation must reject/return typed `repository_mismatch` unless it equals the canonical runtime repository identity `AlbertoRacerro/JarvisOS_v1` **and** is present in `settings.coding_repositories`.

This prevents a valid additional configured repository from being compared against the JarvisOS local root. No `.git/config` remote discovery, arbitrary local repository mapping, or new configuration field is needed for 119.

## Trusted root derivation

`runtime_truth.py` derives the expected repository root from its own resolved module location, equivalent to `Path(__file__).resolve().parents[4]` for the accepted file location, then validates the observed Git top-level path against that resolved path.

The implementation must avoid exposing the raw absolute path. API/log identity is SHA-256 of a normalized resolved path string. Root derivation is not request-configurable.

## Fixed Git observer

A private probe helper uses `subprocess.Popen`/equivalent bounded communicate semantics directly; it does not reuse runner ownership/execution sessions because those create working/lock artifacts and own executable code execution rather than observation.

Frozen constraints:

- executable command family is fixed to `git` with only the accepted read probes from the full spec;
- `shell=False`;
- cwd is the trusted derived root only;
- environment is constructed explicitly with `GIT_OPTIONAL_LOCKS=0` and `GIT_TERMINAL_PROMPT=0`; implementation may preserve only host variables proven necessary to locate/start Git on supported Windows/POSIX platforms (for example `PATH`, and Windows process-launch essentials such as `SystemRoot`) and tests must assert no arbitrary application/provider credentials are forwarded;
- stdin is disabled/closed;
- stdout/stderr are captured as bytes and each bounded to 64 KiB before UTF-8 parsing;
- hostile repository/branch/filename text is never executed, logged, or interpolated into another command;
- no optional-lock/index-refresh fallback is allowed.

Official Git behavior supports this design: `GIT_OPTIONAL_LOCKS=0` / `--no-optional-locks` prevents the optional status index refresh. Tests enforce the environment rather than relying on host side effects as the sole proof.

## Startup latency bound — closes PR #531 P3 PARK

The four allowed observations do **not** each receive an independent worst-case 2-second budget at startup. Instead one complete snapshot has a **2.0-second total wall-clock deadline**:

- compute a monotonic deadline before the first probe;
- each later probe receives only remaining time;
- after root/SHA failure or deadline exhaustion, stop optional later probes and return the typed degraded snapshot;
- no retries;
- startup capture must occur off the async event-loop path when invoked from lifespan, or before the loop begins during app construction; it must never synchronously block an active event loop for Git I/O.

Therefore Git observation can delay a process/reload by at most approximately the single 2-second snapshot budget, not ~8 seconds. Git unavailable/non-Git should fail much faster. The snapshot is immutable after capture.

## Target stability — closes PR #531 P3 PARK

For every result that could otherwise become `aligned`, `local_behind`, or `divergent`, target-ref re-resolution through 118 is **mandatory** immediately before final classification. Initial and final exact target SHA must match. A moved target produces `alignment=unknown`, `reason=remote_target_moved`.

If the result is already irreducibly `unknown` from local evidence before remote classification (for example dirty/unknown state or startup/live mismatch), implementation may fail fast without spending an unnecessary second target resolution, provided it does not emit a non-unknown state.

## Remote request budget — closes PR #531 P3 PARK

119 performs no background polling and no automatic refresh loop. One explicit runtime-truth request has:

- normally 2 GitHub reads for initial/final `repository_ref_truth` when local SHA already equals target and no relation compare is needed;
- worst-case the existing 118 `compare_truth` resolution/compare reads in addition when a clean unequal local SHA needs ancestry classification.

119 must not call 118 compare for dirty/unknown/startup-changed cases and must not call compare merely to produce decorative delta metadata. Rate limiting remains fail-closed to typed unknown/unavailable and is never retried or bypassed with another provider/credential.

No cache is introduced because a cache would create a second freshness owner; no new credential is introduced by 119.

## Ancestry versus projection completeness — closes PR #531 P2 PARK

The full-spec statement that any `compare_truth.partial` prevents `local_behind`/`divergent` is narrowed here to the actual 118 semantics.

118 `partial` can be set because changed-file/commit **projection** exceeds its bounded return surface. This does not by itself invalidate GitHub's top-level compare relationship fields. Therefore:

- semantic delta/file projection preserves and displays `partial=true` when bounded;
- ancestry classification may still use top-level `status`, `ahead_by`, and `behind_by` when all are present, type-valid, internally consistent, and describe the requested exact local/target SHA pair;
- missing/malformed/contradictory relation fields, typed provider failure, stale target, or inability to resolve the local SHA remain `unknown`;
- `local_behind` requires target/head to be strictly ahead of local/base (`status="ahead"`, `ahead_by>0`, `behind_by=0`) under 118's compare(base=local, head=target) orientation;
- `divergent` requires an exact unequal clean pair with a valid non-behind relationship (`status="diverged"` or target-behind/local-ahead evidence as represented by the validated 118 fields); implementation tests must freeze the actual accepted status/field combinations and reject unknown strings rather than infer.

Projection truncation never becomes an excuse to fabricate file completeness, but it also does not erase reliable ancestry metadata.

## Startup/live identity semantics

The startup snapshot is captured once for the backend worker process and never recomputed by request handling. It records process-start observation provenance, not byte-for-byte loaded-module proof.

A fresh live snapshot is captured per explicit request. Any SHA/dirty/ref-state difference between startup and live observations forces `worktree_changed_since_start=true` and `alignment=unknown` even if live HEAD currently equals remote target.

Matching startup/live SHA is insufficient when either dirty state is not clean.

## Route contract

Accepted route remains GET-only:

`GET /api/coding/runtime-truth?repository=AlbertoRacerro/JarvisOS_v1&target_ref=<validated-ref>`

Request fields are only `repository` and `target_ref`. No path, cwd, executable, argv, environment, PID, service name, local SHA, dirty override, provider URL, token, or command field exists.

The response returns only bounded structured metadata:

- startup and live SHA/ref-state/branch/dirty/provenance/timestamp/root digest;
- stable remote repository/ref/SHA evidence from 118;
- `alignment`, `reason`, and `worktree_changed_since_start`;
- optional 118-owned compare projection with its partial flag;
- observer/remote status and typed failure codes.

Raw absolute paths, status filenames, stdout/stderr, environment, process inventory, repository content, and secrets are excluded.

## Failure behavior

Git unavailable, non-Git installation, root mismatch, timeout, malformed/oversized output, unsafe dirty-state inability, startup capture failure, remote target unavailable/moved/rate-limited, remote local-SHA not found, or relation evidence unavailable all degrade safely to typed observer state / `alignment=unknown` as appropriate. App startup must continue even if the startup snapshot is unavailable.

A failed observer never invokes update/restart/sync behavior and never retries through a different command/provider.

## Deterministic implementation tests

The implementation PR must include offline/injected-probe tests for at least:

1. exact clean startup/live/target match -> aligned;
2. dirty matching SHA -> unknown;
3. startup/live SHA or dirty/ref mismatch -> worktree-changed + unknown;
4. validated 118 relation with `status=ahead`, ahead>0, behind=0 -> local_behind even when only compare projection is partial;
5. valid diverged/local-ahead top-level relation -> divergent under frozen combinations;
6. malformed/contradictory/unknown relation fields -> unknown;
7. local-only/unpushed SHA not resolvable by 118 -> unknown and no local diff engine;
8. initial/final target SHA mismatch -> remote_target_moved + unknown;
9. target re-resolution is performed before every non-unknown classification;
10. dirty/local-changed cases short-circuit unnecessary remote compare;
11. detached clean known SHA is valid observation and classified by SHA relation only;
12. git unavailable/non-Git/root mismatch fail typed without blocking app startup;
13. root resolver cannot be supplied/escaped by request and mismatch halts trusted observation;
14. probe seam uses shell=false, fixed cwd/argv family, `GIT_OPTIONAL_LOCKS=0`, `GIT_TERMINAL_PROMPT=0`, stdin disabled, and credential-free minimal environment;
15. one snapshot shares a total 2.0-second deadline and does not accumulate four independent 2-second waits;
16. slow startup capture does not block an active asyncio event loop;
17. timeout terminates/reaps the Git child and returns typed failure;
18. 64-KiB stdout/stderr bound and malformed UTF-8 fail typed without raw-output logging;
19. hostile status/branch/filename content can only influence dirty/ref data and is never executed/logged;
20. canonical runtime-repository mismatch is rejected even when another repository is validly configured for 118;
21. request schema cannot express path/executable/argv/env/PID/service/token/local-state overrides;
22. mutation Git verbs, runner execution, service control, file mutation, package/build actions and direct network transport are absent/unreachable;
23. raw local path and dirty filenames do not appear in response/logs;
24. existing `/api/system/info` fields and semantics remain unchanged;
25. no new dependency/database/cache/background worker/provider credential is introduced.

## Readiness conclusion

The accepted 119 boundary is implementable on fresh master as one small local observer + one GET-only route + startup registration + focused tests. It reuses 118 for all remote truth, keeps local and remote evidence distinct, has a bounded 2-second startup observation budget, resolves the review's ancestry/partial ambiguity, fails closed under Git/provider uncertainty, and adds no update/restart authority.

After this readiness artifact merges, transition the live `119` row mechanically from `planned` to `ready`. Only fresh `STATUS.md=ready` with dependency 118 still merged authorizes implementation.
