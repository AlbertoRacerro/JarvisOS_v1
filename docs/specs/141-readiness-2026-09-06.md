# 141 LOCAL-WORKTREE-ACTUATOR-1 — readiness decision — 2026-09-06

## Decision

**READY pending the registry transition in this readiness PR.** This artifact authorizes only the bounded repository implementation described below once `docs/specs/STATUS.md` records 141 as `ready` on the same accepted readiness head. It does not install or enroll a worker on any workstation, bootstrap credentials, authorize 125/126, create browser/desktop authority, or make a local host a global availability dependency.

Derivation basis: exact `master` `4ce7205dd7f5596fd8c76dcf31db0a3567d4f4f8`, containing the merged 141 definition and full specification. Hard dependencies 118, 119, 120, and 123 are already `merged` in the live registry.

## Minimum implementation ownership

The implementation is limited to these owners, with minimum splitting allowed only when tests prove it reduces authority coupling rather than creating another stack:

1. `scripts/repository_delivery.py` — one deterministic shared Git mutation-safety primitive for repository-development lanes. It owns normalized protected/default-branch refusal, remote/ref validation, common sensitive-path baseline, ordinary non-force push admission, exact remote-head readback, CAS/result classification, and safe Git invocation configuration. Existing 022/079 callers retain their lane-specific policy and credential/orchestration semantics; they may compose stricter restrictions on top of this baseline.
2. `scripts/local_worktree_actuator.py` — the 141 worker core: registered worker/repository/worktree identity, OS-local user-scoped request handling, observer/reviewer/implementer capability admission, worktree lifecycle, named test profiles, durable local state/audit, local writer lock, stage/commit, and delegation of every network-mutating Git operation to `repository_delivery.py`.
3. `backend/tests/test_repository_delivery.py` — deterministic shared Git-delivery safety tests over temporary repositories/bare remotes.
4. `backend/tests/test_local_worktree_actuator.py` — worker topology, state, containment, role, persistence, audit and named-profile tests.
5. Existing `scripts/codex_pr_autopush.py` and `scripts/daily_development_continuation.py` plus their existing tests may receive only the smallest compatibility edits required to consume the shared primitive without changing 022/079 accepted semantics.

No product backend route, frontend surface, product SQLite migration/store, generic MCP framework, generic process supervisor, PTY, desktop layer, or self-update component is authorized.

## Frozen sensitive-path policy for implementation

Readiness resolves the full-spec review ambiguity by freezing one **shared baseline plus lane-specific stricter policy**, not by pretending the existing 022 and 079 classifiers are already identical.

The shared baseline must refuse before stage/commit/push:

- `.github/**`;
- `AGENTS.md` and every recognized `CODEOWNERS` path;
- `scripts/codex_pr_autopush.py`, `scripts/daily_development_continuation.py`, the 141 worker/shared-delivery modules, and the tests that guard those authority boundaries;
- `.env`, `.env.*`, and credential/secret/token/key material using the 022 source-code carve-out so ordinary source files such as `token_counter.py` are not classified as secrets merely by their names.

079 may continue to refuse a broader set. 022 may retain its current workflow-bootstrap exception only where its own accepted policy permits it. 141 has **no** model-driven exception for the shared baseline.

## First-push boundary

Readiness resolves the parked absent-remote-ref ambiguity by **not granting remote branch creation in 141 MVP**.

`push_branch` is admitted only when the target non-default branch already exists on the approved GitHub HTTPS remote and has a concrete 40-character `expected_remote_head`. An absent remote branch returns typed `REMOTE_BRANCH_ABSENT` with no credentialed push. Creating/publishing a new remote branch remains outside 141 and may use an already-authorized GitHub/control-plane path.

This preserves a single-value CAS contract and directly supports the first dogfood target (#559), whose PR branch already exists remotely. The optional host activation smoke must therefore create or seed its disposable remote branch through a non-141 authorized path before exercising the 141 guarded push.

## Local state and Windows credential adapter

The worker state root is OS-user-private and outside registered repositories. MVP layout is the full-spec `worker.json`, atomically replaced `registry.json`, `locks/`, `audit.jsonl`, and an empty trusted hooks directory. The worker must fail closed if permissions/ownership or path identity cannot be proven. State is development-plane evidence only and never STATUS or product authority.

First supported host is **Windows current-user**. Credential acquisition is delegated to an existing **Git Credential Manager** installation used by controlled HTTPS GitHub Git operations. The model/request protocol cannot select or rewrite helpers. Readiness does not authorize GitHub CLI token export, PAT files, SSH keys, a new credential database, or returning helper payloads. If the approved GCM executable/config cannot be identified fail-closed, local push is `LOCAL_CREDENTIAL_UNAVAILABLE` while all non-local lanes remain operational.

Audit remains secret-free. Implementation must include bounded size/rotation behavior: rotate `audit.jsonl` before it exceeds 10 MiB, retain at most five rotated local files, and perform rotation only inside the worker-private state directory. Rotation is local evidence housekeeping and cannot delete repository/GitHub evidence.

## Deterministic test mapping

### `backend/tests/test_local_worktree_actuator.py`

- zero workers online leaves mocked non-local GitHub/CI/review/browser-proof capabilities available;
- one worker offline does not poison another worker/cloud lane;
- wrong-worker dirty/persistent continuation refuses;
- reconnect preserves worktree/local commit metadata and forces remote reread before push admission;
- wrong repository/common-dir/branch/HEAD binding refuses;
- `master`, `main`, configured default/protected branch write paths refuse;
- traversal, symlink and platform-conditional junction/reparse/case-normalization escape refuse;
- reviewer write/stage/commit/push refuses;
- second writer refuses; interrupted writer recovery preserves dirty state;
- unknown named profile and caller-provided argv/env/cwd refuse; no shell/PTTY request surface exists;
- persisted local commit survives requester/session-loss plus worker restart;
- admitted and refused authority-bearing operations both produce reconstructable redacted audit records;
- audit rotation remains inside the private state root and honors the bounded retention contract.

### `backend/tests/test_repository_delivery.py`

- common sensitive paths and protected control tests return `SENSITIVE_PATH_REFUSED` before stage/commit/push;
- pre-existing local commit containing a sensitive delta is independently refused before credential/network mutation;
- source-code secret-name carve-out is deterministic and 079 may layer stricter policy without changing baseline semantics;
- repository/local hooks cannot execute; unapproved credential-helper override refuses;
- URL rewrite, proxy, push-url, SSH command and external filter/process configuration cannot redirect execution/network/credentials;
- unregistered, non-HTTPS or non-GitHub remote refuses;
- child environment is scrubbed and credential sentinel never reaches response/log/audit/error output;
- explicit staged diff produces exact local commit SHA;
- absent remote target returns `REMOTE_BRANCH_ABSENT` with no push;
- stale `expected_remote_head` performs no push;
- pre-read→push remote movement fails ordinarily with no force path;
- force/force-with-lease/delete/merge/default-branch operations are structurally absent/refused;
- successful push is success only after exact remote SHA reread equals intended local commit;
- local/no-op commit is never remote-verified;
- ambiguous result resolves only as full-spec rules permit: intended remote = verified; unchanged expected remote = fresh re-admission required; third-party head = refusal;
- architecture assertion fails if an accepted 141 path introduces a second ordinary Git push implementation outside the shared primitive.

### Existing 022/079 regression tests

Run the existing focused tests for Codex autopush and scheduled continuation. They must prove the factorization does not weaken their current workflow-sensitive paths, no-automerge boundary, candidate/marker/OIDC semantics, or credential separation.

CI uses temporary repositories/bare remotes and no live provider or GitHub credential call. Windows junction/reparse coverage may use a Windows CI lane or a deterministic platform adapter test; actual GCM presence remains host-only activation evidence.

## LOCAL CAPABILITY ACTIVATION smoke

After repository implementation is merged, optional Windows activation is:

1. start worker as the maintainer's ordinary user;
2. enroll one allowed JarvisOS repository/worktree root through the maintainer-only activation path;
3. prove the approved GCM adapter is available without printing credentials;
4. health + read-only status;
5. seed a disposable remote non-default branch using a non-141 authorized path, attach/create the local worktree, create a local commit, guarded-push against its concrete expected remote SHA, then prove exact post-push SHA;
6. stop the worker and prove non-local GitHub/Actions/review/browser-proof lanes remain unaffected;
7. restart and prove durable metadata plus fresh remote revalidation.

Failure of any host-only step disables only the affected local capability. It is never a global roadmap blocker.

## Minimum-necessary / authority proof

- 141 needs a tiny host-local registry/audit owner because local work must survive requesting-model/product-runtime loss; placing this state in product SQLite would couple an optional development plane to product authority.
- The shared Git mutation primitive prevents a second CAS/push policy stack and preserves environment-specific credentials behind separate adapters.
- No dependency on 125 or 126 exists; unrestricted terminal/process and self-update remain unavailable.
- No browser-proof implementation or future spec identity is assumed by 141.
- No second credential store exists: Windows MVP uses OS-owned GCM only.
- With zero local workers, non-local control/evidence lanes remain available by contract and test.

## Readiness result

The bounded implementation above is sufficient to address the observed local-work-loss/delivery failure family without granting broad local-computer authority. Remaining workstation enrollment/GCM proof is explicitly **LOCAL CAPABILITY ACTIVATION** after repository implementation, not a prerequisite for cloud-side Stage 2.

Once this readiness artifact and the matching `STATUS.md: 141 -> ready` transition are accepted on one exact head, implementation may begin. Any need discovered during implementation for arbitrary PTY/filesystem/process authority, worker self-update, remote desktop, remote branch creation, general credential storage, or product/domain authority invalidates this readiness and requires separate authority.
