# Spec 079 readiness decision — 2026-08-01

## Decision

Spec 079 is ready for its minimal implementation after merge of this decision and the superseding full specification.

The accepted implementation is one scheduled GitHub Actions workflow plus one deterministic Python script. Authority and idempotency use only `STATUS.md`, the existing PR, its branch and exact head, commit history, workflow history and a PR comment marker.

## Test del minimo necessario

### Test del minimo necessario
Criterio di accettazione della spec:
Una sessione interrotta riprende da sola sullo stesso ramo e sulla stessa spec senza un nuovo maintainer message.

Questo lavoro serve a soddisfarlo?           sì
Il criterio è raggiungibile senza di esso?   no — un trigger futuro è necessario.
Il criterio è raggiungibile con meno?         no — un solo workflow giornaliero è già il meccanismo minimo.

## Decisions

1. Use `schedule` once per day plus `workflow_dispatch` for proof and diagnosis.
2. Use one repository-wide concurrency group with `cancel-in-progress: false`.
3. Continue only a single existing `in_review` implementation PR; v0 does not invent pre-PR state.
4. Bind every request to the exact current PR head.
5. Store idempotency only as an immutable marker in the PR conversation.
6. Use the existing Actions `GITHUB_TOKEN`; add no secret or personal token.
7. Keep review/fix/re-review outside 079 in planned spec 080.
8. Keep prior CAS and bare-Git proof as historical evidence only.

## Rejected as unnecessary

- GitHub App;
- service or daemon;
- PostgreSQL, Redis or queue;
- `jarvis-control` branch or authority JSON;
- claims and leases;
- separate proof repository;
- webhook, ruleset, token-revocation and permission-abuse programs;
- spend ledger and provider reservation state.

These mechanisms may be reconsidered only if a later acceptance criterion cannot be met with existing GitHub state.

## Readiness gates

- full spec 079 contains a closed workflow, discovery, idempotency and fail-closed contract;
- 080 exists as a separate planning kernel;
- implementation adds no dependency, credential, account, database or runtime service;
- tests are offline and make no provider call;
- rollback is deletion of one workflow and one script;
- implementation PR must update the registry to `in_review` and pass full CI.

## Remaining uncertainty

OpenAI documents that a PR comment can ask Codex to work in the PR context, but the implementation does not assume that CI can validate a real provider response. The deterministic acceptance proof is the scheduled control action, exact-head binding and one-shot request. Actual model execution remains external and advisory.
