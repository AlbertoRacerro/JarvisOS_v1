# Spec 079 readiness decision — 2026-08-01

## Decision

Spec 079 is ready for the minimal scheduled-continuation implementation defined in `079-autonomous-development-loop-0.md`.

The accepted mechanism is one daily GitHub Actions workflow plus one standard-library Python control script. It reuses the repository's installed `anthropics/claude-code-action@v1` integration and existing `CLAUDE_CODE_OAUTH_TOKEN`.

## Minimum-necessary result

### Test del minimo necessario
Acceptance criterion of the specification:
An interrupted implementation session resumes on the same branch and specification without a new maintainer message.

Does this work satisfy it?                   yes
Can the criterion be met without it?         no — a future trigger and an invokable agent are both required.
Can it be met with less infrastructure?      no — the existing Claude action, one daily workflow, one script, and existing GitHub state are sufficient.

## Binding decisions

1. Use `schedule` once per day plus `workflow_dispatch`.
2. Use repository-wide concurrency with `cancel-in-progress: false`.
3. Use modes `OFF`, `SHADOW`, and `EXECUTE_NO_MERGE`; absent mode means `OFF`.
4. Discover active state by enumerating open PRs and reading `STATUS.md` from each exact PR head.
5. Continue only one same-repository `in_review` implementation PR.
6. Bind every action to the exact head and prior output checkpoint.
7. Invoke Claude only in a read-only job without a write credential.
8. Treat Claude output as an untrusted patch; a separate job validates, runs all gates, rereads the exact head, and alone may push.
9. Store idempotency only in PR checkpoint markers and Git ancestry.
10. Keep review/fix/re-review in separate planned spec 080.
11. Do not assume `GITHUB_TOKEN` pushes trigger CI; run gates before push.
12. Never merge from the continuation workflow.

## Existing secret evidence

`.github/workflows/claude-review.yml` already names and uses `CLAUDE_CODE_OAUTH_TOKEN` with the official action. GitHub APIs do not reveal secret values or expiry. The workflow therefore checks non-empty presence without disclosure; actual validity is exercised only in `EXECUTE_NO_MERGE` and is not tested by making a provider call.

This uncertainty does not block implementation or `SHADOW`, because default `OFF` and `SHADOW` invoke no provider. If the first execute run reports authentication failure, refreshing the existing secret is the bounded credential remedy.

## Rejected as unnecessary

- new repository or organization;
- GitHub App or webhook service;
- PostgreSQL, Redis, or queue;
- `jarvis-control` branch or authority JSON;
- compare-and-swap authority ledger, claim, or lease;
- ruleset, branch-protection, permission-abuse, and token-revocation laboratories;
- new provider account or credential;
- spend ledger or provider reservation state.

The previous CAS and bare-Git work remains historical evidence only.

## Readiness gates

- 079 contains a closed contract for modes, discovery, exact-head binding, idempotency, patch validation, gates, push, and rollback;
- 080 exists separately and remains `planned`;
- implementation adds no dependency, account, credential, repository, database, or runtime service;
- tests are offline and invoke no provider;
- the implementation PR records 079 as `in_review` and links itself;
- full CI and current review findings must be green/closed before merge.

## Promotion boundary

This decision authorizes implementation and merge under the permanent operating regime. It does not change `JARVISOS_CONTINUATION_MODE`, dispatch Claude, test a live provider, implement spec 080, or authorize merge from the scheduled workflow.
