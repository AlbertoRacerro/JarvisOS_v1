# 139 RUNNER-STRANDED-RECOVERY-1 — readiness decision

Decision: READY

Exact-master basis: `6e1d369d936935174d2384c391ee18da5c5ea6df`

## Fresh evidence

The current runner still persists a `running` claim independently from the lifetime of the separate Python child created by `backend/app/modules/runner/local_python.py::execute_python_script`. An abrupt server-process failure can therefore leave a persisted running pair without enough durable evidence to distinguish a dead execution from a still-live orphan child.

Prior F8 analysis that proposed unconditional startup reconciliation is superseded by the bounded child-ownership finding: startup, reload, or acquisition of a backend/data-root lock alone is not abandonment proof. The implementation must first establish the minimum runner-specific child ownership/liveness evidence and only then perform idempotent recovery when ownership is conclusively gone.

## Readiness checks

- Scope is closed to the existing local Python runner's stranded-running failure mode.
- The implementation must preserve live work and prove the live-child versus abandoned-child distinction.
- Recovery is exactly-once/idempotent and preserves artifacts, logs, rows and events.
- Queued/succeeded/failed state is untouched; inconsistent pairs fail closed.
- Normal supported reload and a second launcher are explicitly negative fixtures: neither may terminalize live work merely because a startup path executed.
- A schema/migration addition is permitted only if it is demonstrably the smallest way to persist execution ownership safely; generic leases, heartbeats, distributed locks and process-supervisor frameworks remain out of scope.
- The final startup/reconciliation hook must be placed only after the ownership precondition is proven; bootstrap-only placement is not accepted by itself.
- Required implementation evidence includes focused real-process/liveness tests, focused recovery/startup tests, normal CI, and independent exact-head semantic review.

## Decision

READY once the canonical registry row for 139 is `ready`. Implementation must use the smallest runner-specific ownership/liveness mechanism that satisfies the frozen acceptance matrix in spec 139; any broader scheduler, lease, heartbeat, process-supervision, BLUECAD, calc-runner, or Coding scope requires fresh authority.
