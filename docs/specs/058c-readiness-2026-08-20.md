# 058c — SCENE-SEMANTICS-A1 readiness

Date: 2026-08-20  
Base master: `f000cb96384701f72b870c81949bc551bd4b74df`  
Definition: `docs/specs/058c-scene-semantics-a1-rederived.md`  
Decision: **ready after merge + registry reconciliation only**

## 1. Readiness decision

The post-092 runtime can support one bounded 058c implementation without a new durable store, provider path, scene authority, general recomputation engine, or broad backend semantic service.

The minimum implementation is an additive **schema-v3 model input contract semantic envelope** carried through the existing model-implementation read path, plus a bounded extension of the existing 071b `EngineeringProperties` controller so the selected 092 `bluecad-part` context can filter/render object-applicable engineering semantics while preserving inactive implementation values inside the same transient working-state owner.

The implementation must remain truthful where current authority is absent:

- existing schema-v1/v2 model implementations remain valid generic model contracts and do not acquire invented object semantics;
- current runtime has no authoritative inspectable equation/output semantic contract, so 058c V0 must **not invent `fx` formulas or derived-value evidence**; `fx` appears only when future accepted authority supplies explicit formula/output metadata;
- current runtime has no persisted set of simultaneously active mutually-exclusive engineering models. The UI already has one selected model implementation ID, so V0 must not create a fake legacy multi-active state model merely to satisfy a theoretical case;
- current BLUECAD manifest gives stable selected `part_id`, `part_kind`, volume/bounds/ports evidence but not authoritative original design dimensions such as nominal length/diameter for every part kind. V0 therefore does not reverse-engineer dimensions from bounds or mesh geometry.

These limits are deliberate minimum-necessary decisions, not missing acceptance.

## 2. Exact runtime findings

### 2.1 Scene target authority is sufficient

Merged 092 publishes a `StageSelection` of kind `bluecad-part` containing:

- `workspaceId`;
- `candidateId`;
- exact GLB `artifactId`;
- `viewerSessionId`;
- ephemeral mesh key;
- exporter semantic key;
- canonical `partId`;
- manifest-derived `partKind` when present.

The resolution path is fail-closed through candidate-owned manifest artifacts and exact GLB digest. Renderer order, raw names, material, colour and bounds are not accepted as identity.

058c must consume this target as read context only. It does not modify 092.

### 2.2 071b is the sole working-state owner

`frontend/src/components/engineering/EngineeringProperties.tsx` currently owns:

- selected model implementation ID;
- baseline bindings;
- working bindings;
- revision;
- bounded Undo stack;
- field/revert-all operations;
- deterministic preview/preflight;
- run request identity/retry reconciliation;
- successful-run baseline adoption.

Changing the selected implementation currently resets baseline/working bindings to empty. Therefore inactive-model value retention is **not yet present**, but it can be added inside this same controller without creating a second store.

### 2.3 Current input contracts are not object-semantic

`backend/app/modules/runner/input_contracts.py` currently supports schema v1/v2.

Current variable authority includes:

- stable name;
- human label;
- exact unit;
- required flag;
- broad category (`design`, `operating`, `property`, `model_parameter`, `equipment`);
- description;
- optional numeric domain;
- v2 physical dimension and semantic basis.

This is enough for generic 071b editing and deterministic validation, but not enough to claim:

- applicability to a selected BLUECAD part kind;
- a mutually-exclusive engineering model family;
- an engineering option label separate from implementation/version identity;
- more specific object-facing property grouping.

No frontend inference from variable names, units, labels, implementation kind or script path is permitted.

### 2.4 Current model implementation records have no semantic family authority

`ModelImplementationRead` exposes model/spec identity, version/implementation identity, script evidence and input contract. It has no canonical field representing an engineering model-choice family or selected-object applicability.

Adding a second SQL table or dedicated semantic service is unnecessary: the existing canonicalized input-contract JSON is already versioned, hashed, validated and returned with each model implementation.

### 2.5 Current formula/output authority is insufficient

Current model input contracts describe inputs and numeric domains. `SimulationRun` / runner responses may contain arbitrary output JSON, but there is no accepted server-owned output semantic schema tying an output key to:

- human engineering property identity;
- declared equation;
- formula inputs;
- result unit;
- validity/domain evidence.

Model script text/hash is Audit evidence, not an inspectable equation contract. 058c V0 therefore must not derive formulas from Python source or output-key naming.

### 2.6 Existing parameter links are real source authority

071b bindings can reference an existing Parameter by `source_parameter_id`. Parameter records already expose name, value, unit, value status and source reference. V0 may present a parameter link as a real linked source without copying the parameter into a scene-owned record.

The operator-facing source label must remain conservative. A working manual value may be labelled `Working override`; a parameter-backed value may be labelled `Linked parameter` with the parameter's actual `value_status` shown as secondary provenance. Do not relabel arbitrary parameters as `Measured`, `User` or `Validated` unless their stored authority proves that claim.

## 3. Minimum schema-v3 contract

Add schema version 3 as an additive extension of schema-v2 numeric/unit semantics. Schema v1/v2 bytes and validation behavior remain unchanged.

The exact V3 semantic shape is:

```json
{
  "schema_version": 3,
  "evaluation_mode": "forward",
  "semantic_context": {
    "applicable_part_kinds": ["tube"],
    "model_family_key": "pressure_drop",
    "model_family_label": "Pressure drop model",
    "model_option_label": "Ergun equation"
  },
  "variables": [
    {
      "name": "void_fraction",
      "label": "Void fraction",
      "unit": "1",
      "required": true,
      "category": "model_parameter",
      "property_group": "Hydraulics",
      "description": "...",
      "physical_dimension": "dimensionless"
    }
  ]
}
```

### 3.1 Validation rules

`semantic_context` is required for schema v3.

- `applicable_part_kinds`: 1–16 unique non-empty stable identifiers; exact string match against authoritative 092 `partKind`; no substring/fuzzy matching.
- `model_family_key`: stable machine identifier, bounded to the same conservative identifier discipline as variable names.
- `model_family_label`: non-empty human label, bounded length, no edge whitespace.
- `model_option_label`: non-empty human option label, bounded length, no edge whitespace.
- `property_group`: non-empty bounded human label on every v3 variable; no frontend mapping from variable name/category.
- v3 retains v2 unit normalization, `physical_dimension`, optional `semantic_basis`, requiredness and domain validation unchanged.
- duplicate variable names remain invalid.
- malformed semantic metadata makes the stored v3 contract invalid/fail-closed.

This contract carries presentation/selection semantics only. It does not add formulas, output schemas, executable expressions, scripts or arbitrary frontend markup.

## 4. Object applicability and model-choice semantics

### 4.1 When a 092 part is selected

For a resolved `bluecad-part` target:

- implementations with valid schema-v3 contracts whose `applicable_part_kinds` contain the exact current `partKind` are object-applicable semantic implementations;
- v1/v2 implementations and non-matching v3 implementations remain valid global/generic implementations but are **not presented as object-specific models**;
- no `partKind` or unsupported kind => object semantics are limited/unresolved, while generic 071b model configuration remains usable.

The UI must not hide or destroy the generic 071b run capability merely because the selected part lacks semantic metadata. When no object-applicable v3 contract exists, show the selected object identity truthfully and retain the generic model editor under a clearly separate label such as `General model configuration — not bound to selected object`.

### 4.2 Mutually exclusive model family

A set of object-applicable v3 implementations with the same `model_family_key` is one mutually-exclusive model choice. `model_family_label` must agree across options in that family; disagreement is invalid semantic metadata and the family fails closed.

Normal valid state has one selected implementation ID. The current 071b `selectedId` remains the active choice token; no second persisted active-model field is added.

If two different semantic families are applicable to one object, V0 may render them as separate family selectors only if the implementation can do so without creating multiple simultaneous runner model identities. Because the current runner executes exactly one `model_version_id`, the initial implementation must support **one active semantic family at a time** and must not pretend independent families compose into one run. Additional compositional-model authority is deferred.

No AI automatic model selection is authorized.

### 4.3 Inactive value retention

Extend the existing 071b controller with a transient per-implementation binding cache keyed by exact model implementation ID.

Required behavior:

- A → B stores A's current binding map before activating B;
- B → A restores A's prior binding map;
- the active implementation's bindings remain the only effective values submitted to preflight/run;
- inactive cached bindings never enter normalized input or execution;
- Undo/Revert operate on the active implementation and preserve the existing single controller ownership;
- switching implementation increments the same working revision and invalidates stale preflight;
- a successful run updates the baseline only for the active implementation snapshot;
- cache lifetime remains the existing in-memory working-session lifetime; no SQL/localStorage persistence is added;
- workspace change clears incompatible cached working state.

This is the minimum way to satisfy inactive-value retention without a second state store.

## 5. Property groups and source semantics

For a matching schema-v3 contract, Properties renders variables by authoritative `property_group`.

Each row reuses existing input-contract / preview authority for:

- label;
- effective working value;
- exact unit;
- required/optional state;
- domain validation;
- blocker state;
- editability.

Source display is derived only from explicit working binding state:

- non-empty manual working value with no parameter reference: `Working override`;
- parameter-backed value: `Linked parameter` plus the actual parameter identity/value-status/source-ref in Inspect;
- empty: `Empty`.

No v3 field claims CAD, Measured, Material DB, Previous run or Jarvis provenance unless a later accepted contract supplies that source explicitly.

The selected BLUECAD object header may show canonical `partId`/`partKind` as object identity. Current manifest volume/bounds/ports remain existing scene/CAD evidence and are not reverse-engineered into editable nominal geometry fields.

## 6. Derived values and `fx`

Implementation-now: **no new derived-property output contract and no formula parser/rendering authority**.

Reason: exact runtime contains no accepted formula/output semantic contract. Adding one solely to populate an unused `fx` panel would be speculative infrastructure and violates minimum-necessary/YAGNI.

Required V0 behavior:

- do not show `fx` on ordinary input variables merely because they have a numeric domain or model implementation;
- do not parse Python script text to extract equations;
- do not infer formulas from output JSON keys;
- do not present input-contract hashes/version IDs as engineering formulas;
- if a selected object/model has no authoritative derived semantics, show no derived/formula section or explicitly state `Formula semantics unavailable for this model` only where useful.

The 058c definition's formula contract remains the downstream compatibility boundary. A future real model/output authority may extend the semantic contract through a separate accepted spec/readiness decision.

## 7. Linked source behavior

V0 supports the linked source already proven by 071b: Parameter.

- parameter-backed values remain owned by the Parameter record;
- Properties reads the linked parameter's actual value/unit/status through the existing list/read data already loaded by the controller;
- manual editing a parameter-backed row converts the working binding to a working override exactly as current 071b behavior does;
- no duplicate parameter is created;
- stale/missing parameter references remain invalid through existing deterministic preview;
- source IDs stay secondary/Inspect.

No process-stream/CAD-to-model automatic value link is invented in this slice. Those labels appear only when a separate existing backend relation can be proven in a later accepted contract.

## 8. Scene and stale-safety integration

The 058c semantic rendering decision is bound to:

- current workspace ID;
- current `bluecad-part` selection;
- candidate ID;
- artifact ID;
- viewer session ID;
- semantic key;
- canonical `partId`;
- current selected implementation ID;
- current working revision.

No new asynchronous backend semantic fetch is required in V0 because semantic metadata arrives through the existing model-implementation list and selection already arrives through 092. Therefore the primary stale risk is React state crossing workspace/scene/model changes.

Required behavior:

- workspace change clears semantic applicability and per-implementation cache before new model data is accepted;
- unresolved/ambiguous/resolving scene selection is not an editable object semantic target;
- candidate/artifact/viewer-session change immediately invalidates the prior object semantic presentation;
- switching model invalidates preview through the existing revision/model guards;
- no stale model list from another workspace may populate the current object selection;
- no selection interaction invokes provider, Jarvis mutation or execution.

## 9. Legacy and migration decision

No SQLite migration is authorized or required.

- Existing model implementation rows keep canonical schema-v1/v2 input contracts unchanged.
- New/updated model implementations may use schema v3 through the existing `input_contract_json` storage path.
- Existing v1/v2 models remain usable in generic 071b mode.
- Existing BLUECAD candidates/manifests remain usable; 092 identity is unchanged.
- Unknown future input-contract schema versions remain rejected by existing fail-closed parsing.

Rollback is bounded: removing v3 semantic rendering leaves schema-v1/v2 generic 071b editing and merged 092 scene binding usable. V3 parsing itself must remain backward-compatible if v3 rows have been created.

## 10. Exact implementation allow-list

Implementation may touch only the minimum paths below unless a concrete failing gate proves one additional path necessary and the PR documents why.

Backend:

- `backend/app/modules/runner/input_contracts.py` — additive schema-v3 semantic validation/canonicalization;
- focused tests for v1/v2 byte stability, v3 validation, malformed/family metadata and preview compatibility.

Frontend:

- `frontend/src/api/client.ts` — additive schema-v3 types only;
- `frontend/src/App.tsx` and/or existing sidecar composition only as needed to pass the current `StageSelection` into Properties;
- `frontend/src/components/engineering/EngineeringProperties.tsx` — object applicability/grouping, active-family presentation, per-implementation inactive-binding retention, conservative source rendering and same-owner stale handling;
- `frontend/src/components/shell/ContextualSidecar.tsx` only if the selection prop must pass through the already-existing sidecar seam.

Tests/evidence:

- focused backend semantic-contract tests;
- the smallest existing frontend/source-contract checker or new focused offline source-contract test needed to prove ownership/no-inference invariants;
- evidence-only browser harness artifacts when needed for the browser matrix.

Do **not** modify 092 scene-binding/export logic unless an actual regression proves a defect there. Do not add a database table, migration, semantic endpoint, provider route, frontend state framework, formula parser, expression evaluator, output-schema engine or new package.

## 11. Deterministic acceptance

Exact-head implementation tests must prove at least:

1. schema-v1 and v2 canonicalization/validation remain unchanged;
2. valid v3 semantic contract canonicalizes deterministically and retains v2 unit/domain semantics;
3. malformed/duplicate/empty semantic applicability/family/group fields fail closed;
4. v3 part applicability is exact, never fuzzy/label/mesh based;
5. v1/v2 implementations do not become object-specific by frontend inference;
6. only the active implementation's bindings enter preview/run payload;
7. A → B → A restores A's transient working values;
8. workspace change clears cached model working values from the old workspace;
9. model switch increments/invalidate working revision/preflight and an old normalized input set cannot execute;
10. parameter-backed values remain source-owned and missing/stale references remain invalid through existing preview authority;
11. required empty vs optional empty behavior remains 071b-compatible;
12. unsupported selected object/model yields truthful limited semantics while generic 071b configuration remains usable;
13. no `fx`/formula content is fabricated from script/hash/output names;
14. semantic selection/model interactions create no provider dispatch, Jarvis mutation or run;
15. removal of the frontend semantic layer leaves generic 071b Properties and merged 092 scene binding usable.

## 12. Browser acceptance matrix

Run on the final implementation head with real app/browser evidence where the harness permits:

1. no scene selection: generic 071b Properties remains usable;
2. resolving/unresolved/ambiguous 092 selection: no editable object-semantic claim;
3. resolved part + matching v3 model: object header + authoritative property groups only;
4. resolved part + no matching v3 model: identified object plus clearly separated generic model configuration;
5. two v3 options in one family: selector uses human family/option labels and exactly one implementation is effective;
6. edit A, switch B, edit B, switch A: A values return; preflight shows only A inputs;
7. candidate/viewer-session switch: old object semantic context disappears before new editing;
8. workspace switch: old model/object cache cannot leak into new workspace;
9. linked parameter: source is visibly linked, actual value-status remains truthful, editing creates working override rather than mutating the parameter;
10. required empty is blocker; optional empty neutral; inactive implementation fields absent from effective payload;
11. malformed/unsupported semantic contract fails to generic/limited presentation, not a crash or guessed grouping;
12. no formula metadata: no fake `fx` equation appears;
13. effective 200%/compact width preserves existing `Jarvis | Properties` behavior and internal scrolling;
14. keyboard navigation reaches model selector, fields, Undo/Revert and blocker navigation; focus remains predictable across model switches;
15. long labels/group names/parameter provenance wrap/contain without page-level horizontal overflow;
16. light/dark/system and reduced-motion invariants remain intact.

## 13. Prepared but not implemented

This readiness deliberately leaves the following prepared by the definition but not implemented in V0 because exact runtime lacks authority:

- authoritative derived-output/formula/`fx` contract;
- process-stream automatic links;
- CAD nominal design-parameter editing from a selected part;
- compositional simultaneous model families in one runner execution;
- persistent working drafts across application restart;
- previous-run baseline loading (006b);
- Jarvis engineering mutations (097);
- lifecycle mutation (098);
- variant comparison (058b).

These deferrals must not be represented as current capability.
