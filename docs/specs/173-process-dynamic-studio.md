## Decision

1. **Frontend first over the 172 API.** Reads and edits use the routes and ops above. There is no second store, no new run route, no new engine path. Limits stay as they are (120 days, 20000 points, 1000 events, 16 controllers).
2. **One additive read.** The draft projection gains an optional `dynamic: {scenarios, schedules, controllers}` holding the stored typed content, present only when the draft has any, so a draft without them keeps a byte-identical projection. This is a read of data the caller can already patch. It adds no authority, op or route.
3. **Editor surface.** A "Dynamic" panel in the Process stage, in new files under `frontend/src/components/dynamic/` with pure logic in `dynamicLogic.ts` (the test target). Scenario form, schedule timeline, controller editor, run list, results view, comparison. Every save is a `patchDraft` with the three set/delete ops. A refusal shows the backend code and message and changes nothing. Values are never clipped or corrected client-side.
4. **Scenario form.** Fields are those of `Scenario`: units, environment profile, schedule, controllers, UTC start and end, output and controller cadence, temperature source, solver, tolerances, downstream flag and cadence, and initial state. Fidelity is shown as the fixed `T1`. Duration, point count and cadence limits are shown next to the fields, and the server verdict stays authoritative.
5. **Schedule timeline.** Events appear in time order, on a to-scale axis and in an equivalent table. All six event types are editable, and the five culture actions edit as in 191. Recurrence (`every_s`, `count`, `end_s`) and state conditions use the existing fields and exclusions. The timeline shows expanded repeats read-only.
6. **Plain-language descriptions.** A pure function turns each typed event into a sentence, for example "Every 2 d from day 1, draw 20 % of the loop from tank T1, until day 30." and "When loop_N falls below 0.05 kg/m3 (0.01 hysteresis, 1 h cooldown), dose 0.4 kg N into T1, at most 3 times." The same applies to controllers ("PI keeps X at 0.8 kg/m3 by feed flow, every 5 min, output 0 to 2e-5 m3/s"). Output depends only on the typed value and the units shown. Unknown future fields render as raw JSON, never as a guess.
7. **Controller editor.** Edits `onoff`, `pi` and `turbidostat` as the model allows: measurement, actuator (`feed:<stream>` or `splitter:<tag>`), cadence, setpoint, bounds, hysteresis, gains, direction. The 172 rules apply and the host refuses the rest. There is no new controller type and no pH, CO2 or thermal actuator (175).
8. **Procedure link (191).** Schedules with a Studio link show its badge: version, "modified" or current. The editor may change a linked schedule only after a confirmation that names the consequence. The save is the normal `set_schedule`, and the link then reads "modified, no longer the pinned procedure" by 191's rule. The editor never rewrites or removes a link, never publishes, and Apply and "Update to vN" stay in Studio. Runs of linked schedules show their link next to the run.
9. **Run and results.** Start posts `{scenario_id}` and polls status and progress. Cancel uses the cancel route. A terminal run shows status, error code, manifest identity, fidelity label, per-unit model-card qualification, profile digests, wall time. Synchronized time-series views use uPlot, share one cursor and x-range, group channels by unit from `manifest.channels`, and never hide a channel's unit. Each view has a values table and keyboard range control. Large runs page the series in `start_s`/`end_s` windows of at most 5000 points and say when a view is strided.
10. **KPIs only from existing data.** Cards come from the manifest and series: final and mean biomass per unit, cumulative harvest (`harvest_X_kg`), event and controller fire counts, the 185 `campaign` KPIs when present, and volumetric or areal productivity only where the manifest reports it. Anything absent shows "not available" with its reason. No new KPI is computed from assumed inputs.
11. **Chips.** Balance: aggregate `residual_rel` against the engine tolerance and `balances.asserted`. Event balances: closed count over the event log. Convergence: job status, `downstream_outcomes` converged and `downstream_unconverged` counts with the recorded residual, and "no downstream" when none was requested. A failed run shows its code and its partial data labelled as partial.
12. **Staleness.** A run is **stale** when `status.current === false`, which is exactly a differing draft content digest and therefore covers any scenario, schedule, controller or unit edit and ignores layout. `current === null` reads "not bound". A stale run keeps its plots and is labelled with the run's revision against the head. The editor offers re-run and never reruns automatically. The `current` flag does not cover a changed profile or model card, since only the engine can recompute `snapshot_digest`. The view lists the profile and card digests the run used and does not claim they are unchanged. Start fails closed on a changed profile or card through `prepare`.
13. **CSV, client side.** Export builds the file in the browser from the series read, paging until `total_points` rows are held, with a header row of channel name and unit and a comment line with job id, `snapshot_digest`, fidelity and the "Unqualified" notice. A strided or truncated export is refused rather than silent. No server file is made.
14. **Run comparison, client side.** Up to 4 runs of one draft, each at its own scenario and revision. Overlays align on elapsed `t_s`, share only channels whose units match, label each trace by run, scenario and stale state, and show a table of KPI differences against a chosen baseline. A run with a different channel set shows the missing channels as absent. Nothing is interpolated across runs.
15. **Replaces the 191 results panel.** The bench keeps Apply, Update and Run for procedures and renders results with the shared results view, so there is one chart owner. Its hand-built SVG chart is removed. The 191 notice and tests stay.
16. **Honest limits on screen.** "Tier 1 lumped model. Unqualified. Simulation only. This does not command any equipment." appears on the editor, results and comparison.

No security boundary changes. No new route, op, actuator, user code or provider call. The only server change is the additive read in decision 2.

## Acceptance

1. **Golden workflow, real Chromium.** An operator using the GUI only: creates a scenario on a PBR draft with a profile; defines a schedule with a recurring draw and a conditioned dose and a controller; runs it; inspects the synchronized plots, KPI cards and chips; edits one schedule event, sees the earlier run marked stale and the editor save a new draft revision; re-runs; compares the two runs; exports CSV; applies a 191 procedure schedule and edits it by hand to see "modified". A keyboard-only pass covers the timeline, the plots' range control and the comparison, and each plot has its table fallback. The workflow fails if any step needs a terminal, hand-written JSON or a backend edit beyond decision 2.
2. **Descriptions.** Table-driven tests: each event type, recurrence form, condition, action and controller type maps to the expected sentence, and a sample covers every `ScheduleEvent` field.
3. **Staleness.** Backend-backed tests: editing a schedule, a scenario or a controller makes `current` false. A layout move keeps it true. The UI mirrors both.
4. **Series and CSV.** A run above 5000 points exports every row, matches the artifact series to the stored `.npz` values, and carries units in the header. A strided request is flagged.
5. **Comparison.** Two runs that differ in one schedule parameter show the expected KPI deltas. Mismatched units are not overlaid. More than 4 runs are refused.
6. **Link behaviour.** Editing a Studio-linked schedule asks for confirmation and then marks the link modified. The editor never writes a link.
7. **Projection compatibility.** A draft with no dynamic content has a byte-identical projection and snapshot digest. The 172, 185, 186, 188 and 191 suites pass without edits.
8. **Refusals.** A bounded-violating cadence, an unknown tank, an unobservable condition and a missing schedule reference show their backend codes and leave the draft revision unchanged.

- No change to engine limits, series caps, run states or artifacts. No server-side comparison, CSV or stale authority.
- No automatic re-run, no run promotion, no parameter or card promotion.
- No procedure authoring, publishing or Apply (191 and Studio).
