# 006b — PARAMETRIC-VARIANTS-1 readiness

Date: 2026-08-24  
Definition authority: `docs/specs/006b-parametric-variants-1-rederived.md`, merged through PR #345 as `4181ccadb1c142f20d2f20174ad816b5934bcbd4`

## 1. Decision

006b is implementable without a new backend route, table, schema, durable variant store, provider path, execution path, or second working-state owner.

The minimum V0 is a frontend composition over existing immutable successful-run evidence plus the existing 071b `useEngineeringProperties` owner:

1. Runs detail identifies a persisted successful run.
2. Existing run detail supplies workspace, `model_version_id`, human `run_label`, status and canonical persisted `input_payload`.
3. Existing model-implementation authority supplies the exact model implementation, `input_contract`, and `input_contract_sha256` for that `model_version_id`.
4. The frontend validates exact compatibility fail-closed.
5. The single 071b owner atomically adopts the historical effective values as a new clean working baseline with provenance `Previous successful run`.
6. The existing deterministic preview/preflight reruns against the current exact model contract.
7. No run is created until the operator separately invokes the existing 071b Run action.

The old child-BLUECAD-candidate / GeometrySpec-slider variant design remains superseded and receives no runtime authority.

## 2. Exact runtime findings

### 2.1 Persisted run read model is sufficient

Current `GET /workspaces/{workspace_id}/simulation-runs/{run_id}` already returns `SimulationRunDetail` containing:

- `id`;
- `workspace_id`;
- `model_version_id`;
- `run_label`;
- persisted `status`;
- persisted `input_payload`;
- `parameter_payload`;
- output/timing/notes evidence.

`RunsWorkbench` already fetches that exact detail through `frontend/src/api/runs.ts::getRun(...)` and applies workspace/run generation guards to reject stale detail responses.

Runner creation persists `input_payload` into `simulation_runs` only after the implementation-specific validator has canonicalized the submitted input set. For schema-v2/v3 linked Parameters, merged 098 additionally preserves the immutable `source_parameter_updated_at` token in new normalized snapshots and guards create/final claim against stale/noncurrent sources.

No new read endpoint is necessary for V0 reconstruction.

### 2.2 Model contract authority is already available

`ModelImplementationRead` already exposes:

- exact `id` / model-version identity;
- workspace ownership;
- `input_contract`;
- `input_contract_sha256`;
- version label, implementation kind evidence and script identity.

`useEngineeringProperties` already loads the workspace's model implementations and owns the selected exact model-version id. The V0 therefore requires the historical run's non-null `model_version_id` to resolve to an existing exact model implementation in the same workspace. No fuzzy cross-version compatibility is authorized.

For schema-v3 semantic contracts, model-family/model-option identity comes from that exact matched implementation contract. It is not inferred from run labels or payload field names.

### 2.3 071b is the only mutable owner

`useEngineeringProperties` currently owns:

- selected model version;
- `baseline`;
- `working`;
- working revision;
- Undo/Revert state;
- preview/preflight generations;
- run label/result/pending-run state;
- the single request-key run-start path.

A model change currently resets the binding map. Successful execution adopts the exact submitted working bindings as baseline only when the working revision and selected model still match, while canonical project records remain unchanged.

There is no prior-run load operation today. 006b authorizes one owner-local historical-baseline adoption operation; it does not authorize a second React store/context/reducer for variants.

### 2.4 Runs and Properties already share the App-level owner seam

`App` creates `useEngineeringProperties(...)` above route rendering. `RunsWorkbench` currently receives only workspace props, while the Properties sidecar receives the controller. The minimum integration is therefore to pass one bounded controller callback/state subset from `App` into Runs rather than introducing global variant state.

No route, shell, sidecar, or backend ownership change is required.

## 3. V0 loadability predicate

A run is loadable only when every condition below is true at apply time:

1. run workspace equals the current workspace;
2. run status is exactly `succeeded`;
3. run has a non-null `model_version_id`;
4. that exact model version still resolves in the current workspace's model-implementation read model;
5. the implementation has a valid current input contract already supported by 071b;
6. persisted `input_payload` parses as a JSON object, with no duplicate/ambiguous reconstruction;
7. every persisted input name exists in the matched contract;
8. every persisted item contains a finite numeric `value` and a `unit` exactly equal to the current contract variable unit;
9. no unknown/extra payload input is silently ignored;
10. every currently required contract variable is present in the persisted successful-run snapshot;
11. missing optional contract variables become explicit empty working bindings rather than invented values;
12. schema-v3 model-family/model-option semantics are those of the exact matched implementation and pass the current contract validator;
13. if a current semantic object target is required to represent an object-specific field, the current 092 target must already be authoritative and compatible; the run never fabricates or restores a scene selection from payload data.

The V0 deliberately requires exact model-version identity rather than attempting to prove compatibility across two different model versions. A historical run whose model version no longer resolves remains inspectable but is not loadable.

Error taxonomy presented to the operator should remain small and semantic:

- `Run did not succeed`;
- `Model version is no longer available`;
- `Run snapshot is incomplete`;
- `Run snapshot does not match this model contract`;
- `Units do not match the current contract`;
- `Current engineering target is incompatible`;
- `Working configuration changed before load completed`.

Technical IDs/digests stay Inspect/Audit.

## 4. Historical linked-source rule

A persisted successful run is immutable historical execution evidence. Its effective value must never be silently reinterpreted through a newer canonical source.

Therefore V0 historical load uses the persisted effective `{value, unit}` as a literal previous-run working value and does **not** recreate a live `source_parameter_id` binding, even when the historical normalized item contains `source_parameter_id` / `source_parameter_updated_at`.

This prevents a changed, archived, deleted, or merely newer Parameter from rewriting history during load.

Operator-facing provenance for bindings equal to the loaded baseline is `Previous successful run` with the human run label where available. Inspect/Audit may expose the source run id and the persisted historical source id/revision as evidence, but those identifiers do not grant current live-link authority.

If the operator later wants a live Parameter source, they must explicitly choose that Parameter through the existing 071b source control. That action is a new working edit and is checked against current 098 lifecycle/current-source rules.

No exact-current-source auto-relink optimization is part of V0; avoiding it is the minimum fail-safe behavior.

## 5. Owner-local apply contract

The implementation may extend `EngineeringPropertiesController` with one bounded operation equivalent to:

`loadPreviousSuccessfulRun(snapshot, options)`

The exact function name is not normative. The ownership contract is.

The owner must:

- validate expected workspace/run/model identity again at apply time;
- use a monotonic load generation/precondition so a late response cannot apply over newer state;
- if the historical exact model version differs from the currently selected version, switch through the existing selected-model owner and apply only after that exact implementation/contract is current; a pending load is invalidated by any newer workspace/model/load intent;
- construct one complete `BindingMap` from the matched contract: persisted values become literal previous-run bindings and absent optional values become empty bindings;
- never populate `parameterId` merely because the historical payload carried `source_parameter_id`;
- replace `baseline` and `working` together only after complete validation;
- set a controller-level baseline provenance record containing source run id + human run label, sufficient to render `Previous successful run` without modifying the core canonical record store;
- clear Undo history after an explicitly confirmed dirty replacement; V0 does not promise undo back into the discarded pre-load working configuration;
- clear stale pending-run/result state that cannot truthfully describe the newly loaded baseline, without deleting persisted Runs evidence;
- increment working revision / invalidate old preview generations;
- trigger the existing deterministic preview/preflight for the loaded current contract;
- perform zero canonical record mutation, zero runner create/run call and zero provider/thread call.

`Revert all` after load returns to the loaded previous-run baseline. New edits after load create normal dirty state and enter the existing Undo/Revert behavior.

The existing next-run label input is not auto-renamed. The loaded baseline is identified separately by the source run's `run_label` (or a human fallback such as `Unnamed run`).

## 6. Dirty-state and confirmation behavior

If the current working configuration is dirty when `Load as working configuration` is requested:

- the first request must not mutate working state;
- Runs shows a confirmation that the current unsaved working edits will be replaced;
- cancel leaves every working/preview/run-start field unchanged;
- explicit confirmation retries the same bounded load against fresh preconditions;
- if state changed again between confirmation and apply, fail stale rather than discarding the newer state.

No partial merge, field-by-field conflict resolver, automatic stash, or persistent draft variant is authorized.

## 7. UI placement

### Runs detail

The V0 action lives primarily in existing Runs detail because that surface already owns historical run selection/read evidence.

For an eligible run:

`Load as working configuration`

For an ineligible run, show a disabled/non-action state with the first semantic incompatibility reason; do not hide the historical run.

The action must not be shown as execution, promotion, restore-to-project, or canonical write.

### Properties

Properties shows the loaded baseline context, for example:

`Baseline: Run 41 · Previous successful run`

Fields equal to that baseline report source `Previous successful run`; once edited they report normal working-edit/source semantics. Exact run id/digest belongs under Inspect/Audit.

006b does not add the 058b comparison matrix or a second variant selector store.

## 8. Current preflight and execution semantics

After successful load:

1. the old preview is invalidated;
2. current deterministic preview runs against the exact matched current model contract;
3. a representable snapshot may still become non-ready because current deterministic constraints/dependencies differ;
4. non-ready state blocks Run and creates zero run records;
5. explicit Run continues through the existing single 071b request-key path;
6. a real execution failure remains a persisted failed run and preserves the edited working configuration;
7. successful execution may become the new local working baseline under existing 071b rules;
8. no execution promotes values into canonical Parameters/Decisions automatically.

006b adds no second run launcher and no background rerun.

## 9. Stale/race rules

Implementation must fail closed without partial apply when any of these change between eligibility/fetch/confirmation/apply:

- workspace;
- selected source run;
- load generation;
- current working revision after the operator saw dirty-state confirmation;
- exact target model version / contract digest;
- current semantic target where required;
- source run availability/status;
- route-driven state that invalidates the intended target owner.

A new load intent invalidates all older load responses. Duplicate rapid actions may coalesce or make the earlier intent stale; they must not apply twice or create any run/provider side effect.

Preview responses from before the load cannot authorize Run after the load because normal 071b revision/preview-generation guards remain authoritative.

## 10. Exact answers to definition §15 readiness questions

1. **Which Runs endpoint contains persisted snapshot/model/status/label?**  
   Existing `GET /workspaces/{workspace_id}/simulation-runs/{run_id}` / `getRun(...)` returns `SimulationRunDetail` with `model_version_id`, `run_label`, `status`, `input_payload` and `parameter_payload`.

2. **Is snapshot evidence sufficient or is a backend seam needed?**  
   Sufficient for V0. `input_payload` is the persisted validator-owned effective snapshot with exact units and linked-source evidence. Reconstruction deliberately restores effective historical values as literals, so no new backend read route is required.

3. **Can 058c model-option identity be reconstructed exactly?**  
   Yes, only by resolving the run's exact `model_version_id` to the immutable/currently readable `ModelImplementationRead` and using that implementation's exact input contract / schema-v3 semantic context. No cross-version inference is allowed.

4. **Smallest compatibility predicate/error taxonomy?**  
   The exact predicate is §3. Same workspace + succeeded + exact model version exists + exact contract variable/unit set + required values present + current semantic applicability. Errors use the bounded semantic reasons in §3.

5. **Where does the operator action live?**  
   Runs detail is the only new action surface. Properties receives the already-global controller state and displays baseline provenance. No duplicate action implementation is needed in Properties.

6. **How are stale loads invalidated without a second owner?**  
   One controller-owned monotonic load generation plus expected workspace/model/working-revision/semantic-target preconditions; model switch + apply is coordinated inside `useEngineeringProperties`. Existing preview generation invalidates pre-load preflight responses.

7. **Is `run_label` sufficient as first variant identity?**  
   Yes. Use persisted `run_label` with an `Unnamed run` fallback. No new durable variant-name metadata/store is justified.

8. **What evidence proves zero side effects?**  
   Focused controller/API mocks plus browser assertions must prove no Parameter/lifecycle PATCH, no runner create/run, no AI/provider/thread call during eligibility/load; then explicitly pressing Run proves the existing runner path is the only execution path.

## 12. Deterministic acceptance

Focused deterministic/frontend tests must prove:

1. exact succeeded run + exact model version + exact units reconstructs the expected complete working map;
2. historical `source_parameter_id` does not become a live current binding on load;
3. loaded baseline provenance is Previous successful run and editing one field switches that field to normal working-edit semantics;
4. failed/queued/running/cancelled/timed-out runs are not loadable;
5. missing model version is not loadable;
6. unknown field, required missing field, malformed item, nonfinite value, or exact-unit mismatch fails before any working mutation;
7. dirty working state requires explicit confirmation and cancel is side-effect free;
8. working revision/workspace/model/load-generation change makes an in-flight load stale;
9. model switch + historical apply occurs only for the exact intended model version and cannot be completed by an older late response;
10. loaded state invalidates old preview and runs fresh preflight;
11. non-ready loaded state creates zero runs;
12. load creates zero runner jobs/simulation runs/provider calls/AI thread calls/canonical record mutations;
13. explicit subsequent Run still uses the existing request-key path;
14. Revert returns to the loaded historical baseline;
15. no 058b comparison behavior, durable variant CRUD, child BLUECAD candidate, or canonical promotion appears.

## 13. Browser acceptance

Real browser evidence on the immutable product head must cover:

- Runs detail for a compatible succeeded run exposes `Load as working configuration`;
- loading changes Properties to the exact persisted values/units and shows `Previous successful run` baseline context;
- a persisted historical linked Parameter is restored as historical effective value, not silently relinked to current Parameter authority;
- dirty current working state produces explicit replacement confirmation; cancel preserves current edits;
- incompatible/legacy run remains inspectable but visibly non-loadable with reason;
- after load, current `Ready` or real deterministic blockers appear; Run is disabled when non-ready;
- editing after load creates normal dirty state and Revert returns to the loaded baseline;
- workspace/model/load switch during fetch cannot apply stale data;
- no run/provider/canonical mutation occurs until explicit Run;
- keyboard-only operation and visible focus;
- effective 200% / compact containment with no page-level horizontal overflow;
- light/dark/system and reduced-motion behavior remains semantic;
- Runs + Jarvis/Properties + Analysis Dock containment does not regress.

Screenshot appearance alone is not evidence; assertions must cover state/effects and zero-side-effect boundaries.
