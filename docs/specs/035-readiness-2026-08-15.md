The implementation is therefore frontend-only and read-first. It reuses App-owned `workspaceId`, existing workspace-scoped list contracts, the 083 shell, 087 lineage/freshness ownership and 088 run ownership. Legacy Domain Foundation remains the mutation/scenario surface.

## Exact supported record kinds

035 supports exactly four canonical record kinds in this slice:

1. `model-spec` from `listModelSpecs(workspaceId)` / `GET /workspaces/{workspaceId}/model-specs`;
2. `assumption` from `listAssumptions(workspaceId)` / `GET /workspaces/{workspaceId}/assumptions`;
3. `parameter` from `listParameters(workspaceId)` / `GET /workspaces/{workspaceId}/parameters`;
4. `decision` from `listDecisions(workspaceId)` / `GET /workspaces/{workspaceId}/decisions`.

Do not include model implementations, simulation runs, proposals or arbitrary future entities. Runs remain in 088; implementations/scenario execution remain legacy until separately migrated.

## Existing typed authority and nullability

`frontend/src/api/client.ts` is the implementation authority for this slice.

### ModelSpec

Fields: `id`, `workspace_id`, `title`, `engineering_question`, optional nullable `scope`, `status`, `maturity_status`, `schema_version`, `created_at`, `updated_at`.

### Assumption

Fields: `id`, `workspace_id`, `statement`, optional nullable `confidence`, `status`.

`confidence` is displayed only as the persisted numeric field; 035 must not reinterpret it as system confidence, correctness probability or promotion authority.

### Parameter

Fields: `id`, `workspace_id`, `name`, optional nullable `symbol`, optional nullable `value`, optional nullable `unit`, `status`.

`value` remains inert persisted text. 035 performs no unit conversion, dimensional inference or numeric recomputation.

### Decision

Fields: `id`, `workspace_id`, `title`, `decision_text`, `status`.

No separate detail endpoint is required: the existing list responses already contain every field authorized for the 035 inspector.

## Freshness, proposal and provenance authority

The four 035 record types expose no 051 freshness field and no canonical proposal/review state beyond their existing persisted `status` fields. Therefore:

- do not synthesize `fresh`, `stale`, `accepted`, `proposed`, `rejected`, confidence or lineage labels from timestamps/status strings;
- render the persisted `status` verbatim, including unknown values;
- freshness is `Unavailable` unless navigation into the existing 087 surface provides separately authoritative evidence;
- concise provenance is limited to canonical record id/workspace id and fields already returned by the record contract;
- do not issue extra graph/freshness requests merely to decorate every row.

This deliberately leaves proposal-review authority to 054 and graph/freshness interpretation to 087.

## Projection, search and deterministic order

Use a small typed projection with `{ kind, id, workspaceId, primary, secondary, status, record }`. Do not stringify complete objects for search.

Kind order is fixed:

1. `model-spec`;
2. `assumption`;
3. `parameter`;
4. `decision`.

Within a kind, sort by case-insensitive primary label, then canonical `id` as the stable tie-breaker.

Primary/search fields:

- model spec: `title`; search also `engineering_question`, `scope`, `status`, `maturity_status`, `id`;
- assumption: `statement`; search also `status`, `id`;
- parameter: `name`; search also `symbol`, `value`, `unit`, `status`, `id`;
- decision: `title`; search also `decision_text`, `status`, `id`.

Search normalization is trim + Unicode-safe lowercase on those explicit text fields only. Empty query shows all fetched supported records. Kind filters are additive; unknown persisted status values never remove a record unless the operator's text query excludes it.

No arbitrary result cap is introduced in this slice because the existing list contracts already return bounded current-workspace collections and no current evidence demonstrates a scale failure requiring pagination/search infrastructure. Rows must remain locally scrollable inside the stage rather than expanding page overflow.

## Request and failure ownership

Fetch the four record lists independently under one workspace generation token. Each request captures both generation and workspace identity; A→B→A late completions are rejected.

Workspace change synchronously clears all prior-workspace record arrays, errors and selection before new responses may paint.

One record-kind failure must not discard successfully loaded kinds. Each failed kind renders one bounded error state in the workbench while the other kinds remain usable. A later successful refresh replaces that kind's error.

No separate record-detail request exists, so X→Y→X network races are not applicable. Selection is over already-fetched immutable projections.

On refresh/search/filter change:

- preserve selection only when exact `{kind,id}` remains visible;
- otherwise select the first deterministic visible row when one exists;
- otherwise clear selection;
- never retain a hidden/disappeared record in the inspector.

Historical nullable fields render `Unavailable`, not empty fabricated values. Unknown `status`/`maturity_status` strings render verbatim.
