## Route decision

Fresh provider configuration proves:

- Scaleway already has the exact provider-specific route `external:scaleway`;
- DeepSeek currently participates in `external:cheap`;
- `external:cheap` has a configured fallback chain from DeepSeek to GLM.

Using `external:cheap` for a DeepSeek diagnostic would therefore change semantics: a retryable DeepSeek failure could become a GLM diagnostic call. Readiness rejects that downgrade.

The accepted implementation direction is the smallest canonical declarative change:

- add `external:deepseek` to the existing `deepseek-v4-pro` route classes in `configs/ai_providers.yaml`;
- do **not** add a fallback chain for `external:deepseek`;
- leave `external:cheap` and its existing DeepSeek→GLM fallback unchanged;
- `deepseek_provider_smoke` requests `external:deepseek` through canonical execution;
- Supervisor maps existing operator `provider_mode=deepseek` to `external:deepseek` and `provider_mode=scaleway` to `external:scaleway`;
- diagnostic modules do not instantiate adapters, read provider credentials, or implement fallback.

This preserves explicit diagnostic provider intent while moving dispatch authority into the canonical execution/provider/egress spine.
